## 3. 本迭代最重要的三条认知

### 3.1 「错误码」是契约，不是实现细节

REQ-007 的第一个 HIGH 是个教科书级案例：

```
存在账号 第 6 次错密码 → 403 ACCOUNT_LOCKED
不存在账号 永远        → 401 INVALID_CREDENTIALS
→ 6 请求/候选即可枚举账号存在性
```

Dev 当时的论证是「未注册账号永远拿不到 `ACCOUNT_LOCKED`，所以不构成枚举」—— **方向反了**：
「拿不到 A 却拿到 B」本身就是判别器。

**最终修法**（D20）：把锁定判定挪到**密码校验之后**。
攻击者只得 `INVALID_CREDENTIALS`，而**知道密码**的被锁用户仍得 `ACCOUNT_LOCKED` —— 两个约束同时满足。
副作用还消掉了 75 倍的时序差（锁定路径原本跳过 Argon2，8.1ms vs 606.9ms）。

**教训**：凡是「两种失败路径返回不同信息」的设计，都要先问「这个差异是不是判别器」。
错误码、状态码、响应体、响应头、耗时 —— **五个维度都能泄露**。

### 3.2 安全机制有前提，前提必须被强制检查，不能靠文档

REQ-006 抓到：**超级用户绕过 RLS**。

开发库的 `base` 是超级用户 → RLS 对它**完全不生效** → 租户隔离 **fail open**。
数据库层那道兜底，在当时等于没装。

Dev 补了角色分离，但真正的修正是**让前提被强制**：
应用启动时检查「当前连接角色是否超级用户 / 是否 BYPASSRLS」，命中就**退出码 3 拒绝启动**。

**教训**：安全机制要写清它的**前提条件**，并且**在启动时断言前提成立**。
「文档里写了要用普通角色」不算，「用超管就连服务都起不来」才算。

### 3.3 我给 Dev 的「实测数字」如果没自己测过,就得标注

Sprint 2 我至少 4 次给了错的信息，其中一次还直接导致 Dev 踩坑：

| 我说的 | 实际 |
|---|---|
| `link-self-contained=+linker` | stable 上**直接报错退出** |
| 冷编译 6-12 分钟 | **21 秒**（依赖集只有 88 个 crate） |
| SCIM 出站零新增依赖 | **+2**（`want`/`try-lock` 是 hyper 的 http1 客户端带来的） |
| `cargo test -- --include-ignored -- --test-threads=2` | **双 `--`** → libtest 把 flag 当过滤串 → **0 passed 却 exit 0** |

第 4 条是最险的 —— 它是**假绿**，而我一直在教别人防假绿。

**教训**：给 Dev 的每个数字，如果不是**我自己在这台机器上量过的**，
就必须标注「未实测，实测值由你产出」。**我给的是参考，不是事实。**

## 6. 低配机实测（第二轮数据）

| 项 | Sprint 1 | Sprint 2 | 说明 |
|---|---|---|---|
| 第三方依赖树 | 88 → 91 | 175 → **273** | 安全能力与 LDAP 是主要增量 |
| 冷编译 `cargo check` | 21s / 1074MB | 46.0s / **1039MB** | 依赖翻倍但**峰值没涨**（profile 调优的功劳） |
| 冷编译（含链接） | 59s / 1414MB | 75s / **1471~1763MB** | 链接阶段方差 ±300MB，**仍在 1.5~2.5G 预算内** |
| 增量 `cargo check` | 0.67s | 0.98s | 日常体验没退化 |
| 数据库栈内存 | 81MB | 81MB | rootless podman，没变 |
| 磁盘占用 | ~2GB | **~4GB** | 预算 20GB，余量充足 |

**结论**：在这台机器上，**依赖树翻倍没有让编译峰值翻倍** —— 真正决定峰值的是
`profile.dev` 的调试信息策略与 `jobs`，不是依赖数量。所以「最小依赖集」的价值
主要在**编译时间**（21s vs 46s），而不在内存。
