## 1. 交付了什么

**租户能接自己的企业身份源登录底座 —— 用户不必在底座里再记一套密码。**

| 层 | 内容 |
|---|---|
| **OIDC 入站** | 授权码 + PKCE：`state` 一次性凭据、`nonce`、发现文档、JWKS（**未知 `kid` 触发刷新**，**拒绝 `x5c`/`jku`**）、算法白名单**硬编码** `RS256`+`ES256` |
| **LDAP 入站** | `SsoLdapClient` trait（**可计数**，否则「空密码 0 请求」没有观测面）+ **RFC 4515 转义** + **空密码连接前拦截** |
| **强制 SSO** | 在**加载用户之前**早退（Argon2 调用计数 **== 0**）；配置读失败 **fail-closed** |
| **回调交接** | `callback` → **302** 到前端 `/sso/callback?ticket=…`，前端 `POST /sso/exchange` 换会话（**token 不进 URL**）|
| **账号绑定** | `ON CONFLICT DO NOTHING` + **读回比对**（**不可改指**）；JIT 建号并发幂等 |
| **审计** | 事件**声明 + 发出**（iam **自建**接缝），**落库留 REQ-014** |
| **前端** | 登录页企业入口、强制 SSO 提示、`SsoCallback` 页、21 个错误码中英文案 |

## 3. 六条教训

### 教训 1：**「我记得这个 API 是这样」不是证据 —— 而且我查的是「存在性」，不是「语义」**

QA 挑出的 51 条里，最严重的三条全是这个病。**我抽验全部成立**：

| 我在规格里写的 | 源码里的真实情况 | 照字面实现的后果 |
|---|---|---|
| 「`ldap3::simple_bind` 可直接校验密码」 | 返回 `Ok(LdapResult)`，**密码错误时外层仍是 `Ok`**（`rc=49`），必须再 `.success()` | **任意密码都能登录** |
| 「`GET /api/config/entries` 取全量配置」 | **必须带 `keys`**，不给返回空数组；`?scope=tenant` 参数**根本不存在** | 测试「0 命中 + 什么也没读到」= **三重假绿** |
| 「照抄 `upsert_external_identity`」 | 它是 `ON CONFLICT … DO UPDATE SET user_id`（**改指**）| 绑定可被**静默改到另一个用户** = 账号接管 |

**最要命的是：我并不是没调研 —— 我查了 9 项前置。但我查的是「存在性」。**

| 我查的 | 结论 | 我没查的 |
|---|---|---|
| `simple_bind` 存在吗 | ✅ 在 `ldap.rs:238` | 它**返回什么**、`Ok` 意味着什么 |
| config 有 `format` 校验吗 | ✅ 有 | `read_entries` **要不要参数** |
| `external_identity` 与 upsert 存在吗 | ✅ 有 | 那条 SQL 的**冲突分支**写的是什么 |

> **「这个能力存在」和「这个能力的行为是我想的那样」是两件事。**
> 前者一个 `grep` 就够，后者必须**读实现**。
>
> 已写进 dev-guide **§9.11**，附四类必须核对的东西：
> 返回类型与语义 / 参数是否必填 / 冲突时的行为 / 加字段的连带影响。

### 教训 2：**「判据」和「目标」不是同一件事 —— 修一半比不修更危险**

这是本轮**最贵的一课**，也是只有「自己注入变异」才能发现的。

Q4 的原始问题是：LDAP bind 的判定 `.success()` 那一行**零测试覆盖**，
所有测试用 `RecordingLdap` 直接返回 `Ok(false)`，**绕过了整个生产包装层**。
QA 的原话：「若有人把判定删掉，753 条测试仍全绿。」

修复轮的做法：抽出纯函数 `bind_succeeded(rc) -> bool`，加单测 + 变异验证。
**从「判据」角度看，它做对了** —— 变异 `bind_succeeded` 恒 true，3 条测试红。

但独立复核做了我没想到的事：**它去变异「生产那一行」**（`Ok(bind_result(&result))` → `Ok(true)`），
**全部测试仍然全绿**。我亲自复现确认了这一点。

**根因是结构性的**：`SsoLdapConn::simple_bind` 返回 `Result<bool>`，
**决策发生在生产包装层内部**，而测试替身绕过了整个包装层。
所以「加纯函数单测」只覆盖了**判定逻辑**，没覆盖**「有没有调用它」**。

> **修法（D129）**：把 trait 签名改成 `Result<ldap3::LdapResult>`（**不让包装层做决策**），
> 决策点 `bind_result(&result)?` **上移到 service 层**。
> 这样测试替身可返回 `Ok(LdapResult{rc:49})`，「把决策改坏」会被**集成测试**直接抓到。
>
> **验证**：我注入变异后 **4 条集成用例红，而 76 条 lib 单测仍绿** ——
> 这个分层正好证明：单测覆盖判据、集成测试覆盖调用点，**两层现在都在**。

**我验收时只看「有没有纯函数、变异会不会红」，没问「这个纯函数在哪里被调用、那条路径测到了吗」。**

### 教训 3：**「阳性对照」可以写成形式主义**

Pre-merge 抓到的 Q1 是一种特别隐蔽的假绿：

```rust
// 号称是「阳性对照」，实际对任何输入都成立
let injected = format!("{dump}\n{CANARY}");
assert!(injected.contains(CANARY), "扫描器必须能命中 canary");
```

它把 canary **拼到输出后面**再断言「包含 canary」—— 证明的是「字符串拼接能拼上」，
**不是「扫描判据有区分力」**。

讽刺的是：**「阳性对照」是我自己写进出口标准 §9.2 的**，然后它被写成了形式主义。

> **修法**：往**真实的** `SsoAuditPayload` 的 `user_agent` 注入 canary，
> 用**同一个** `scan_hits` 判据扫，断言命中 1 次。
> 现在判据退化成恒 0 → 红；序列化丢白名单键 → 红。
>
> **验证方式**：变异 `scan_hits` 恒 0 → 测试红，报错正是「扫描判据必须能命中注入的 canary」。

### 教训 4：**我又写了一条物理不可达的 AC（第三次）**

AC-S-105 步骤 6 原文：「把 `frank` 的 `mail` 改成已被 `gina` 绑定的邮箱 → 登录 → 409」。

但因 **P6「`external_id`（DN）优先」**，DN 没变 → 第一步就命中 `frank`，
**永远走不到 mail 匹配** → 这个前置**物理上不可达**。

**前两次**：

**而且这次是 Dev 和 QA 都判断出来了，我又是最后一个知道的。**

> 共同点：**写 AC 时只在纸上推演，没走一遍真实执行路径。**
>
> 这条我要老实说：**三次了，说明「写时可执行性检查」还没有变成我的习惯**，
> 光靠「记住教训」是不够的。可能的机械对策：AC 里每条前置都要求标注

### 教训 5：**跨端缺口只有做的人才会撞上**

前端 Dev 发现 `GET /api/iam/sso/oidc/authorize` **也带不上请求头**（它是整页导航的起点，
且此刻还没有 `state` 可反查租户）。QA 挑了**回调方向**，我据此写了 P3；**authorize 方向漏了**。

前端 Dev 还顺手修了 `router.ts` 的 `start()` 会抹掉查询串 —— 那是 **REQ-011 的既有缺陷**，
之前没有页面依赖 URL 参数所以从未暴露（登记 TD-021）。

> **双 Dev 并行的价值不在快，在交叉发现。**
> 只要 AC 用脚本客户端验证，就永远发现不了「真实浏览器做不到」。

### 教训 6：**Dev 主动报「还没做好」比报「全部通过」有价值**

后端 Dev 的诚实清单里有一条**真风险**：

> **`client_secret` 是单环境变量、多租户共用。**
> 多 IdP 场景下这是真错。AC 没覆盖（mock IdP 不校验 secret），所以**验收会过，但生产会坏**。

这条如果它不说，我这轮会带着一个「验收通过、生产会坏」的问题合并（登记 **TD-022**，标为高风险）。

同理它指出**规格数字错**（`TITLES.len()` 我写 56/77，实测 58/79）——
我一开始用两种方法数出来确实是 56，**差点驳回它**，查下去才发现漏了 6 条 `org.member-added`
这类**事件码**（也在同一张表里）。

> **Dev 纠正 BA 的规格错误时，要先怀疑自己的统计口径。**
