## 3. 三条核心教训

### 3.1 让 QA 在 Dev 动手**之前**写用例，并**明确要求它挑验收标准的毛病**

REQ-009 用这个流程挑出 22 条；REQ-010 沿用，挑出 **50 条**。

**比例在恶化，不是在改善**：REQ-010 的 50 条里有 **12 条是我自己写错的**，
包括 7 条纯设计错误（不留到实现后就是省 7 轮返工）：

| 我写的 | 为什么错 |
|---|---|
| `SELECT max(epoch)` 判缓存失效 | 租户 epoch 高于平台时 **`max` 不变** → 只要某租户先改过自己的配置，之后所有平台级变更对它全部失效不掉 |
| 「租户连接连写都写不进平台表」 | 本仓只有一个 `base_app` 池、无平台管理角色，且 `ALTER DEFAULT PRIVILEGES` 让**新表自动继承写权** —— 这句话是空话 |
| flag 登记 `boolean` 又要求 `rolloutPercent` | 那个值**无处安放**（另立键被「未声明 400」拒） |
| 「跑平台的契约测试」验 C-5 | 该入口**不存在**（`ContractFixture` 要求 `Repository`+`PlatformModule`） |
| 一条 `PUT` 路由管两种写权限 | 静态 `route_layer` 做不到：要么挡住租户级写、要么平台权限点**无调用点** |
| 给 `ConfigScope` 加 `default` 变体 | 它同时是**写入作用域**类型 → 凭空开出**第 4 个可写层** |
| 未定校验顺序 | 越级写会把类型校验**顶包** → 类型校验根本没被验到 |

**结论**：这条流程已经证明有效，但它**不是一次性的**。规格越长，自己写错的概率越高。
**REQ-011 起要把「QA 挑刺」写进迭代出口标准**，而不是当作 REQ-010 的临时做法。

### 3.2 ★ 修漏洞会制造新漏洞 —— 修复本身要被独立复核

这是本轮最贵的一课。REQ-010 的修复被 QA 打回**两次**：

| 轮次 | 我修了什么 | QA 折出什么 |
|---|---|---|
| 1 | 越级写断言：行数 → **快照比对** | ① `before_snapshot` 取在**被测写操作之后** → 污染已进「写前」快照 → 必然「一致」<br>② SQL 只取 `count` + `max(value)`，**同值覆盖不可见**<br>③ **我的注释声称覆盖了 `updated_at`，而 SQL 里没有** |
| 2 | 日志过滤器：补 target → **抽到 `platform-core`** + 全局默认级别 | `NOISY_TARGETS` 里 `tower_http` **根本不在依赖树**、`hyper` 未启用 tracing → **两条空转**；测试被 `RUST_LOG` 劫持（5 条会红） |

**三次都是同一类错误**：**断言/配置写了一个「看起来对」的形态，但没验证它真的能抓到东西。**

于是得到两条硬规则（D89 / D90）：

> **D89 快照断言的取点必须在任何被测写操作之前，且必须含 `updated_at`**
> —— 否则「同值覆盖」不可见。
>
> **D90 降级/过滤清单的每一项都要能被验证**
> —— 空转项不会报错，但会让读者**误以为噪音已处理**。

**推论**：**「我修好了」必须由没参与修复的人验证**。BA 自己修的东西，更要被复核 ——
因为修的人知道自己的意图，容易把「意图」当成「事实」。

### 3.3 注释与代码不一致，比没有注释更坏

`conflict_strategy_snapshot` 的注释写着「`updated_at` 也抓」，
而 SQL 里**没有 `updated_at`**。下一个人读注释会得出结论「这块是安全的」。

这与本仓反复出现的「静默放行」是同一个病根：**证据链完整，结论错误**。

**规则**：注释里凡写「也覆盖 X」「也能抓到 Y」，**必须有一条变异验证支撑**。
写不出变异，就别在注释里承诺。

## 4. 技术上值得记的

### 4.1 「测试与生产必须调同一个函数」是结构问题，不是纪律问题

REQ-010 的 HIGH：`platform_config` 的 WARN 在默认部署下被**静默丢弃**。
根因不是「漏了一个 target」，而是**测试够不着生产的 `log_filter`** ——
只能用 `EnvFilter::new("platform_config=warn")` 近似，于是「测过的」与「线上跑的」**不是同一份代码**。

**修法**：把 `log_filter` 抽到 `platform-core`，测试与生产调同一个。
再配上「全局默认级别 + 噪音库降级」的形态 —— **新增 crate 不需要改清单**，漏配不再是失败模式。

> 本仓这个 bug **犯过两次**：先漏 `base`（bin crate 名 ≠ lib crate 名），后漏 `platform_config`。
> 第一次的注释里甚至写着这个坑，第二次还是踩了 —— 因为修法是「补清单」，不是改形态。

### 4.2 三张表 vs 单表 nullable：RLS 的 `WITH CHECK` 是写侧口子

单表方案下 RLS 只能写成 `tenant_id IS NULL OR tenant_id = current_setting(...)`，
而 `tenant_id IS NULL` 那一支**同时放行了平台级行的插入** → 租户能写一行影响所有租户。

**这是写侧越权，比读侧更严重**（读侧还有 RLS 兜底，写侧没有）。
拆三张表后平台级表**没有 `tenant_id` 列**，`WITH CHECK` 只剩一条语义。

配套：`REVOKE` 直接 DML + `SECURITY DEFINER` 函数作为**唯一写通道**。
但**别把话说满** —— 数据库保证的是「没有意外的写路径」，不是「没有写路径」；
应用被攻破仍可调那个函数。

### 4.3 灰度的确定性：`RandomState` 是多实例部署的隐形杀手

`sha256("<flag>:<user>") % 100` 与阈值比较，**不能用 `RandomState`**
（每进程随机播种 → 同一用户在不同实例判出不同结果，表现为「一半请求命中」）。

这条**单进程测不出来** —— 必须用两个独立进程判同一批用户。

### 4.4 未校验的请求头不得改变行为

`X-Space-Id` 是**完全未校验**的（契约 C3：缺失视为不限空间、不报错），本仓又没有 space 实体。
所以：空间级配置**只对展示类白名单键**生效；**Feature Flag 不支持空间级**。
能把别人空间的品牌换成别的，是低危；能把别人的 `conflictStrategy` 换掉，是高危。
