## 3. 本轮最重要的三个流程改进

### 3.1 ★ 让 QA 在 Dev 动手**之前**写用例，并**明确要求它挑验收标准本身的毛病**

**做法**：REQ-009 开工顺序是「BA 写规格 → **QA 写 61 条用例（允许挑刺）** → BA 裁定 → Dev 实现」。

QA 在用例设计阶段挑出 **12 条**验收标准问题，复核阶段又挑出 **10 条**。其中 5 条是硬伤：

| 问题 | 为什么是硬伤 |
|---|---|
| AC-S-045 自相矛盾 | 前置条件写「用户**有权**访问 R2」，第 3 步预期却写「两次响应状态码相同（都是 404）」—— 不能同时成立。**存在性不泄露的对照对象本来就搞反了**：应该是「越权资源」vs「不存在资源」 |
| AC-S-040 与设计冲突 | 要求造出「两个主部门」，但设计又加了部分唯一索引拦住它 —— 需求内部矛盾 |
| AC-S-041 无法区分并集与交集 | 步骤 3 的结果与步骤 1 相同 → 就算实现取交集也会通过 |
| AC-S-042 注入判据不成立 | 「注入串与原值不同时，结果必然不同」—— 判据本身是错的 |
| 管理接口自举防护缺失 | 初版没规定谁能调 `/api/rbac/*` —— **任何登录用户都能给自己授权 `platform-admin`** |

**为什么值得**：这 5 条如果留到 QA 验证阶段才发现，就是**两轮返工**（Dev 写完 → QA 打回 → 改 → 再验）。
放在开工前发现，成本是 BA 多改两轮文档。

**教训**（与 Sprint 1 / 2 的教训同源，但更进一层）：
> Sprint 1/2 的教训是「**代码**里最容易出的是静默放行」。
> Sprint 3 的教训是：**「验收标准」本身也是「看起来对」的产物** —— 写得再仔细，也会自相矛盾、判据不成立、漏掉攻击面。
> 让一个**以挑刺为职责**的角色（QA）在实现之前先读一遍规格，收益远大于 BA 自己反复读。

### 3.2 ★「多 X 怎么合并」必须写成**可判定的真值表**

本轮 BA 写了一条规则：「`CUSTOM` 不参与宽松比较：与其它 scope 同时出现时，取 `CUSTOM` 那一路」。

**Dev 忠实实现了它，然后上报疑问**：这个结果**既不是并集也不是交集**，
而且会让「加一个角色**缩小**可见范围」—— 与同一份设计里 §4.3 的「多角色取最宽松（并集语义）」**直接矛盾**。

**根因不是实现，是规格**：BA 想比较「宽松度」，但五种 scope **没有全序**
（`CUSTOM` 与 `ALL` 之间无法比较）。**凡是要比较却没有全序的东西，规格里就不能只写一句话**。

**改法**（D37）：不比较宽松度，**直接做过滤条件的并集** —— 与权限点「任一满足即通过」一致。
`CUSTOM` 之间取 **OR**，`CUSTOM` 与包含型 scope 也取 **OR**。

**教训**：
> 「A 和 B 同时出现时怎么办」是规格里**最容易写出一句话糊弄过去**的地方。
> 写不成真值表，就说明这个概念**缺一个序** —— 那时候该改的是概念，不是措辞。

### 3.3 ★ 规格的**实现**和规格的**文字**会各走各的，要分开验

Dev 上报了第二个问题：trait 文档写「非法条件返回 `None`」，
而**已裁定的 D40 说应该返回「永不匹配的条件」**。实现按 D40 做的（对的），
**文档**却还是最初的写法 —— 而调用方把 `None` 当放行。

**后果**：照文档实现 `PermissionChecker` 的下一个开发者，会**静默放行非法条件** ——
这正是 D40 要防的那类「静默放行」。**当前实现没有漏洞，漏洞在契约文字里。**

**教训**：
> 规格的**语义**由决策记录（decisions）裁定，但规格的**文字**散落在几十个 doc comment 里。
> 决策改了，文字不会自动跟着改 —— **必须显式检查文字**，而且要作为**独立的一条**去查。
> QA 的第 1 条 MEDIUM 就是这么抓到的。

## 4. 技术上值得记的

### 4.1 C-5 检查：扫**调用点**，不能扫字面量

`extension-points v1` §4 自己写明的缺口：「已登记权限点必须有对应鉴权调用点」。
实现时最省事的做法是**复用 C-2 的字面量扫描** —— 但 C-2 分不出
「定义了一个权限点常量」和「真的调用了鉴权」。**沿用它，C-5 会假绿**。

正确做法：扫 `require_permission(` **调用**的字面量参数。
QA 用**自造夹具 + 独立探针**验了这一点：只有 const 字面量、没有调用的模块，
被判成「已登记但无鉴权调用点」→ **失败**。

**推论**：「C-2 沿用 C-1 的实现」这类**看似省事的复用**，在检查类代码里往往是错的。

### 4.2 鉴权入口必须放 `platform-core`，不能放 `platform-rbac`

业务模块的运行期依赖只有 `platform-core` + `platform-db`（AGENTS.md 硬规则 2）。
入口若住在 `platform-rbac`，业务模块就得依赖平台内部模块 → 违规。
`platform-core` 本来就依赖 axum，放得下；实现靠**请求扩展**注入
`Arc<dyn PermissionChecker>`（trait 全同步 → 仍 dyn 兼容），不靠泛型状态。

### 4.3 缓存用 **DB epoch**，不引 Redis 客户端

本仓**当前没有任何 Redis 客户端依赖**，`base-redis` 容器无人使用。
epoch 方案（变更方自增、读取方比对）**跨进程正确** —— 纯进程内广播只在单实例下正确。
代价是每个已认证请求多一次主键查询（本机 PG 约 0.1ms 量级）。

### 4.4 测试夹具的**全局 schema 变更**是间歇性失败的常见来源

QA 的第 2 条 MEDIUM：fail-closed 用例为了验证「DB 预防层失效」，
**全局** `DROP INDEX` 了唯一索引再装回。若中途 panic，**预防层会留在关闭状态**直到本轮结束
→ 后续用例失去 DB 层保护 → 间歇性失败。

Dev 的修法：歧义测试改在**独立 schema** 里跑（平台已有 `DbOptions.schema` 旋钮），
**全局索引从此不再被摘**；DELETE 补上 `tenant_id`；收尾断言索引仍在。

**这条同时推翻了 Dev 的一个归因**：Dev 把某条 `platform-org` 的偶发失败归因为
「与本次改动无关（platform-org 不碰 ScopeFilter）」——
但 REQ-009 **恰恰给 `user_org` 加了这条全局索引**，且新增了**运行期摘掉它**的用例。
**「无关」的归因没有证据支撑。** QA 15 次 org + 4 轮完整套件未能复现，
根因**至今未定论** —— 机制已消除，根因未查明（遗留项）。
