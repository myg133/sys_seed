## 本需求自有 AC

### AC-S-088: 后端错误体**零中文**（跨全部模块）
- **前置条件**: 平台已运行；`title` 已收敛到集中的 `TITLES` 表（D113）
- **测试步骤**:
  1. **静态 ①**：找到 `TITLES`（集中映射表），断言**每一行**的 title 值都是纯 ASCII
  2. **静态 ②**：`grep` 全仓确认**没有第二处** title 文案来源 ——
     即 `fn *title*` 只剩「转发到 `TITLES`」，不再有机内 `match` 字面量
  3. **运行时**：遍历 `TITLES` 的**每一个 code**，触发对应错误，抓响应体
  4. 对每个响应体，断言 `title` / `detail` / `type` 三个字段都不含 CJK
- **预期结果**:
  - 1 → `TITLES` 表**零 CJK**
  - 2 → `grep -E 'fn \w*title\w*' -A 20` 的结果里**没有**中文字符串字面量
  - 3 / 4 → 每个触发到的响应体，三个字段都**零 CJK**
  - **未覆盖的 code**（没有触发条件的）→ 用静态 ① + ② 保底
  - ⚠️ **允许**：`tracing` 日志中文（契约 C6）、`params` 里的用户数据、代码注释
- **类型**: 功能
- **⚠️ rev 1 的错（必须记住）**：rev 1 写「检查 `ProblemDetails` 构造点的字符串字面量」——
  **实际 54 处由 `title_of()`/`title()` 函数产出**，构造点拿到的是函数调用 →
  **扫完 0 命中、全部通过**。这是**必然漏报**，比误报危险得多。
- **为什么收敛成一张表**（D113）：54 处分散在 4 个 `match` 里，静态扫不干净；
  收敛后「扫一张表」就可判定，且**新增错误码只能往表里加**

  - 3 → 文案里出现的每个 `{key}` 都能在 `params` 里找到
- **类型**: 功能
- **注意**：本条**只验后端**（`params` 是否完整）。前端能否渲染见 089b

### AC-S-090: 语言协商的多级优先级
- **前置条件**: 平台默认 `zh-CN`；租户 T1 配置 `en-US`；
  用户 U1 偏好 `ja-JP`；存在两个已注册语言 `zh-CN` / `en-US`
- **测试步骤**:
  1. 只带 `Accept-Language: zh-CN`（无用户偏好、无租户配置）→ 断言协商结果
  2. 租户配 `en-US`，请求头带 `zh-CN` → 断言
  3. 用户偏好 `ja-JP`（未注册），请求头带 `zh-CN` → 断言
  4. 用户偏好 `en-US`，请求头**不带** `Accept-Language` → 断言
  5. 请求头 `Accept-Language: fr-FR`（未注册）+ 租户 `en-US` → 断言
  6. 请求头 `Accept-Language: zh-CN;q=0.9, en-US;q=0.8` → 断言
  7. 请求头 `Accept-Language: *` → 断言
  8. ★ **用户偏好已注册 + 请求头相反**：用户偏好 `en-US`（已注册）+ 请求头 `zh-CN`
     → 断言 `locale` 与 `source`
  9. ★ **平台配置层**：平台级写 `locale=en-US`、**租户未配** → 断言
  10. ★ **平台 + 租户都写**：平台 `en-US`、租户 `ja-JP` → 断言
- **预期结果**:
  - 1 → `zh-CN`（请求头）
  - 2 → **`zh-CN`**（请求头 > 租户配置）。
    顺序已按 design §3.1 固定为：**用户显式偏好 > `Accept-Language` > 租户配置 > 平台配置 > manifest 默认**
  - 3 → `ja-JP` **未注册** → 回退到请求头的 `zh-CN`（因为用户偏好未注册即视为没设），
    **不是** `ja-JP`、**不是**租户的 `en-US`
  - 4 → `en-US`（用户偏好）
  - 5 → `fr-FR` 未注册 → 回退到 `en-US`（租户）或 `zh-CN`（平台默认），**不是** `fr-FR`
  - 6 → 按 `q` 值取**最高**的已注册语言 → `zh-CN`
  - 7 → `*` → **平台默认**（不做「任意匹配」）；`q=0` 表示**明确拒绝**该语言，跳过
  - 8 → **`locale === "en-US"` 且 `source === "user"`** ——
    **这一步是优先级的唯一有效判据**：两者相同时无法区分谁生效
  - 9 → **`en-US`**（平台配置层），`source === "platform"`；
    **不是** manifest 默认的 `zh-CN`
  - 10 → **`ja-JP`**（租户覆盖平台），`source === "tenant"`
  - **任何情况下**，协商结果**必须是已注册语言之一** —— 不允许返回未注册的 locale
  - **观测通道**（D110）：`GET /api/i18n/context` 返回
    `{ locale, timezone, currency, source }`；
    `source ∈ {user, accept-language, tenant, platform, default}`
    > **rev 3 修订（D119）**：原 4 值集合**缺 `platform`** ——
    > 平台级配置被**静默丢弃**，而**同一个键**在通用配置路由 `/api/config/entries`
    > 里读得到 `source=platform`。两处对同一键给出不同答案是**不一致**。
    > **裁定**：平台配置层**加入**协商（排在租户配置之后、manifest 默认之前），
    > `source` 集合扩为 **5 值**。
    > 依据：**D53** 已定 `scope` 是「允许覆盖到的最深层」→
    > `scope: tenant` 意味着**平台层可以写**，平台层的值就是**组织级默认值**。
    > 平台管理员改了全组织默认语言却毫无效果 = **静默丢弃运维配置**。
  - **时区的 `source`**：时区协商**不含请求头**（§3.4），故其 `source ∈ {user, tenant, platform, default}`
    （**永不出现 `accept-language`**）
- **类型**: 功能
- **顺序已固定**（design §3.1）：
  **用户显式偏好 > `Accept-Language` > 租户配置 > 平台配置 > manifest 默认**。
  > 起草时我把顺序写反了（原写「请求头 > 用户偏好」）——
  > **用户在我们系统里显式设的偏好应当最权威**，`Accept-Language` 只是「没设时的最佳猜测」
  >
  > rev 3 补入「平台配置层」（D119）—— 原 4 级链**少了**这一级，
  > 导致平台层配置被静默丢弃

### AC-S-091: 翻译键的命名规则与单一来源
- **前置条件**: 至少一个前端翻译包
- **测试步骤**:
  1. 列出全部翻译键
  2. 检查命名规则
  3. 检查同一语义的键是否重复
  4. 检查错误码对应的键与后端 `code` 常量是否**逐字一致**
- **预期结果**:
  - 2 → 键格式为 `<domain>.<key>`（如 `error.UNAUTHENTICATED`、`common.save`），
    且 `domain` 来自**固定枚举**（`error` / `common` / `schema` / `nav` …），
    不是随手写的字符串
  - 3 → **同一语义只有一个键**（不允许 `common.save` 与 `common.btnSave` 并存）
  - 4 → 错误类的键名**逐字等于**后端 `problem.rs` 里的 `CODE_*` 常量值
    （如 `error.UNAUTHENTICATED` 对应 `code === "UNAUTHENTICATED"`）
- **类型**: 可维护性

### AC-S-092: 缺失键的回退与记录
- **前置条件**: 基准语言 `zh-CN` 有键 `common.save`；目标语言 `en-US` **缺**该键
- **测试步骤**:
  1. 用 `en-US` 渲染 `common.save`
  2. 断言渲染结果
  3. 断言「缺失被记录」的证据
  4. 构造「**两种语言都缺**」的键，再渲染
  5. 检查渲染结果是否泄露 key 原文
- **预期结果**:
  - 2 → 回退到基准语言的文案（`"保存"`），**不是**空串、**不是** `common.save`
  - 3 → **可观察的记录**：至少满足其一 ——
    ① `console.warn` 输出含该 key；
    ② 导出一个 `missingKeys()` 返回缺失键集合；
    ③ 调用方可注入 `onMissingKey` 回调并被调用一次
    （**实施前在 design 里选定一种并写死**）
  - 4 → 两种语言都缺 → 渲染 **`"?"`**（统一占位）
    > **rev 2 修订（D-裁定 #7）**：rev 1 写「回退到键的最后一段」（`common.save` → `save`）——
    > **坏设计**：`error.INSUFFICIENT_PERMISSION` 的最后一段就是错误码本身，
    > 且与步骤 5「不含完整路径」打架。回退链简化为
    > **目标语言 → 基准语言 → `"?"`**
  - 5 → 渲染结果**不含**完整 key 路径（如 `common.save`）——
    那会向用户泄露实现细节
- **类型**: 功能
- **⚠️ 假绿防护**：步骤 2 不能只断言「非空」——
  现有的 `translate()` fallback 就是「回落到 key 本身」，
  那样 `"common.save"` 也非空。**必须断言「不是 key 本身」**

### AC-S-093: 租户级语言/时区/币种配置（走 REQ-010 的 config）
- **前置条件**: REQ-010 的 config 基础设施可用
- **测试步骤**:
  1. 检查 manifest 里是否声明了 `locale` / `timezone` / `currency`
  2. 检查每个的 `scope`
  3. 以租户 A 写入 `locale=en-US`，租户 B 不写 → 分别读
  4. 写入**非法**值（`timezone=Not/AZone`、`currency=XXXX`）→ 断言
  5. 检查默认值来源
- **预期结果**:
  - 1 → 三个键**都已声明**（未声明则写入会被 400 拒绝，D53）
  - 2 → 三个都是 `scope: "tenant"`（允许租户覆盖；**不是** `platform`）
  - 3 → 租户 A 读到 `en-US`；租户 B 读到**平台默认**
  - 4 → **400**，`code` 明确指出「值非法」；
    **不是**存进去后在渲染时才炸
    > **rev 2 新增（D111）**：manifest 的 config 段原本**只有 type，没有格式校验器**
    > → `timezone=Not/AZone` 会 200 落库。必须新增 `format`（固定枚举
    > `locale` / `iana-timezone` / `iso4217`）。**不用任意正则**：`^[A-Z]{3}$` 会放行 `XXX`
  - 5 → 平台的 `locale` / `timezone` / `currency` 默认值来自 manifest 的 `default`
- **类型**: 功能

### AC-S-094: 时区渲染 —— 同一时间点在不同时区正确（**只在前端**）
- **前置条件**: 后端存 `2026-01-15T00:00:00Z`（UTC）；租户 T1 时区 `Asia/Shanghai`，
  T2 `America/New_York`
- **⚠️ rev 2 收窄（D114）**：**时区渲染只在前端** —— 后端 `time` crate 无 tzdb，
  加则违反零新依赖；浏览器自带完整 tzdb。后端只负责时区**值的校验与存储**（D111）
- **测试步骤**:
  1. 前端以 T1 的时区渲染该 UTC 时间
  2. 前端以 T2 的时区渲染同一个 UTC 时间
  3. 断言两个结果
  4. 断言「**不是**直接把 UTC 字符串原样显示」
- **预期结果**:
  - 1 → `2026-01-15 08:00:00`（+08:00）
  - 2 → `2026-01-14 19:00:00`（−05:00，注意**日期变了**）
  - 3 → 两者表示**同一时刻**（转回 UTC 相等）
  - 4 → 若两个租户显示**相同**的本地时间，则**时区被忽略了** → 失败
  - 后端返回的**原始值**仍是 `2026-01-15T00:00:00Z`（UTC，契约 C13）——
    时区只影响**展示**，不影响**存储与传输**
- **类型**: 功能
- **⚠️ 关键**：必须选一个**跨日**的例子（如上），
  否则「时区生效」与「时区没生效但日期相同」无法区分

### AC-S-095: 时区与语言偏好的优先级
- **前置条件**: 平台默认 `Asia/Shanghai`；租户 T1 配 `America/New_York`；用户 U1 偏好 `Europe/London`
- **测试步骤**:
  1. 只租户配置 → 取时间
  2. 加上用户偏好 → 取时间
  3. 检查三者是否能区分（用同一个 UTC 时间点）
- **预期结果**:
  - 1 → 纽约时间
  - 2 → **伦敦时间**（用户 > 租户）
  - 3 → 三个时区的结果**两两不同**（否则无法证明优先级生效）
- **类型**: 功能
- **⚠️ 与 AC-S-090 的关系**：语言与时区**共用同一套优先级**（用户 > 租户 > 平台），
  但**请求头不参与时区协商**（`Accept-Language` 不含时区）→ 这点必须在 design 写明
- **⚠️ rev 2 收窄（D112）**：**用户级时区只在前端**（`sessionStorage`）——
  用户表**无该列**，所以「用户 > 租户」**在前端可验、在后端不可验**。
  本条只在前端验。要「跨设备」需另立需求（建列 + 迁移）

### AC-S-096: `Money` 全程整数，零浮点误差
- **前置条件**: `Money` 类型可用
- **测试步骤**:
  1. 检查类型的字段
  2. 做一组会**暴露浮点误差**的运算：`0.1 + 0.2`（浮点下 `!= 0.3`）
  3. 大额累加：`9_999_999.99 × 1000` 次
  4. 检查源码里是否有浮点类型参与金额运算
- **预期结果**:
  - 1 → 类型是 `{ minorUnits: i64, currency }` —— **整数**，不是 `f64` / `Decimal`
  - 2 → `Money::from_minor(10) + Money::from_minor(20)` **等于** `Money::from_minor(30)`；
    且 `Money::from_major("0.1") + Money::from_major("0.2")` **等于** `Money::from_major("0.3")`
    （**精确相等**，不是「差值小于 eps」）
  - 3 → 累加 1000 次后**精确等于**期望值（无累积误差）
  - 4 → 金额运算路径上**没有** `f32` / `f64`
  - **溢出**：`i64::MAX` 附近做加法 → 返回 **`MONEY_OVERFLOW`**（400），
    **不是** panic、**不是**静默回绕
    > **rev 2 补充（裁定 #11）**：rev 1 只说「返回错误」，没定码。
    > `MONEY_OVERFLOW` 要登记到 `TITLES` 表（D113）
- **类型**: 安全
- **⚠️ 假绿防护**：不能断言「差值 < 1e-9」—— 那是浮点思维。
  必须断言**整数相等**

### AC-S-097: 跨币种换算可追溯到汇率快照
- **前置条件**: 有汇率表；存在 CNY→USD 的两条不同日期快照
- **测试步骤**:
  1. 写入两条汇率快照（如 `2026-01-01` 与 `2026-06-01`，值不同）
  2. 用 `2026-01-01` 的快照换算 100 CNY
  3. 用 `2026-06-01` 的快照换算同样的 100 CNY
  4. 检查换算结果的**可追溯信息**
  5. 用**不存在**的币种对换算
- **预期结果**:
  - 2 / 3 → 两个结果**不同**（证明用了不同快照）
  - 4 → 换算结果**带**快照标识（`rateId` 或 `asOf` + `source`），
    能从结果反查到「用的是哪条汇率」
  - 5 → **错误**，`code` 明确（如 `FX_RATE_NOT_FOUND`），**不是** 0 或原值
  - **舍入**：**银行家舍入**（round half to even），**算法写死**（rev 2，裁定 #12）：
    ```
    numerator = a_minor as i128 * rate_micros as i128   // ← 必须 i128！
    quotient  = numerator / 1_000_000
    remainder = numerator % 1_000_000
    remainder*2 >  1_000_000 → quotient + 1
    remainder*2 == 1_000_000 → 偶数化（quotient 为奇数才 +1）
    最终 try_into::<i64>() → 溢出则 MONEY_OVERFLOW
    ```
    > ⚠️ **中间量必须是 `i128`**：两个 `i64` 相乘可达 ~8.5×10^37，
    > **`i64` 会溢出**（上限 9.2×10^18）。rev 1 没写宽度，Dev 会踩。
  - **溢出用例**：`a = i64::MAX` 附近换算 → **不 panic**，返回 `MONEY_OVERFLOW`
- **类型**: 功能

### AC-S-098: 币种与金额按 locale 格式化

  2. 用 `en-US` 格式化

- **类型**: 功能
