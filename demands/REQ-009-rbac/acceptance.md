## 本需求自有 AC

### AC-S-033: 权限点注册表双向对账且不一致即启动失败
- **前置条件**: 一个模块的 `manifest.json` 声明了权限点；平台库里有 `platform_permission` 表
- **测试步骤**:
  1. 只在 manifest 里加一个权限点（不改库）→ 启动服务
  2. 只在库里加一个权限点（不改 manifest）→ 启动服务
  3. 两边一致 → 启动服务
- **预期结果**:
  1. 启动**失败**（进程退出码非 0），错误信息**逐条列出**缺失的权限点编码，
     且每条都带**来源 manifest 的文件路径**（形如 `modules/foo/manifest.json`）
  2. 启动**失败**，逐条列出多余的权限点编码
  3. 启动成功
  - 差异**不是**告警、不是日志里一行带过 —— 不一致必须让进程起不来
- **类型**: 功能 / 安全

### AC-S-034: 角色、授权与绑定可用且带租户维度
- **前置条件**: 两个租户各有用户与组织数据；用户 M 是**普通用户**（只有 `platform-user` 内置角色），
  用户 A 持有 `rbac:role:write` 管理权限点
- **测试步骤**:
  1. 建角色、给角色授权、把用户绑到角色（**以用户 A 身份**）
  2. 用租户 A 的上下文读租户 A 的角色
  3. 用租户 A 的上下文操作租户 B 的角色 id
  4. 用**应用连接角色 `base_app`**（非超管）查角色表
  5. **以用户 M 身份**调 `/api/rbac/*` 的写接口（建角色 / 授权 / 绑定）
- **预期结果**:
  - 角色 / 授权 / 绑定三件事都能通过 `/api/rbac/*` 完成（不要求管理界面）
  - 只能读到本租户的角色；跨租户 id 操作返回 **404**（不泄露存在性）
  - 角色、授权、绑定三张表都有 `tenant_id`
  - **RLS 兜底可验**：用 `base_app` 连接执行 `SELECT count(*) FROM platform_role`，
    在租户 A 的上下文下**只能看到租户 A 的行**；且 `pg_policies` 里能查到这三张表的 policy
    （表名逐张列出，不允许「有 policy 就行」）
  - **★ 管理接口自身受保护**（自举防护）：第 5 步 **403 `INSUFFICIENT_PERMISSION`** ——
    `/api/rbac/*` 的写接口**必须**要求管理权限点（如 `rbac:role:write`），
    **普通用户不得调用**。否则任何登录用户都能给自己授权 `platform-admin` → 权限系统被架空。
    这条同样适用于**读接口**（读角色列表也应要求管理权限点）
- **类型**: 功能 / 安全

### AC-S-035: 角色继承展开且成环被拒
- **前置条件**: 角色 A → 继承 → B → 继承 → C，三者权限点各不相同
- **测试步骤**:
  1. 查 A 展开后的权限点集合
  2. 试图让 A 继承 A 的后代（构成环）
- **预期结果**:
  1. A 的权限集合 = A ∪ B ∪ C 的并集（**逐个列出**权限点编码，不只是数量相等）
  2. 成环的写入被**拒绝**，错误信息**指出是哪两个角色构成的环**（不是泛泛的「非法继承」）
- **类型**: 功能

### AC-S-036: 权限点通配语义正确且禁止全通过
- **前置条件**: 注册表里已登记 `sandbox:demo:read` / `sandbox:demo:write` / `org:org-node:read` /
  `org:org-node:write` 等权限点（**用注册表里真实存在的模块前缀**，不要假设 `iam:` 存在）
- **测试步骤**:
  1. 角色授予 `sandbox:*` → 查展开后的权限点
  2. 角色授予 `sandbox:demo:*` → 查展开后的权限点
  3. 尝试授予 `*:*`、或跨模块通配如 `*:demo:read`
- **预期结果**:
  1. `sandbox:*` 匹配 `sandbox:` 下**全部**权限点，且**不匹配** `org:` 下的
     （对照：给 `org:` 的权限点必须不在 `sandbox:*` 的展开结果里）
  2. `sandbox:demo:*` 只匹配 `sandbox:demo:` 下的
  3. `*:*` 与跨模块通配**写入被拒**（不得出现「一个角色拿到全平台权限」的路径）
- **类型**: 功能 / 安全

### AC-S-037: 内置角色不可删除也不可降权
- **前置条件**: 内置角色 `platform-admin`（`data_scope = ALL`）与 `platform-user`（`data_scope = SELF`）
- **测试步骤**:
  1. 删除 `platform-admin` 2. 改 `platform-admin` 的 `data_scope` 为 `SELF`
  3. 移除 `platform-admin` 的某个权限点 4. 查 `platform-admin` 的实际权限集合
- **预期结果**:
  - 1~3 **全部被拒**（错误码明确区分「内置角色受保护」）
  - `platform-admin` 的权限集合 = **注册表里当前全部权限点**，
    **逐个比对**（不是抽样、不是只比数量）——
    注册表新增一个权限点后，`platform-admin` 的集合**自动多出**该权限点（不靠人工补授权）
- **类型**: 安全

### AC-S-038: 数据范围五种语义求值正确
- **前置条件**: 真实库里的夹具能同时区分五种 scope：
  - 夹具表 `sandbox_scope_item`（**含** `org_node_id` 与 `created_by` 两列）
  - 用户 U 的主部门是 `dept-a`（`is_primary = true`），`dept-a` 下有子节点 `dept-a-1`
  - 至少 5 条记录，分别落在：主部门、本部门子节点、他部门、本人创建、非本人且非本部门
- **测试步骤**: 对同一张表分别以 `ALL` / `OWN_ORG` / `OWN_ORG_AND_BELOW` / `SELF` / `CUSTOM` 五种 scope 查询
- **预期结果**: **每种 scope 的期望结果集必须逐条列出记录 id**（不是只断言「互不相同」）

  | scope | 期望结果集 |
  |---|---|
  | `ALL` | 夹具里的全部记录 id |
  | `OWN_ORG` | 主部门 `dept-a` 的记录 id（**不含**子节点 `dept-a-1` 的） |
  | `OWN_ORG_AND_BELOW` | 主部门 `dept-a` **∪** 子节点 `dept-a-1` 的记录 id |
  | `SELF` | `created_by = U` 的记录 id |
  | `CUSTOM` | 条件命中的记录 id |

  - 五种结果集**两两不相等**（夹具必须做到，否则用例无效）
  - `OWN_ORG_AND_BELOW` 必须**跨层**（含子节点），不能只取一层
- **类型**: 功能

### AC-S-039: 兼岗默认按主部门，取并集必须显式开启
- **前置条件**: 用户 U 同时属于 `dept-a`（`is_primary = true`）与 `dept-b`（`is_primary = false`），
  两个部门**各自都有记录**，且 `dept-b` 下还有子节点 `dept-b-1`
- **测试步骤**:
  1. 默认配置下查 `OWN_ORG` 2. 默认配置下查 `OWN_ORG_AND_BELOW`
  3. 在**该角色**上开启 `use_all_memberships = true` 后重复 1、2
- **预期结果**:
  - 1、2（默认）：结果集**只含 `dept-a` 的记录**，**不含 `dept-b` / `dept-b-1` 的任何一条**
  - 3（显式开启）：结果集 = `dept-a` ∪ `dept-b` ∪ `dept-b-1` 的记录
  - 默认行为不得随租户 / 角色 / 缓存状态变化
- **类型**: 功能 / 安全

### AC-S-040: 主部门缺失或歧义时 fail closed 到 SELF
- **前置条件**: 用户 V **没有任何** `is_primary = true` 的成员行
- **测试步骤**:
  1. 给 V 再插一条 `is_primary = true` 的成员行（**数据库约束应当拒绝**）
  2. 以 V 的身份查 `OWN_ORG` 与 `OWN_ORG_AND_BELOW`
  3. **绕过数据库约束**（测试里临时移除部分唯一索引）造出两个主部门，
     以该用户身份再查 `OWN_ORG` 与 `OWN_ORG_AND_BELOW`
- **预期结果**:
  - 1：**被数据库拒绝**（插入报错，约束生效）
  - 2：结果集 = **只有 V 本人创建的记录**（退化为 `SELF`），
    **不得**看到本部门 / 全租户数据（退化成 `ALL` 或任何更宽的结果即判失败）
  - 3：**同样退化为 `SELF`** —— 歧义状态即使能绕过 DB 造出来，判定层也必须 fail closed
    （这一步验证的是**防御层**，第 1 步验证的是**预防层**）
- **类型**: 安全

### AC-S-041: 数据范围优先级与多角色组合
- **前置条件**: 用户 X 同时绑定三个角色 ——
  - R1：`data_scope = OWN_ORG`，含普通读权限点
  - R2：`data_scope = OWN_ORG`，但该角色下的 `export` 权限点单独收紧为 `SELF`
  - R3：`data_scope = OWN_ORG_AND_BELOW`，含同一个普通读权限点
- **测试步骤**:
  1. 查 X 对「普通读权限点」的数据范围
  2. 查 X 对「export 权限点」的数据范围
  3. **解绑 R3**（只剩 R1 + R2），再查「普通读权限点」的数据范围
- **预期结果**:
  - 1：结果取**最宽松**的（R3 的 `OWN_ORG_AND_BELOW`）—— 多角色 scope 是并集语义
  - 2：**权限点级覆盖角色级** → `SELF`
  - 3：结果退为 R1 的 `OWN_ORG`（**与第 1 步结果不同** —— 这一步是为了区分「并集」与「交集」：
    若 1 与 3 结果相同，说明实现取的是交集而非并集）
  - 角色级 > 用户默认（`SELF`）的优先级同样成立
- **类型**: 功能

### AC-S-042: 受限表达式 DSL 拒绝越界写法且不产生拼接 SQL
- **前置条件**: 白名单字段集已确定（如 `$record.amount`、`$record.dept_id`）
- **测试步骤**: 解析并求值下列表达式
  1. `$record.amount <= 10000`（合法）
  2. `$record.secret == "x"`（字段不在白名单）
  3. `now() < $record.created_at`（函数调用）
  4. `$record.name == "a' OR '1'='1"`（字符串里含 SQL 片段）
  5. `$record.amount <= 10000; DROP TABLE t`（多语句）
- **预期结果**:
  - 1：解析成功，生成的 SQL 条件**走参数绑定** —— 语句文本里**只有占位符**，
    看不到字面量值 `10000`
  - 2、3、5：**解析失败**并给出明确原因（不在白名单 / 不允许函数调用 / 不允许多语句）
  - 4：**三条判据同时成立**：
    1. 生成的 SQL 文本里**不出现**该字符串（只有占位符）
    2. 查询结果**不出现**「全表命中」的效果（即没有多余的行被返回）
    3. 只返回**字面量值恰好等于**该字符串的行（若有）
    —— 即注入串被当作**普通字符串值**处理，既不改变查询语义，也不出现在 SQL 文本里
- **类型**: 安全

### AC-S-043: 属性级校验（RBAC + ABAC 混合）生效
- **前置条件**: 权限点 `demo:invoice:approve` 携带条件 `$record.amount <= 10000`
- **测试步骤**: 1. 用户有此权限点，对金额 5000 的记录调用 2. 用户有此权限点，对金额 20000 的记录调用
  3. 用户**没有**此权限点，对金额 5000 的记录调用
  4. 权限点的条件引用**白名单外**的属性
- **预期结果**:
  - 1：放行 2：**被拒**（条件不满足，错误码与 HTTP 状态按契约 C5 判定） 3：**被拒**（缺权限点）
  - 4：判定为**不通过**（fail closed），**不是**「忽略条件放行」
- **类型**: 安全

### AC-S-044: 鉴权中间件的三种拒绝语义与错误体形状
- **前置条件**: 一个需要权限点 `sandbox:demo:read` 的路由；夹具里有 3 条记录
- **测试步骤**: 1. 不带令牌调用 2. 带**有效**令牌但用户无该权限点调用
  3. 带有效令牌、**有**该权限点，但目标记录不在其数据范围内调用
- **预期结果**:
  - 1 → **401** + `code = UNAUTHENTICATED`
  - 2 → **403** + `code = INSUFFICIENT_PERMISSION`
  - 3 → **404** + `code = NOT_FOUND`
  - 三者的响应体都符合 RFC 9457：**必带 `trace_id`**；`detail` 是**英文 ASCII**
    （不得出现中文句子）；`instance` 是请求路径
  - `detail` **可以**包含被拒的**权限点编码**（`sandbox:demo:read`）—— 那是开发者信息；
    但**不得**出现被拒**资源**的任何业务细节（标题、金额、归属人、`org_node_id` 等）
- **类型**: 安全

### AC-S-045: 404 不泄露资源存在性（资源类越权）
- **前置条件**: 用户 P **拥有**权限点 `sandbox:scope-item:read`，
  但记录 `item-a1` 落在其数据范围**之外**；`item-not-exist-9999` 是**不存在**的 id；
  记录 `item-a2` 落在 P 的数据范围**之内**
- **测试步骤**:
  1. **绕过前端**直接调接口访问 `item-a1`（不经过任何 UI 显隐逻辑）
  2. 直接调接口访问 `item-not-exist-9999`
  3. 对比 1、2 两次响应的**状态码、错误体结构、响应头集合**
  4. 直接调接口访问 `item-a2`（对照组）
- **预期结果**:
  - 1、2：状态码**相同**（都是 404）、**错误体结构相同**、**响应头集合相同**
    —— 除 `trace_id` / `instance` 外**无可区分差异**
  - 4：返回 **200** 且返回该记录（证明接口本身可用、不是恒 404）
  - 「无权访问的资源」与「不存在的资源」**必须无法区分** ——
    这正是资源类越权用 404 而不是 403 的理由
  - **注意**：动作类越权（缺权限点 → 403）是契约 C5 明确规定的行为，
    **不算**存在性泄露，不在此条的判定范围内
- **类型**: 安全

### AC-S-046: 已登记权限点必须有鉴权调用点，且鉴权入口唯一
- **前置条件**: 契约检查 C-5 已落地（`extension-points v2`）
- **测试步骤**:
  1. 在某模块 manifest 里登记一个**代码中不存在**的权限点 → 跑该模块的契约测试
  2. 在模块代码里写一个**自定义鉴权函数**（绕过平台入口）调用已登记权限点 → 跑契约测试
  3. 让某模块用**非字面量**参数调用鉴权入口 → 跑契约测试
  4. 正常模块（既登记又有调用点）→ 跑契约测试
  5. 全仓搜索鉴权入口的**定义处**（不是调用处）
- **预期结果**:
  - 1：**失败**，并指出「权限点 X 已登记但无鉴权调用点」
  - 2：**失败**（绕过平台入口 = 扫描不到）
  - 3：**失败**（无法静态确认 → fail closed，不放行）
  - 4：通过
  - 5：鉴权入口在整个仓库**只有一个定义处**；出现第二个 → 检查失败
- **类型**: 安全 / 可维护性

### AC-S-047: 权限撤销在下一个请求即生效，不等 TTL
- **前置条件**: 用户 Q 拥有权限点 `sandbox:demo:read`；平台有权限缓存；
  **两个独立的 checker 实例**（各自持自己的缓存，共享同一个数据库）用来模拟两个进程
- **测试步骤**:
  1. 用实例 1 调接口确认 Q 当前**可以**执行该操作
  2. 用实例 1 撤销 Q 的角色授权（或改角色权限 / 改角色数据范围 / 改组织成员关系）
  3. **立刻**用**实例 2**（缓存里还是旧值）调同一接口
  4. 再用实例 1 调同一接口
- **预期结果**:
  - 3、4：**被拒**（403 或 404，按 C5 口径）—— 不允许出现「撤销后 60 秒内仍可用」
  - 第 3 步验证**跨进程**：实例 2 的缓存**不是**失效原因，
    失效信号必须来自共享的数据库（epoch），否则多实例部署下撤销不生效
  - 撤销**数据范围**（而非权限点本身）同样立即生效
- **类型**: 安全

### AC-S-048: 数据范围过滤在 SQL 层生效且业务模块无法绕过
- **前置条件**: 业务模块用平台的查询构造器执行列表查询
- **测试步骤**:
  1. 业务模块**故意不写**任何数据范围条件，用平台构造器查列表
  2. 检查平台构造器**渲染出的 SQL 文本**里是否含平台追加的范围条件
  3. 业务模块尝试提供「跳过数据范围」的开关 / 参数
- **预期结果**:
  - 1：结果**已被过滤**（用户无权看到的记录查不到），
    且**不是**查出来后在内存里筛（判据见第 2 步）
  - 2：渲染出的 SQL **含平台追加的范围条件片段**，
    且该片段里的值**走参数绑定**（SQL 文本里不出现拼进去的字面值）
  - 3：**不存在这样的开关** —— 平台不提供、业务模块也构造不出来
    （判据：平台的构造器 API 上没有「跳过范围」的方法/参数；
    业务模块若绕过构造器直接写 SQL，则由 `check-deps` / 约定挡住并在评审中判失败）
- **类型**: 安全
