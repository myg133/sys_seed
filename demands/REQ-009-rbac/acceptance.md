## 本需求自有 AC

### AC-S-033: 权限点注册表双向对账且不一致即启动失败
- **前置条件**: 一个模块的 `manifest.json` 声明了权限点；平台库里有 `platform_permission` 表
- **测试步骤**:
  1. 只在 manifest 里加一个权限点（不改库）→ 启动服务
  2. 只在库里加一个权限点（不改 manifest）→ 启动服务
  3. 两边一致 → 启动服务
- **预期结果**:
  1. 启动**失败**（进程退出码非 0），错误信息**逐条列出**缺失的权限点编码与来源 manifest 路径
  2. 启动**失败**，逐条列出多余的权限点编码
  3. 启动成功
  - 差异**不是**告警、不是日志里一行带过 —— 不一致必须让进程起不来
- **类型**: 功能 / 安全

### AC-S-034: 角色、授权与绑定可用且带租户维度
- **前置条件**: 两个租户各有用户与组织数据
- **测试步骤**:
  1. 建角色、给角色授权、把用户绑到角色
  2. 用租户 A 的上下文读租户 A 的角色
  3. 用租户 A 的上下文操作租户 B 的角色 id
- **预期结果**:
  - 角色 / 授权 / 绑定三件事都能通过 `/api/rbac/*` 完成（不要求管理界面）
  - 只能读到本租户的角色；跨租户 id 操作返回 **404**（不泄露存在性）
  - 角色、授权、绑定三张表都有 `tenant_id` 并生成 RLS policy
- **类型**: 功能 / 安全

### AC-S-035: 角色继承展开且成环被拒
- **前置条件**: 角色 A → 继承 → B → 继承 → C，三者权限点各不相同
- **测试步骤**:
  1. 查 A 展开后的权限点集合
  2. 试图让 A 继承 A 的后代（构成环）
- **预期结果**:
  1. A 的权限集合 = A ∪ B ∪ C 的并集
  2. 成环的写入被**拒绝**，错误信息**指出是哪两个角色构成的环**（不是泛泛的「非法继承」）
- **类型**: 功能

### AC-S-036: 权限点通配语义正确且禁止全通过
- **前置条件**: 已登记 `order:invoice:read` / `order:invoice:write` / `order:order:read` 等权限点
- **测试步骤**:
  1. 角色授予 `order:*` → 查展开后的权限点
  2. 角色授予 `order:invoice:*` → 查展开后的权限点
  3. 尝试授予 `*:*`（或跨模块通配如 `*:invoice:read`）
- **预期结果**:
  1. `order:*` 匹配 `order:` 下**全部**权限点，不匹配 `iam:` / `org:` 的
  2. `order:invoice:*` 只匹配 `order:invoice:` 下的
  3. `*:*` 与跨模块通配**写入被拒**（不得出现「一个角色拿到全平台权限」的路径）
- **类型**: 功能 / 安全

### AC-S-037: 内置角色不可删除也不可降权
- **前置条件**: 内置角色 `platform-admin`（`data_scope = ALL`）与 `platform-user`（`data_scope = SELF`）
- **测试步骤**:
  1. 删除 `platform-admin` 2. 改 `platform-admin` 的 `data_scope` 为 `SELF`
  3. 移除 `platform-admin` 的某个权限点 4. 查 `platform-admin` 的实际权限集合
- **预期结果**:
  - 1~3 **全部被拒**（错误码明确区分「内置角色受保护」）
  - `platform-admin` 的权限集合 = 平台登记的**全部**权限点（逐个比对，不是抽样）
- **类型**: 安全

### AC-S-038: 数据范围五种语义求值正确
- **前置条件**: 真实库里两个部门（dept-a 有数据、dept-b 有数据），另有本部门外的数据
- **测试步骤**: 对同一张表分别以 `ALL` / `OWN_ORG` / `OWN_ORG_AND_BELOW` / `SELF` / `CUSTOM` 五种 scope 查询
- **预期结果**:
  - `ALL` 返回全部（不加任何过滤）
  - `OWN_ORG` 只返回主部门的数据
  - `OWN_ORG_AND_BELOW` 返回主部门**及其子节点**的数据（递归 CTE，不是单层）
  - `SELF` 只返回本人创建的数据
  - `CUSTOM` 返回条件命中的数据
  - 五种结果**互不相同**（若某两种在夹具下结果相同，视为夹具无效，测试必须换夹具）
- **类型**: 功能

### AC-S-039: 兼岗默认按主部门，取并集必须显式开启
- **前置条件**: 用户 U 同时属于 dept-a（`is_primary = true`）与 dept-b（`is_primary = false`），
  两个部门**各自都有数据**，且 dept-b 下还有子节点
- **测试步骤**:
  1. 默认配置下查 `OWN_ORG` 2. 默认配置下查 `OWN_ORG_AND_BELOW`
  3. 开启 `use_all_memberships = true` 后重复 1、2
- **预期结果**:
  - 1、2（默认）：**只含 dept-a 的数据**，**不含 dept-b 的任何数据**
  - 3（显式开启）：含 dept-a **∪** dept-b 及其子树的数据
  - 默认行为不得随租户 / 角色 / 缓存状态变化
- **类型**: 功能 / 安全

### AC-S-040: 主部门缺失或歧义时 fail closed 到 SELF
- **前置条件**: 用户 V **没有任何** `is_primary = true` 的成员行；用户 W **有两条** `is_primary = true` 的行
- **测试步骤**: 分别以 V、W 的身份查 `OWN_ORG` 与 `OWN_ORG_AND_BELOW`
- **预期结果**:
  - 两人都**只看到自己创建的数据**（退化为 `SELF`）
  - **都不得看到本部门 / 全租户数据**（退化成 `ALL` 或「看到空」以外的更宽结果即判失败）
  - V 与 W 的 `is_primary` 歧义状态在库里被**部分唯一索引**挡住（新增第二个主部门行 → 数据库拒绝）
- **类型**: 安全

### AC-S-041: 数据范围优先级与多角色组合
- **前置条件**: 用户 X 同时有两个角色 —— R1（角色级 scope = `OWN_ORG`）、
  R2（该角色下 `export` 权限点单独收紧为 `SELF`）；另有角色 R3（scope = `OWN_ORG_AND_BELOW`）
- **测试步骤**:
  1. 查 X 对「普通读权限点」的数据范围
  2. 查 X 对「export 权限点」的数据范围
  3. 去掉 R1、只留 R3，重复 1
- **预期结果**:
  - 1：结果取**最宽松**的（R3 的 `OWN_ORG_AND_BELOW`）—— 多角色 scope 是并集语义
  - 2：**权限点级覆盖角色级** → `SELF`
  - 3：结果为 `OWN_ORG_AND_BELOW`
  - 角色级 > 用户默认（`SELF`）的优先级同样成立
- **类型**: 功能

### AC-S-042: 受限表达式 DSL 拒绝越界写法且不产生拼接 SQL
- **前置条件**: 白名单字段集已确定（如 `$record.amount`、`$record.dept_id`）
- **测试步骤**: 解析并求值下列表达式
  1. `$record.amount <= 10000`（合法）
  2. `$record.secret == "x"`（字段不在白名单）
  3. `now() < $record.created_at`（函数调用）
  4. `$record.name == "a' OR '1'='1"`（字符串里含 SQL 片段）
  5. `$record.amount <= 10000; DROP TABLE t`（多语句）
- **预期结果**:
  - 1：解析成功，生成的 SQL 条件**走参数绑定**（语句里看不到字面量值）
  - 2、3、5：**解析失败**并给出明确原因（不在白名单 / 不允许函数调用 / 不允许多语句）
  - 4：解析成功但**注入串被当作普通字符串值绑定**，查询结果与注入前一致
    （注入串不得改变查询语义，也不得出现在 SQL 文本里）
- **类型**: 安全

### AC-S-043: 属性级校验（RBAC + ABAC 混合）生效
- **前置条件**: 权限点 `demo:invoice:approve` 携带条件 `$record.amount <= 10000`
- **测试步骤**: 1. 用户有此权限点，对金额 5000 的记录调用 2. 用户有此权限点，对金额 20000 的记录调用
  3. 用户**没有**此权限点，对金额 5000 的记录调用
- **预期结果**:
  - 1：放行 2：**被拒**（条件不满足，错误码与 HTTP 状态按契约 C5 判定） 3：**被拒**（缺权限点）
  - 条件里的属性**必须在白名单**；引用白名单外的属性 → 判定为**不通过**（fail closed），不是「忽略条件放行」
- **类型**: 安全

### AC-S-044: 鉴权中间件的三种拒绝语义与错误体形状
- **前置条件**: 一个需要权限点 `demo:invoice:approve` 的路由
- **测试步骤**: 1. 不带令牌调用 2. 带**有效**令牌但用户无该权限点调用
  3. 带有效令牌、有权限点，但目标记录不在其数据范围内调用
- **预期结果**:
  - 1 → **401** + `code = UNAUTHENTICATED`
  - 2 → **403** + `code = INSUFFICIENT_PERMISSION`
  - 3 → **404** + `code = NOT_FOUND`
  - 三者的响应体都符合 RFC 9457：**必带 `trace_id`**；`detail` 是**英文 ASCII**
    （不得出现中文句子）；`instance` 是请求路径
  - `detail` 里**不得**出现被拒资源的任何细节（标题、金额、归属人等）
- **类型**: 安全

### AC-S-045: 越权拦截不依赖前端，且 404 不泄露资源存在性
- **前置条件**: 用户 P 无权访问记录 R1，**有权**访问记录 R2（R1、R2 同租户、同类型）
- **测试步骤**:
  1. **绕过前端**直接调接口访问 R1（不经过任何 UI 显隐逻辑）
  2. 直接调接口访问 R2 3. 对比两次响应的状态码、错误体结构与响应头
- **预期结果**:
  - 1：**被拒**（前端显隐不参与判定）
  - 3：两次响应的**状态码相同**（都是 404）、**错误体结构相同**、**响应头集合相同**
    —— 除 `trace_id` / `instance` 外**无可区分差异**；不得出现「无权时返回 403、有权时返回 200」
    这类把存在性泄露出去的差异
- **类型**: 安全

### AC-S-046: 已登记权限点必须有鉴权调用点，且鉴权入口唯一
- **前置条件**: 契约检查 C-5 已落地（`extension-points v2`）
- **测试步骤**:
  1. 在某模块 manifest 里登记一个**代码中不存在**的权限点 → 跑该模块的契约测试
  2. 在模块代码里写一个**自定义鉴权函数**（绕过平台入口）调用已登记权限点 → 跑契约测试
  3. 让某模块用**非字面量**参数调用鉴权入口 → 跑契约测试
  4. 正常模块（既登记又有调用点）→ 跑契约测试
- **预期结果**:
  - 1：**失败**，并指出「权限点 X 已登记但无鉴权调用点」
  - 2：**失败**（绕过平台入口 = 扫描不到）
  - 3：**失败**（无法静态确认 → fail closed，不放行）
  - 4：通过
  - **鉴权入口在整个仓库只有一个**；出现第二个入口 → 检查失败
- **类型**: 安全 / 可维护性

### AC-S-047: 权限撤销在下一个请求即生效，不等 TTL
- **前置条件**: 用户 Q 拥有权限点 `demo:invoice:approve`；平台有权限缓存
- **测试步骤**:
  1. 调接口确认 Q 当前**可以**执行该操作
  2. 撤销 Q 的角色授权（或改角色权限 / 改角色数据范围 / 改组织成员关系）
  3. **立刻**再调同一接口（不等待、不重启）
- **预期结果**:
  - 3：**被拒**（403 或 404，按 C5 口径）—— 不允许出现「撤销后 60 秒内仍可用」
  - 撤销**数据范围**（而非权限点本身）同样立即生效
  - 该结论**跨进程**成立（不能只在本进程内生效）
- **类型**: 安全

### AC-S-048: 数据范围过滤在 SQL 层生效且业务模块无法绕过
- **前置条件**: 业务模块用平台的查询构造器执行列表查询
- **测试步骤**:
  1. 业务模块**故意不写**任何数据范围条件，用平台构造器查列表
  2. 业务模块尝试提供「跳过数据范围」的开关 / 参数
- **预期结果**:
  - 1：平台**自动叠加**数据范围条件（用户无权看到的记录在数据库层就被滤掉，
    不是查出来后在内存里筛）
  - 2：**不存在这样的开关** —— 平台不提供、业务模块也构造不出来
  - 数据范围条件与租户条件一起以**参数化**方式渲染（语句里不出现拼进去的字面值）
- **类型**: 安全

## 明确不做的（不在本期验收范围）

- **前端权限组件与 `can()` 实现** —— 属 REQ-011。
  本期只保证「权限点注册表是单一来源 + 有接口可读 + 后端新增权限点不需要改后端代码」，
  **前端拿到注册表后自己怎么用，不在本期验收**。
- 权限申请 / 审批流（属 REQ-017）
- 审计落库（属 REQ-014）—— 本期只保证权限变更**触发了**可审计的事件，不负责落库
- 跨租户授权（平台管理员代客操作）
- 字段级权限的可视化配置界面
- Redis 部署形态下的缓存一致性（本期缓存是**进程内 + DB epoch**，多实例靠 epoch 收敛）
