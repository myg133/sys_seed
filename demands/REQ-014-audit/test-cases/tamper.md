# 篡改检测、沿链连锁与告警（AC-S-022、AC-S-125）

- **覆盖 AC**: AC-S-022（4 条：TC-014-029 ~ 032）、AC-S-125（10 条：TC-014-033 ~ 042）
- **前置基线**:
  - 测试库 `base_test`；租户 `t-audit`（T-A）
  - T-A 下已有 **3 条**链正确的审计记录（通过平台 sink 写入）
  - 篡改一律**绕过应用**，用管理员连接（`base`）直接 `UPDATE` 列值
  - 链校验能力：`GET /api/audit/verify`（需 `audit:verify:run` 权限）或等价的校验函数
- **实现事实（用例按此写）**:
  - design §5.2 定义 `reason` 取值**恰好两个**：
    `hash_mismatch`（重算哈希与存储不符）、`prev_hash_mismatch`（本条的 `prev_hash` 与上一条的 `hash` 不接）
  - 重算哈希的输入是**该条记录自己的 `prev_hash` 列**（D131）——
    所以「改了上一条的 `hash`」**不会**改变下一条的重算结果，只会让下一条的**接续关系**断掉
  - 校验响应形状：`{ ok, checked, broken: [{ id, reason, expected, actual }] }`
  - AC-S-022 步骤 5 要求「error 级别日志 + 结构化字段 `tenant_id` / `event_id` / `reason`」
  - ⚠️ 本仓日志用 `tracing`（`tracing = "0.1"`，根 `Cargo.toml:42`）；
    结构化字段落在**日志事件**上，不是响应体里 —— 断言要对着日志捕获器做，
    不能对着 HTTP 响应做。〔S-12〕

## AC-S-022：哈希链可校验（定期校验链完整性，篡改任一条目即告警）

### TC-014-029: 未篡改时链校验返回 `ok = true`、`checked = 2`、`broken = []`

- **关联 AC**: AC-S-022
- **前置条件**: T-A 下有 **恰好 2 条**链正确的审计记录
- **测试步骤**:
  1. 调用链校验能力（`GET /api/audit/verify` + 具备 `audit:verify:run` 的令牌）
  2. 读响应体
- **预期结果**:
  1. HTTP 状态 `200`
  2. `ok == true`
  3. `checked == 2`（**恰好 2**，不是 `>= 2`）
  4. `broken` 是**空数组**（长度 `0`）
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 基本路径
- **备注**: `checked` 的口径必须钉死：**是本租户在线表里的记录数**。
  归档后的记录不在在线表里 → `checked` 会变少（见 TC-014-098）。

### TC-014-030: 篡改任一条 `after` → `ok = false`，`broken` **恰好 1 条**，且点名那条

- **关联 AC**: AC-S-022
- **前置条件**: 同 TC-014-029；记下两条记录的 `id`
- **测试步骤**:
  1. 用管理员连接执行 `UPDATE platform_audit_log SET after = '{"tampered":true}' WHERE id = <第 1 条 id>`
  2. 再次调用链校验
  3. 读响应体
- **预期结果**:
  1. `ok == false`
  2. `broken` 长度 `== 1`（**恰好 1**，不是 `>= 1`）
  3. `broken[0].id == <被篡改那条的 id>`
  4. `broken[0].reason == "hash_mismatch"`
  5. `broken[0].expected != broken[0].actual`（两者都有值，且不相等）
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 攻击路径
- **备注**: 「恰好 1 条」是 AC 的核心 —— 漏报（0 条）与误报（2 条）都要被这条抓住。

### TC-014-031: 篡改被检出时产生**至少一条 error 级别**日志

- **关联 AC**: AC-S-022
- **前置条件**: 同 TC-014-030；测试内挂一个 `tracing` 日志捕获器
- **测试步骤**:
  1. 清空已捕获日志
  2. 篡改一条记录
  3. 调用链校验
  4. 从捕获器里筛出 `Level::ERROR` 的事件
- **预期结果**:
  1. 步骤 4 的 `ERROR` 事件数 `>= 1`
  2. 其中**至少一条**提到被篡改那条的 `id`
  3. 日志**不包含**审计内容里的明文敏感值（若有 `before` / `after` 值，只应出现 `id` / 原因码）
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 基本路径 + 下界断言
- **备注**: AC 说「检查步骤 4 **期间**产生的日志」—— 所以断言要**只统计校验调用之后**的日志，
  否则写入时的其它 error 日志会混进来造成假绿。

### TC-014-032: 告警日志含结构化字段 `tenant_id` / `event_id` / `reason`

- **关联 AC**: AC-S-022
- **前置条件**: 同 TC-014-031
- **测试步骤**:
  1. 篡改一条记录并调用链校验
  2. 取那条 `ERROR` 日志的**结构化字段**（不是格式化后的文本）
- **预期结果**:
  1. 存在一条 `ERROR` 日志，其字段集合**包含** `tenant_id`、`event_id`、`reason`
  2. `tenant_id == "t-audit"`
  3. `event_id == <被篡改那条的 id>`
  4. `reason == "hash_mismatch"`
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 字段集合精确判定
- **备注**: AC 只写了字段名，**没写字段值**与**是否允许额外字段**。
  本用例按「至少包含这 3 个 + 值正确」写；
  **若 BA 要「恰好 3 个」**，须在 AC 里补一句「字段集合恰好为这 3 个」。〔S-12〕
  ⚠️ 字段名 `event_id` 与表列名 `id` 不一致 —— BA 需在「日志字段名」与「列名」之间
  明确二选一（我按 AC 原文的 `event_id` 写）。〔S-12〕

## AC-S-125：篡改可检测且沿链连锁

### TC-014-033: 案例 A（改第 2 条的 `after`）→ `broken` **恰好 1 条**

- **关联 AC**: AC-S-125
- **前置条件**: T-A 下已有 **3 条**链正确的审计记录（记为 `r1` / `r2` / `r3`）
- **测试步骤**:
  1. 记录当前链校验结果（应为 `ok=true`）
  2. 用管理员连接执行 `UPDATE platform_audit_log SET after = '{"tampered":true}' WHERE id = r2.id`
     （**不动** `hash`）
  3. 调用链校验
- **预期结果**:
  1. 步骤 1 的结果 `ok == true`、`broken` 长度 `0`
  2. 步骤 3 的结果 `ok == false`
  3. `broken` 长度 `== 1`（**恰好 1**）
  4. `broken[0].id == r2.id`
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 攻击路径
- **备注**: 案例 A **不**牵连第 3 条 —— 第 3 条的 `prev_hash` 指向 r2 **存储的** `hash`（未变）→ 接续关系完好。
  这正是案例 A 与案例 B 的**唯一**区别，两条必须成对存在。

### TC-014-034: 案例 A 的 `broken[0].reason == "hash_mismatch"`

- **关联 AC**: AC-S-125
- **前置条件**: 同 TC-014-033
- **测试步骤**:
  1. 复现案例 A
  2. 读 `broken[0].reason`
- **预期结果**:
  1. `reason == "hash_mismatch"`（逐字）
  2. `reason != "prev_hash_mismatch"`
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 等价类（枚举）
- **备注**: 与 TC-014-037 成对 —— 两个 reason 必须能被区分开，
  否则「reason 字段」就是装饰性的。

### TC-014-035: 案例 B（改第 2 条**存储的 `hash`**）→ `broken` **恰好 2 条**

- **关联 AC**: AC-S-125
- **前置条件**: 同 TC-014-033（案例 A 之后需**恢复原状**：把 `after` 改回、
  把 `hash` 改回原值；AC 步骤 2 明写「恢复原状后」）
- **测试步骤**:
  1. 恢复案例 A 的改动，复验 `ok == true`
  2. 执行 `UPDATE platform_audit_log SET hash = '<另一个 64 位十六进制>' WHERE id = r2.id`
     （其它列**一律不动**）
  3. 调用链校验
- **预期结果**:
  1. 步骤 1 的结果 `ok == true`（恢复干净，否则本用例不成立）
  2. 步骤 3 的结果 `ok == false`
  3. `broken` 长度 `== 2`（**恰好 2**）
  4. `broken` 的 `id` 集合 `==` `{r2.id, r3.id}`（**不含** `r1.id`）
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 攻击路径
- **备注**: 这条是 AC-S-125 的**核心论证** —— 「第 3 条被牵连 … 这证明链是连锁的，不是逐条独立的校验」。
  第 4 条断言 `r1` **不**在 broken 里 —— 若实现把「链首之后的全部记录」都标成 broken，
  就会多一条，那是误报。

### TC-014-036: 案例 B 中第 2 条的 `reason == "hash_mismatch"`

- **关联 AC**: AC-S-125
- **前置条件**: 同 TC-014-035
- **测试步骤**:
  1. 复现案例 B
  2. 取 `broken` 里 `id == r2.id` 的那条，读 `reason`
- **预期结果**:
  1. `reason == "hash_mismatch"`（逐字）
  2. `expected != actual`
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 等价类（枚举）
- **备注**: r2 的 `hash` 列被直接改过 → 它**自身**的重算哈希与存储值不符 → `hash_mismatch`。无歧义。

### TC-014-037: 案例 B 中第 3 条的 `reason == "prev_hash_mismatch"`〔AC 修正〕

- **关联 AC**: AC-S-125
- **前置条件**: 同 TC-014-035
- **测试步骤**:
  1. 复现案例 B
  2. 取 `broken` 里 `id == r3.id` 的那条，读 `reason`
- **预期结果**:
  1. `reason == "prev_hash_mismatch"`（逐字）
  2. `expected` 等于 r2 **当前存储**的 `hash`，`actual` 等于 r3 **自身**的 `prev_hash`（两者不相等）
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 等价类（枚举）+ 判定表
- **备注**: ⚠️ **AC 原文写的是「第 3 条 `reason` == `hash_mismatch`」，与 design §5.2 的两值定义冲突。**
  推导：第 3 条的 `prev_hash` 列**没被改** → 按 D131 用**它自己的 `prev_hash`** 重算 →
  重算值 **等于**它存储的 `hash` → **不构成** `hash_mismatch`；
  真正断掉的是「`prev_hash` 与上一条存储的 `hash` 接不上」→ `prev_hash_mismatch`。
  **两种可能的实现口径必须由 BA 二选一**（见挑刺报告 〔S-01〕）：
  (a) 逐条重算 + 接续校验（本用例按此写，`reason` 有两个取值，design §5.2 已定义）；
  (b) 链式重算（用上一条的**重算值**当下一条的前提）→ 则第 3 条才是 `hash_mismatch`，
  但此时 design §5.2 的 `prev_hash_mismatch` **永远不可能出现**，该 reason 变成死值。
  **BA 不拍板，本用例无法判定红绿。**

### TC-014-038: 案例 B 中第 3 条**自身**的重算哈希仍等于存储值（它没被直接篡改）

- **关联 AC**: AC-S-125
- **前置条件**: 同 TC-014-035；测试侧有独立哈希实现
- **测试步骤**:
  1. 复现案例 B
  2. 取 r3 的**全部字段**（含它自己的 `prev_hash` 列与存储的 `hash` 列）
  3. 用 r3 自己的 `prev_hash` 参与重算
- **预期结果**:
  1. 重算值 `==` r3 存储的 `hash`（**说明 r3 本体没被改**）
  2. r3 的 `prev_hash != ` r2 **当前存储**的 `hash`（**接续关系已断**）
  3. 两条同时成立 → r3 被 broken 的唯一理由是**接续**，不是**自身哈希**
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 基本路径（把「原因」拆成两个独立判据）
- **备注**: 本用例是 TC-014-037 的**依据**，也是 AC-S-125 那句「这证明链是连锁的」的机械表达：
  连锁性由「接续关系断裂」体现，**不是**由「第 3 条自身哈希变了」体现。
  把这两件事分开，才能同时判出「检出」与「检出原因正确」。

### TC-014-040: 篡改 `actor_id` / `action` / `object_type` / `object_id` 均被检出

- **关联 AC**: AC-S-125
- **前置条件**: T-A 下 3 条链正确记录
- **测试步骤**:
  1. 依次把 `r2` 的 `actor_id` / `action` / `object_type` / `object_id` 各改成一个不同的值
     （**每次改完都恢复原状**，且只改一个字段）
  2. 每次改动后调用链校验
- **预期结果**:
  1. 4 次改动**每次**都 `ok == false`
  2. 4 次的 `broken` 长度都 `== 1`，且 `broken[0].id == r2.id`
  3. 4 次的 `reason` 都是 `hash_mismatch`
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 攻击路径（等价类）
- **备注**: D131 的 10 个字段**逐个**都是哈希输入。少哈希任何一个字段 = 少一类篡改能被检出。
  本用例把「逐字段参与哈希」变成可机械判定的清单。

### TC-014-041: 篡改 `prev_hash` **列**被检出

- **关联 AC**: AC-S-125
- **前置条件**: T-A 下 3 条链正确记录
- **测试步骤**:
  1. `UPDATE platform_audit_log SET prev_hash = '<另一个 64 位十六进制>' WHERE id = r2.id`
  2. 调用链校验
- **预期结果**:
  1. `ok == false`
  2. `broken` 长度 `>= 1`，且含 `id == r2.id`
  3. r2 的 `reason` **至少有一个**属于 `{hash_mismatch, prev_hash_mismatch}`
     （**具体是哪一个由实现口径决定，AC 未规定** → 本用例只断言集合成员）
- **类型**: 安全
- **优先级**: P1
- **自动化**: 可自动化
- **设计方法**: 攻击路径
- **备注**: 改 `prev_hash` 列同时破坏了两件事（自身重算 + 与上一条的接续），
  哪一条先被检出取决于校验顺序 → **AC 没写**，这里只锁「必须被检出」。
  若 BA 要钉死，应指定校验顺序（先接续、后重算，或反之）。

### TC-014-042: 篡改 `created_at` 被检出

- **关联 AC**: AC-S-125
- **前置条件**: T-A 下 3 条链正确记录
- **测试步骤**:
  1. `UPDATE platform_audit_log SET created_at = created_at + INTERVAL '1 day' WHERE id = r2.id`
  2. 调用链校验
- **预期结果**:
  1. `ok == false`
  2. `broken` 长度 `>= 1`，且含 `id == r2.id`
  3. `broken[0].reason ∈ {hash_mismatch, prev_hash_mismatch}`
- **类型**: 安全
- **优先级**: P1
- **自动化**: 可自动化
- **设计方法**: 攻击路径
- **备注**: 改 `created_at` 还会**改变排序位置**（校验按 `created_at ASC` 排）→ r2 可能被排到第 1 位，
  此时「接续」关系整体错位 → `broken` 可能多于 1 条。故本用例只断言「`>= 1` 且含 r2」，
  **不断言恰好 1 条** —— 断「恰好 1 条」需要先钉死排序 tiebreaker 口径。〔S-11〕
