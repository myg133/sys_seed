# 权限变更审计（AC-S-128）

- **覆盖 AC**: AC-S-128（8 条：TC-014-061 ~ 068）
- **前置基线**:
  - 测试库 `base_test`；租户 `t-audit`（T-A）
  - 角色 `r-1` 已存在；权限 `p-1` 尚未授予 `r-1`
  - 操作者 `u-op` 具备角色管理权限
- **实现事实（用例按此写）**:
  - 埋点位置（design §6.1）：`crates/platform-rbac/src/service.rs:391`（`grant_permission`）、
    `:451`（`revoke_permission`）、`:245`（`create_role`）、`:299`（`delete_role`）
  - 事件码（design §6.1）：`rbac.role.grant` / `rbac.role.revoke` / `rbac.role.create` / `rbac.role.delete`
  - ⚠️ AC-S-128 原文只说「`action` 为**授予动作**」—— **没给具体事件码**。
    本用例按 design §6.1 的码写；若 BA 换码，需同步改本文件。〔S-15〕
  - `before` / `after` 的**内容结构**（装权限码列表还是装角色对象）规格**未定义** →
    本用例按「能解析出 `p-1` 的**在 / 不在**」写，不锁具体 JSON 形状。〔S-30〕

### TC-014-061: 授予权限 `p-1` 给 `r-1` → **恰好 1 条**审计记录

- **关联 AC**: AC-S-128
- **前置条件**: T-A 下 `action='rbac.role.grant'` 的记录数为 0
- **测试步骤**:
  1. 以 `u-op` 调 `POST /api/rbac/roles/r-1/permissions`（授予 `p-1`）
  2. 查 `SELECT count(*) FROM platform_audit_log WHERE tenant_id='t-audit' AND action='rbac.role.grant'`
- **预期结果**:
  1. 步骤 1 返回成功
  2. 步骤 2 的计数 `== 1`（**恰好 1**）
  3. 该条 `actor_id == 'u-op'`
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 基本路径
- **备注**: 「恰好 1 条」排除「一次授权写多条」与「没写」两种实现。

### TC-014-062: 撤销权限 `p-1` → **再**产生 **恰好 1 条**审计记录

- **关联 AC**: AC-S-128
- **前置条件**: TC-014-061 已完成（`r-1` 现在持有 `p-1`）
- **测试步骤**:
  1. 以 `u-op` 撤销 `r-1` 的 `p-1`
  2. 查 `action='rbac.role.revoke'` 的条数
  3. 查 `action='rbac.role.grant'` 的条数（**确认没有多写一条 grant**）
- **预期结果**:
  1. 步骤 2 的计数 `== 1`
  2. 步骤 3 的计数仍 `== 1`（撤销**不**追加一条 grant）
  3. 撤销那条 `actor_id == 'u-op'`
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 基本路径
- **备注**: 第 2 条防「撤销时复用 grant 事件码」的实现错误 —— 那是**审计说谎**，
  看板上「授权次数」会虚高。

### TC-014-063: 授予的 `before` / `after` 方向正确（**变更前不在、变更后在**）

- **关联 AC**: AC-S-128
- **前置条件**: 同 TC-014-061
- **测试步骤**:
  1. 授予 `p-1`
  2. 读该条记录的 `before` / `after`，**解析**成 JSON
  3. 在两份里找 `p-1`
- **预期结果**:
  1. `before` 可解析，`after` 可解析
  2. `p-1` **不在** `before` 里
  3. `p-1` **在** `after` 里
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 状态迁移（前 → 后）
- **备注**: 「方向」是这条 AC 的核心，**不锁 JSON 形状**（规格没定义形状）。
  「`p-1` 在不在」的判据要在**任一层**都能取到（顶层数组 / 顶层对象的某个键）→
  建议 BA 把形状钉死（推荐 `{"permissions":["p-1"]}`），否则实现自由度太大。〔S-30〕

### TC-014-064: 撤销的 `before` / `after` 方向**相反**（**变更前在、变更后不在**）

- **关联 AC**: AC-S-128
- **前置条件**: 同 TC-014-062（`r-1` 先持有 `p-1`）
- **测试步骤**:
  1. 撤销 `p-1`
  2. 读该条记录的 `before` / `after` 并解析
  3. 在两份里找 `p-1`
- **预期结果**:
  1. `p-1` **在** `before` 里
  2. `p-1` **不在** `after` 里
  3. 授予那条与撤销那两条的 `before` / `after` **方向相反**（不是同一份内容复制两遍）
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 状态迁移
- **备注**: 第 3 条防「两个事件用同一份 before/after」。若方向反了，
  审计记录会**说反**变更事实 —— 这正是审计最不能出的错。

### TC-014-065: 两条记录的 `actor_id` == **操作者** ID（不是被操作对象）

- **关联 AC**: AC-S-128
- **前置条件**: 同 TC-014-061 / 062
- **测试步骤**:
  1. 授予 + 撤销各一次
  2. 读两条记录的 `actor_id` 与 `object_id`
- **预期结果**:
  1. 两条的 `actor_id` 都 `== 'u-op'`
  2. 两条的 `object_id` 都 `== 'r-1'`（**不是** `u-op`、不是 `p-1`）
  3. 两条的 `actor_id != object_id`
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 字段映射
- **备注**: 「谁做的」与「对谁做的」必须分开 —— 混了就没法追责。

### TC-014-066: `object_type` == **角色**对象类型（逐字）

- **关联 AC**: AC-S-128
- **前置条件**: 同 TC-014-061
- **测试步骤**:
  1. 授予 `p-1`
  2. 读该条记录的 `object_type`
- **预期结果**:
  1. `object_type` 非空
  2. `object_type` 的值**逐字**等于实现约定的角色对象类型串
     （**具体值由 BA 钉死**；推荐沿用既有 `rbac` 域命名，如 `role`）
  3. `object_type != "permission"`（被授予的 `p-1` **不是**审计对象本身）
- **类型**: 功能
- **优先级**: P1
- **自动化**: 可自动化
- **设计方法**: 字段映射
- **备注**: AC 原文只说「`object_type` == **角色对象类型**」—— **没有给字面量**。
  本用例把第 2 条标为**待钉死**。〔S-15〕

### TC-014-067: 创建角色 → **恰好 1 条** `rbac.role.create`

- **关联 AC**: AC-S-128
- **前置条件**: 同 TC-014-061
- **测试步骤**:
  1. 以 `u-op` 创建一个新角色
  2. 查 `action='rbac.role.create'` 的条数
- **预期结果**:
  1. 步骤 2 的计数 `== 1`
  2. 该条 `object_id == <新建角色的 id>`
  3. 该条 `before IS NULL`、`after` **非 NULL**（新建：前无后有）
- **类型**: 安全
- **优先级**: P1
- **自动化**: 可自动化
- **设计方法**: 基本路径
- **备注**: AC-S-128 只点了「授予与撤销」；design §6.1 埋点表里还有
  `rbac.role.create` / `rbac.role.delete`（demand §5 也列了「创建角色、删除角色」）。
  **AC 覆盖不全** —— 本条与 TC-014-068 把 design 的承诺补上。〔S-31〕

### TC-014-068: 删除角色 → **恰好 1 条** `rbac.role.delete`

- **关联 AC**: AC-S-128
- **前置条件**: 先创建一个角色并记下其 id
- **测试步骤**:
  1. 以 `u-op` 删除该角色
  2. 查 `action='rbac.role.delete'` 的条数
  3. 读该条的 `before` / `after`
- **预期结果**:
  1. 步骤 2 的计数 `== 1`
  2. 该条 `object_id == <被删角色的 id>`
  3. 该条 `before` **非 NULL**、`after IS NULL`（删除：前有后无）
- **类型**: 安全
- **优先级**: P1
- **自动化**: 可自动化
- **设计方法**: 基本路径
- **备注**: 同 TC-014-067。**删除的 `after` 应该是 NULL 而不是 `{}`** ——
  若实现统一写成 `{}`，本条第 3 条会红（那是**语义分歧**，不是格式分歧）。
