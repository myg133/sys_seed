# 保留策略与归档（AC-S-131）

- **覆盖 AC**: AC-S-131（10 条：TC-014-091 ~ 100）
- **前置基线**:
  - 测试库 `base_test`；租户 `t-audit`（T-A）
  - 审计表里有 **1 条足够旧**的记录与 **1 条很新**的记录
  - 应用连接 = `base_app`（`base_platform_app` 组角色成员）
  - 归档触发方式二选一（design D137）：`POST /api/audit/archive`（需 `audit:archive:run`）
    或 `cargo xtask audit archive`
- **实现事实（用例按此写）**:
  - 保留期配置：`audit.retention.online_days`（默认 90）、`audit.retention.archive_days`（默认 365，
    **本轮只登记不执行**，design §8）
  - 归档走 `SECURITY DEFINER` 函数 `platform_audit_archive_move(p_before TIMESTAMPTZ)`
    （design §3.6）—— **不是**应用角色直删
  - 归档响应（design §5.3）：`{ moved, archivedAt, nextRecommendedAt }`
  - ⚠️ **「足够旧的记录」无法通过 sink 构造**：写入函数内部固定用 `clock_timestamp()`（D143），
    没有「指定 `created_at`」的入口。所以只能用**管理员连接直接 INSERT** 一条
    `created_at` 在保留期之前的记录（**绕开 sink**）。
  - ⚠️ 归档表也有 RLS（design §3.3），应用角色查它需要先设租户上下文。

### TC-014-091: 超期记录被**搬入**归档表，旧记录离开在线表

- **关联 AC**: AC-S-131
- **前置条件**: T-A 在线表有 1 条旧记录（`created_at` 早于保留期）与 1 条新记录
- **测试步骤**:
  1. 执行归档动作（接口或 xtask）
  2. 查在线表（`platform_audit_log`）与归档表（`platform_audit_archive`），按 `id` 查
- **预期结果**:
  1. 旧记录的 `id` **不在**在线表
  2. 旧记录的 `id` **在**归档表
  3. 新记录的 `id` **仍在**在线表、**不在**归档表
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 基本路径
- **备注**: 「旧 / 新」的判据是 `created_at` 与保留期阈值的关系 —— 阈值由
  `audit.retention.online_days`（默认 90 天）决定。用例用「120 天前」与「今天」两条，
  留足余量（不依赖阈值的精确边界）。

### TC-014-092: 归档表内容与被搬走的记录**逐字段相同**（含 `hash` / `prev_hash`）

- **关联 AC**: AC-S-131
- **前置条件**: 同 TC-014-091；**先记下旧记录的全列快照**
- **测试步骤**:
  1. 执行归档
  2. 读归档表里那条记录的**全部列**
  3. 与快照逐列比对
- **预期结果**:
  1. 13 个契约字段**逐个相同**（含 `hash`、`prev_hash`、`before`、`after`、`created_at`）
  2. 归档表**额外**有 `archived_at`（非空）
  3. `archived_at` **不等于**原记录的 `created_at`
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 状态快照
- **备注**: 「逐字段相同」是 AC 的原文判据，也是**归档不破坏链**的前提 ——
  `hash` / `prev_hash` 必须原样带走，否则搬完链就断了。
  第 2 条说明归档表确实**多**了一列（design §3.2）。

### TC-014-093: 归档表的列集合 = 在线表列集合 **+ `archived_at`**

- **关联 AC**: AC-S-131
- **前置条件**: 归档表已存在
- **测试步骤**:
  1. 查 `pg_attribute` 取两张表的列名集合
  2. 比对
- **预期结果**:
  1. 归档表列集合 `==` 在线表列集合 **∪** `{archived_at}`
  2. 归档表列数 `==` 14（13 + 1）
- **类型**: 功能
- **优先级**: P1
- **自动化**: 可自动化
- **设计方法**: 集合精确匹配
- **备注**: AC 说「逐字段相同」，但**没说归档表会不会多列**。design §3.2 说会多 `archived_at`。
  本用例把这条钉死，避免「归档表少一列」（那会让 `SELECT *` 的形状对不上）。

### TC-014-094: 归档**幂等** —— 第二次执行不报错，归档表行数不变

- **关联 AC**: AC-S-131
- **前置条件**: TC-014-091 已完成；记下归档表当前行数
- **测试步骤**:
  1. 再执行一次归档动作
  2. 查归档表行数与在线表行数
- **预期结果**:
  1. 步骤 1 **不报错**（HTTP `200`；xtask 退出码 `0`）
  2. 归档表行数与执行前**完全相同**
  3. 响应 `moved == 0`
  4. 在线表行数与执行前**完全相同**
- **类型**: 功能
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 幂等
- **备注**: design §3.6 明写「幂等：第二次执行没有可搬的行 → 影响 0 行，不报错」。
  第 3 条把「幂等」落成**响应体里的数字**，不只是「不报错」。

### TC-014-095: 应用角色对**归档表** `UPDATE` → `permission denied`

- **关联 AC**: AC-S-131
- **前置条件**: 归档表里至少 1 条记录；应用连接 = `base_app`
- **测试步骤**:
  1. 以 `base_app` 执行 `UPDATE platform_audit_archive SET after = '{}' WHERE id = <某条>`
  2. 记录错误
- **预期结果**:
  1. 语句**失败**
  2. 错误信息含 `permission denied`
  3. SQLSTATE `== 42501`
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 攻击路径
- **备注**: 与 TC-014-012 同族，但**对象是归档表** —— 归档表不是「二等公民」，
  它同样必须 append-only（demand §6、AC-S-131 步骤 4）。

### TC-014-097: 归档表行数在两条失败语句后**不变**

- **关联 AC**: AC-S-131

### TC-014-098: 归档后链校验仍 `ok = true`（`checked` 相应减少）

- **关联 AC**: AC-S-131
- **前置条件**: T-A 归档前有 3 条记录；链正确
- **测试步骤**:
  1. 记录归档**前**的链校验结果（`checked` = 3）
  2. 执行归档（把 1 条旧记录搬走）
  3. 再调用链校验
- **预期结果**:
  1. 步骤 3 的 `ok == true`、`broken` 长度 `0`
  2. 步骤 3 的 `checked == 2`（**归档后在线表里剩几条就 checked 几条**）
  3. 步骤 1 与步骤 3 的 `checked` 之差 `==` 被搬走的条数
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 状态迁移
- **备注**: ⚠️ **AC 与 design 都未定义归档后的链校验语义**。
  搬走中间的记录会让剩余记录的 `prev_hash` **接不上**（第 2 条的 `prev_hash` 指向已搬走那条）→
  合理的口径有三种：(a) `ok=false` 且 broken 报接续断裂；(b) `ok=true` 且只验**连续段**；
  (c) 归档时**重算**剩余记录的链（但那会破坏「逐字段相同」）。
  **BA 必须钉死一种**，否则本用例无法判定红绿。〔S-16〕

### TC-014-099: 归档动作可由**接口**触发（`POST /api/audit/archive`）

- **关联 AC**: AC-S-131
- **前置条件**: 有一个具备 `audit:archive:run` 的令牌
- **测试步骤**:
  1. 调 `POST /api/audit/archive`（带令牌 + `x-tenant-id`）
  2. 读状态码与响应体
- **预期结果**:
  1. HTTP `200`
  2. 响应体含 `moved`（数字）、`archivedAt`（RFC3339）、`nextRecommendedAt`（RFC3339）
  3. `nextRecommendedAt > archivedAt`
- **类型**: 功能
- **优先级**: P1
- **自动化**: 可自动化
- **设计方法**: 基本路径
- **备注**: design §5.3 的响应形状 + D137 的「让运维看得见下次该什么时候归档」。
  第 3 条把「看得见」变成可判定断言。

### TC-014-100: 归档动作可由**命令行**触发（`cargo xtask audit archive`）

- **关联 AC**: AC-S-131
- **前置条件**: `DATABASE_URL` 指向 `base_test`（**用哪个角色连由 BA 定** —— 见备注）
- **测试步骤**:
  1. 执行 `cargo xtask audit archive`
  2. 读退出码与标准输出
- **预期结果**:
  1. 退出码 `== 0`
  2. 标准输出含被搬走的条数（**或**一句可解析的摘要）
  3. 执行后在线表少了对应条数、归档表多了对应条数
- **类型**: 功能
- **优先级**: P1
- **自动化**: 半自动
- **自动化理由**: xtask 需要**环境变量**（`DATABASE_URL`）与**工作目录**，
  放进 Rust 测试套件要起子进程 + 拼环境，比较笨重；
  判据（退出码 + 行数变化）本身可机械判定，建议由**验收脚本**跑一次并留输出。
- **设计方法**: 基本路径
- **备注**: ⚠️ **角色未定**：xtask 用**超级用户 `base`** 连 → 绕过 RLS → 能搬所有租户的记录；
  用 `base_app` 连 → 受 RLS 限制 → 只搬得到本租户。
  **AC-S-131 没说归档是「全平台」还是「单租户」** → 需 BA 钉死。〔S-34〕
