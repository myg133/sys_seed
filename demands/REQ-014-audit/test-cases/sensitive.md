# 敏感值防护（AC-S-133）

- **覆盖 AC**: AC-S-133（10 条：TC-014-101 ~ 110）
- **前置基线**:
  - 测试库 `base_test`；租户 `t-audit`（T-A）
  - 测试口令 `p@ssw0rd`（**canary**），检索时按**完整字面量**搜
  - 敏感键扫描器是**可单独调用**的（能喂一段字符串进去）
- **实现事实（用例按此写）**:
  - D134：敏感键集合含 `password` / `secret` / `token` / `credential` / `private_key` / `api_key`
    等，**大小写与连字符变体一并匹配**；**硬拒绝**（不静默剥离）
  - design §3.5：敏感键检查作用在**入参文本**上（`jsonb_path_exists` 或 `jsonb_each_text`）
  - design §2.3：敏感键检查在 `platform-core/extension/audit.rs`（应用侧）
  - ⚠️ **检查放在哪一层没定**：design §2.3 说 core 做、§3.5 说 DB 函数内做。
    若**只在 DB 做**，则「绕过 core 直接调 `platform_audit_append`」的路径不拦；
    若**只在 core 做**，则 DB 函数不拦。两处都做才闭合 —— 但两处**必须用同一套键集合**。〔S-19〕
  - ⚠️ **扫描器的宿主没定**：AC-S-133 步骤 4 要求「对一段**确实含**敏感键的样例字符串跑
    **同一个**敏感键扫描器」—— 能被喂字符串的扫描器只能在 **Rust 侧**（DB 里的 plpgsql
    函数没法被喂一段任意字符串并返回命中集合）。〔S-19〕

### TC-014-101: `before` 含 `password` 键 → 写入**被拒绝**且未落库

- **关联 AC**: AC-S-133
- **前置条件**: T-A 下 `action='demo.sensitive'` 的记录数为 0
- **测试步骤**:
  1. 尝试记录一条 `before = {"password":"p@ssw0rd"}` 的事件
  2. 查 T-A 的审计表里 `action='demo.sensitive'` 的条数
- **预期结果**:
  1. 步骤 1 **失败**（返回错误，**不是** 200）
  2. 步骤 2 的计数 `== 0`（**事件未落库**）
  3. 错误响应体是 RFC 9457 ProblemDetails，`code == "AUDIT_SENSITIVE_PAYLOAD_REJECTED"`
  4. 错误响应体**不含** `p@ssw0rd`
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 攻击路径
- **备注**: 错误码取自 design §7。AC 只说「返回**明确错误码**（不是 500）」——
  本用例把「明确」落成具体码。〔S-20〕
  第 4 条防「拒绝时把值回显到错误信息里」（design §3.5 明确要求不得回显）。

### TC-014-102: `after` 含 `password` 键 → 同样被拒绝

- **关联 AC**: AC-S-133
- **前置条件**: 同 TC-014-101
- **测试步骤**:
  1. 尝试记录一条 `after = {"password":"p@ssw0rd"}` 的事件
  2. 查落库条数
- **预期结果**:
  1. 步骤 1 **失败**，`code == "AUDIT_SENSITIVE_PAYLOAD_REJECTED"`
  2. 步骤 2 的计数 `== 0`
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 攻击路径（等价类）
- **备注**: `before` 与 `after` 是**两个独立字段**（D131 里的两个位置），
  只查一个是最常见的漏做。AC-S-133 步骤 1 只写了 `before` → 本条补齐 `after`。

### TC-014-103: `before` 为 `{"name":"ok"}` 的正常事件**正常落库**

- **关联 AC**: AC-S-133
- **前置条件**: 同 TC-014-101
- **测试步骤**:
  1. 记录一条 `before = {"name":"ok"}` 的事件
  2. 查落库条数与内容
- **预期结果**:
  1. 步骤 1 **成功**
  2. 步骤 2 的计数 `== 1`
  3. 该条 `before` 解析后 `== {"name":"ok"}`
- **类型**: 功能
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 正常对照组
- **备注**: 这条是 TC-014-101 的**对照组** —— 只断言「拒绝」的话，
  「所有写入都被拒」也能通过。

### TC-014-104: 落库后检索**不含** `p@ssw0rd`

- **关联 AC**: AC-S-133
- **前置条件**: 同 TC-014-101
- **测试步骤**:
  1. 执行 TC-014-101（尝试写 `{"password":"p@ssw0rd"}`，被拒）
  2. 检索 T-A 的**全部审计记录文本**（所有列拼成一个大字符串）
  3. 在该字符串里搜 `p@ssw0rd`
- **预期结果**:
  1. 步骤 3 的命中数 `== 0`
  2. 步骤 2 检索到的记录数 `> 0`（**防空绿**：证明确实检索到了东西）
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 攻击路径 + 全量扫描
- **备注**: 第 2 条是关键 —— 「检索结果不含 X」在「什么也没检索到」时是**恒真**的。
  与 TC-014-057 同款纪律。

### TC-014-105: 敏感键扫描器**阳性对照** —— 喂一段确实含敏感键的样例，必然命中

- **关联 AC**: AC-S-133
- **前置条件**: 敏感键扫描器是**可单独调用**的（能接收一段 JSON 文本并返回命中键集合）
- **测试步骤**:
  1. 构造样例串：
     `{"user":"alice","password":"p@ssw0rd","nested":{"api_key":"AKIA-CANARY-0001"}}`
  2. 把这段串喂给**与生产写入路径同一个**扫描器
  3. 读返回的命中键集合
- **预期结果**:
  1. 步骤 3 的命中集合**非空**
  2. 命中集合**包含** `password`
  3. 命中集合**包含** `api_key`（**嵌套层也命中**）
  4. 命中集合**不包含** `user`（不误伤）
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 阳性对照（dev-guide §9.2）
- **备注**: **没有这条，TC-014-104 的「0 命中」不可信** ——
  扫描器根本没生效与真的干净，在输出上完全一样。
  dev-guide §9.2 明确点名「敏感值扫描也必须带阳性对照」。
  ⚠️ 这条**要求扫描器是可单独调用的** → 扫描器必须在 **Rust 侧**（core），
  DB 侧的 plpgsql 实现无法被喂字符串。〔S-19〕

### TC-014-106: 敏感键**集合** —— 6 个基线键全部被拒

- **关联 AC**: AC-S-133
- **前置条件**: 扫描器可单独调用
- **测试步骤**:
  1. 对下列 6 个样例各调一次扫描器：
     `{"password":"x"}`、`{"secret":"x"}`、`{"token":"x"}`、`{"credential":"x"}`、
     `{"private_key":"x"}`、`{"api_key":"x"}`
  2. 记录每个样例的命中键集合
- **预期结果**:
  1. 6 个样例**全部**命中（`>= 1` 个键）
  2. 每个样例的命中键**恰好对应**它自己的那个键（不多不少）
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 判定表（等价类）
- **备注**: D134 列了这 6 个基线键 + 「**等**」。
  **「等」字把集合留空了** → AC 没定义「哪些键算敏感」→ 不可判定。
  本用例把集合钉成 **D134 明列的 6 个**（最小闭包）；**BA 需补全完整清单**
  （建议再补 `passwd` / `pwd` / `refresh_token` / `client_secret` / `authorization` / `cookie`）。〔S-20〕

### TC-014-107: 大小写与连字符变体一并匹配

- **关联 AC**: AC-S-133
- **前置条件**: 扫描器可单独调用
- **测试步骤**:
  1. 对下列样例各调一次扫描器：
     `{"Password":"x"}`、`{"PASSWORD":"x"}`、`{"api-key":"x"}`、`{"apiKey":"x"}`、
     `{"API_KEY":"x"}`、`{"access-token":"x"}`
  2. 记录命中情况
- **预期结果**:
  1. 6 个样例**全部**命中
  2. `{"Password":"x"}` 与 `{"PASSWORD":"x"}` 的命中键**归一化后**等于 `password`
     （即匹配是**大小写不敏感**的）
  3. `{"api-key":"x"}` 与 `{"api_key":"x"}` 都命中（**连字符与下划线等价**）
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 等价类（书写变体）
- **备注**: D134 明写「大小写与连字符变体一并匹配」。
  第 2 条要求命中键**归一化后**比较 —— 报 `Password` 还是 `password` 规格没定，
  本用例按「归一化后相等」写（不锁原始大小写）。〔S-20〕

### TC-014-108: **嵌套**层级的敏感键也命中

- **关联 AC**: AC-S-133
- **前置条件**: 扫描器可单独调用
- **测试步骤**:
  1. 对 `{"a":{"b":{"password":"x"}}}` 调扫描器
  2. 对 `[{"password":"x"}]`（数组元素里的对象）调扫描器
- **预期结果**:
  1. 两个样例**都**命中
  2. 命中键 `== "password"`（或归一化后等价）
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 边界值（深度 / 数组）
- **备注**: design §3.5 提到用 `jsonb_path_exists`（**递归**）或 `jsonb_each_text`（**只到顶层**）——
  两者能力不同！`jsonb_each_text` **不递归** → 用它的实现会漏掉嵌套键。
  本用例是这条差异的守卫。

### TC-014-109: 不含敏感键的 JSON **不误伤**

- **关联 AC**: AC-S-133
- **前置条件**: 扫描器可单独调用
- **测试步骤**:
  1. 对下列样例各调一次扫描器：
     `{"name":"ok"}`、`{"user":"alice"}`、`{"tokenizer":"gpt"}`、`{"secretary":"alice"}`、
     `{"passwordPolicy":"none"}`
  2. 记录命中情况
- **预期结果**:
  1. 5 个样例**全部 0 命中**
- **类型**: 边界
- **优先级**: P1
- **自动化**: 可自动化
- **设计方法**: 反例 / 误报边界
- **备注**: ⚠️ `{"secretary":"alice"}` 含子串 `secret`、`{"tokenizer":"gpt"}` 含子串 `token`
  —— 若实现用**子串匹配**就会误伤。本用例要求**按完整键名匹配**（不是子串）。
  第 3 条 `{"passwordPolicy":"none"}` 同理。
  **误报率过高**会让业务方把敏感键塞进别的字段名绕过防护 —— D134 的「注意」段也说了这点。

### TC-014-110: 拒绝时的错误信息**不回显**敏感值

- **关联 AC**: AC-S-133
- **前置条件**: 同 TC-014-101
- **测试步骤**:
  1. 记录一条 `before = {"password":"p@ssw0rd"}` 的事件
  2. 捕获**错误响应体**与**服务端日志**
  3. 在两者里搜 `p@ssw0rd`
- **预期结果**:
  1. 步骤 3 在**响应体**里的命中数 `== 0`
  2. 步骤 3 在**日志**里的命中数 `== 0`
  3. 错误响应体含 `code == "AUDIT_SENSITIVE_PAYLOAD_REJECTED"`
  4. 错误响应体可含**键名**（`password`），但**不含**值
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 攻击路径 + canary
- **备注**: design §3.5 明写「**不得**把值原样回显到错误信息里」。
  本条把「不得回显」扩到**日志** —— 拒绝日志里带上原值同样是一次泄漏。
  第 4 条区分「键名可回显」与「值不可回显」。
