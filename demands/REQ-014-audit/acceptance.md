### AC-S-022: 哈希链可校验: 定期校验链完整性，篡改任一条目即告警

- **前置条件**: 测试库 `base_test` 可用（`DATABASE_URL_TEST` 已设置）；
  租户 `t-audit` 下已有 **≥2 条**审计记录（通过平台 sink 写入，chain 正确）。
- **测试步骤**:
  1. 读取该租户的审计记录，按 `created_at` 升序排列；
  2. 调用链校验能力（`GET /api/audit/verify` 或等价的校验函数）；
  3. **绕过应用**，直接用 SQL 把其中一条的 `after` 列改成另一个值（模拟篡改）；
  4. 再次调用链校验；
  5. 检查步骤 4 期间产生的日志。
- **预期结果**:
  - 步骤 2 返回 `ok = true`、`checked = 2`、`broken = []`；
  - 步骤 4 返回 `ok = false`，`broken` **恰好 1 条**，
    `broken[0].id` == 被篡改那条的 `id`，`broken[0].reason` == `hash_mismatch`；
  - 步骤 5 产生**至少一条 error 级别**日志，且含结构化字段
    `tenant_id` / `event_id` / `reason`。
- **类型**: 安全

### AC-S-122: 审计写入完整：一次敏感操作产生一条含全部固定字段的审计记录

- **前置条件**: 测试库可用；已认证用户 `u-1`，租户 `t-audit`。
- **测试步骤**:
  1. 通过平台审计 sink 记录一条事件（`action = "demo.update"`、
     `object_type = "demo_item"`、`object_id = "obj-1"`，
     `before = {"name":"old"}`、`after = {"name":"new"}`）；
  2. 查询该租户的审计记录。
- **预期结果**:
  - 步骤 2 恰好出现 **1 条**新增记录；
  - `tenant_id` == `t-audit`；`actor_id` == `u-1`；
  - `action` / `object_type` / `object_id` 与传入**逐字相同**；
  - `before` / `after` 解析后**等于**传入的 JSON（值相等即可，不要求键序）；
  - `ip` 与 `user_agent` **存在该列**（无值时为空串，**不得缺列**）；
  - `created_at` 非空；`prev_hash` 与 `hash` 均为 64 位小写十六进制。
- **类型**: 功能

### AC-S-123: 审计表 append-only：应用角色无法 UPDATE / DELETE 审计记录

- **前置条件**: 测试库可用；审计表已存在且至少 1 条记录；
  持有**应用连接角色**（`base_platform_app`）的连接。
- **测试步骤**:
  1. 以应用角色执行 `UPDATE platform_audit_log SET after = '{}' WHERE id = <某条>`；
  2. 以应用角色执行 `DELETE FROM platform_audit_log WHERE id = <某条>`；
  3. 统计该表的行数。
- **预期结果**:
  - 步骤 1、2 **两条语句都失败**（错误含 `permission denied`）；
  - 步骤 3 的行数与执行前**完全相同**。
- **类型**: 安全

> ⚠️ 该判据**必须用应用角色**验证。用表 owner 连接会绕过权限，测不出任何东西。

### AC-S-124: 哈希链按租户分链且可链接

- **前置条件**: 测试库可用；租户 `t-audit` 与 `t-other`。
- **测试步骤**:
  1. 在 `t-audit` 连续写入 3 条审计记录；
  2. 在 `t-other` 写入 1 条；
  3. 按租户分别取出记录，按 `created_at` 升序；
  4. **独立**用 `sha256` 复算每条的 `hash`（复算方式见
     [design-summary.md](design-summary.md) §4 规范化定义）。
- **预期结果**:
  - `t-audit` 第 1 条的 `prev_hash` == **genesis**（64 个字符 `0`）；
  - `t-audit` 第 2 条的 `prev_hash` == 第 1 条的 `hash`；
  - `t-audit` 第 3 条的 `prev_hash` == 第 2 条的 `hash`；
  - `t-other` 第 1 条的 `prev_hash` == **genesis**（**分链**，不接 `t-audit` 的尾）；
  - 步骤 4 的独立复算结果与存储的 `hash` **逐条相同**。
- **类型**: 安全

### AC-S-125: 篡改可检测且沿链连锁

- **前置条件**: 测试库可用；`t-audit` 下已有 **3 条**链正确的审计记录。
- **测试步骤**:
  1. **案例 A**：直接用 SQL 把第 2 条的 `after` 内容改成另一个值（不动 `hash`），
     调用链校验；
  2. **案例 B**：恢复原状后，直接用 SQL 把第 2 条**存储的 `hash` 值**改成另一个
     64 位十六进制（其它列不动），调用链校验。
- **预期结果**:
  - 案例 A：`ok = false`，`broken` **恰好 1 条**（第 2 条），`reason` == `hash_mismatch`；
  - 案例 B：`ok = false`，`broken` **恰好 2 条**（第 2 条与**第 3 条**），
    第 2 条 `reason` == `hash_mismatch`，第 3 条 `reason` == `hash_mismatch`
    —— 第 3 条被牵连是因为它的 `prev_hash` 指向了已被改掉的第 2 条 `hash`，
    **这证明链是连锁的**，不是逐条独立的校验。
- **类型**: 安全

### AC-S-126: 审计记录跨租户不可见（数据库强制，非应用层过滤）

- **前置条件**: 测试库可用；租户 `t-audit` 有 1 条记录；租户 `t-other` 有 1 条记录。
- **测试步骤**:
  1. 以租户 `t-other` 的令牌调用审计查询接口；
  2. 以应用角色连接，把 `app.tenant_id` 设为 `t-other` 后直接查
     `SELECT * FROM platform_audit_log`；
  3. 把 `app.tenant_id` 设为 `t-audit` 再查一次。
- **预期结果**:
  - 步骤 1 的结果**不含** `t-audit` 的那条记录；
  - 步骤 2 的结果**不含** `t-audit` 的那条记录（**RLS 生效**）；
  - 步骤 3 的结果**含** `t-audit` 的那条记录。
- **类型**: 安全

### AC-S-127: 登录审计：成功与失败各一条，含 IP 与设备，且不含凭据

- **前置条件**: 测试库可用；本地登录接口可用；一个 SSO provider 已配置。
- **测试步骤**:
  1. 用正确密码本地登录一次；
  2. 用错误密码本地登录一次；
  3. 走一次 SSO 登录成功；
  4. 检索该租户的全部审计记录文本。
- **预期结果**:
  - 步骤 1 产生 **1 条** `iam.login.succeeded`；
  - 步骤 2 产生 **1 条** `iam.login.failed`；
  - 步骤 3 产生 **1 条** `iam.sso.login.succeeded`；
  - 上述三条**均含**非空的 `ip` 与 `user_agent`；
  - 步骤 4 的检索结果**不含**测试密码的字面量，也**不含**任何 access/refresh token。
- **类型**: 安全

### AC-S-128: 权限变更审计：授予与撤销各一条，含变更前后值

- **前置条件**: 测试库可用；已有一个角色 `r-1`；操作者具备角色管理权限。
- **测试步骤**:
  1. 给 `r-1` 授予权限 `p-1`，检索审计记录；
  2. 从 `r-1` 撤销权限 `p-1`，检索审计记录。
- **预期结果**:
  - 步骤 1 产生 **1 条**记录，`action` 为授予动作，
    `object_type` == 角色对象类型，`object_id` == `r-1`，
    `before` / `after` 能解析出 `p-1` 在**变更前不在**、**变更后在**；
  - 步骤 2 再产生 **1 条**记录，`before` / `after` 的方向**相反**
    （变更前在、变更后不在）；
  - 两条记录的 `actor_id` == 操作者 ID。
- **类型**: 安全

### AC-S-129: 统一埋点入口：业务模块不需自建审计表

- **前置条件**: 测试库可用。
- **测试步骤**:
  1. 用平台提供的**通用审计事件类型 + sink trait** 记录一条事件；
  2. 把 `platform-org` 已声明的事件（`org.node.create`）送进平台 sink；
  3. 把 `platform-iam` 的 SSO 事件送进平台 sink；
  4. 扫描全部 crate 的源码，查找 `INSERT INTO platform_audit_log`；
  5. 运行 `platform-org` 与 `platform-iam` 的既有测试。
- **预期结果**:
  - 步骤 1~3 的事件**都**出现在审计表里；
  - 步骤 4 的扫描结果**只有平台 sink 所在模块**命中；
    且扫描器有**阳性对照** —— 用同一扫描器扫一段确实含该 SQL 的样例，
    **必然命中**（否则「0 命中」不可信，见 dev-guide §9.2）；
  - 步骤 5 全绿（`platform-org` / `platform-iam` 的既有 recorder trait
    **签名未被破坏**）。
- **类型**: 功能

### AC-S-130: 审计查询接口：分页、多维过滤、权限控制

- **前置条件**: 测试库可用；租户 `t-audit` 下写入 **5 条**记录，
  它们在 `actor_id` / `action` / `object_type` / `created_at` 上**互不相同**。
- **测试步骤**:
  1. 调用 `GET /api/audit/events?page=1&size=2`；
  2. 分别按 `actorId`、`action`、`objectType`、`from`/`to` 过滤；
  3. 用**没有** `audit:events:read` 权限的令牌调用同一接口；
  4. 用一个 `size=1000` 的请求调用。
- **预期结果**:
  - 步骤 1 返回该租户的 **2 条**记录 + **总数 5**；
  - 步骤 2 每种过滤的结果与写入的数据**一致**（不多不少）；
  - 步骤 3 返回 **403** 且错误码**明确**（不是 500）；
  - 步骤 4 的 `size` 被**夹到上限**（≤ 200），不返回 1000 条。
- **类型**: 功能

### AC-S-131: 保留策略与归档：超期记录搬入归档表，归档表同样 append-only

- **前置条件**: 测试库可用；审计表有 1 条**足够旧**的记录与 1 条**很新**的记录；
  应用角色连接可用。
- **测试步骤**:
  1. 执行归档动作；
  2. 查询在线审计表与归档表；
  3. 再执行一次归档动作；
  4. 以应用角色对**归档表**执行 `UPDATE` 与 `DELETE`；
  5. 统计归档表行数。
- **预期结果**:
  - 步骤 2：旧记录**不在**在线表、**在**归档表；新记录**仍在**在线表；
  - 步骤 3：**幂等** —— 不报错，且归档表行数与步骤 2 相同；
  - 步骤 4：两条语句**都失败**（`permission denied`），归档表行数不变；
  - 归档表内容与被搬走的记录**逐字段相同**（含 `hash` / `prev_hash`）。
- **类型**: 安全

### AC-S-132: 审计查询界面：列表、分页、过滤、字段展示

- **前置条件**: shell 已启动；测试库可用且有审计数据；
  有一个具备 `audit:events:read` 权限的账号。
- **测试步骤**:
  1. 进入审计查询页面；
  2. 翻页；
  3. 按操作人与动作过滤；
  4. 用**无权限**账号访问该页面。
- **预期结果**:
  - 步骤 1 列出审计记录，且**同时显示**操作人、时间、动作、对象、来源 IP；
  - 步骤 2 分页可用，翻页后记录**不重复**；
  - 步骤 3 过滤生效，结果与后端接口一致；
  - 步骤 4 落 **403 页**，且 403 页**不是**空白页。
- **类型**: 功能

### AC-S-133: 敏感值防护：`before` / `after` 含敏感键时写入被拒绝

- **前置条件**: 测试库可用。
- **测试步骤**:
  1. 尝试记录一条 `before` 为 `{"password":"p@ssw0rd"}` 的事件；
  2. 记录一条 `before` 为 `{"name":"ok"}` 的正常事件；
  3. 检索该租户的全部审计记录文本；
  4. 对一段**确实含**敏感键的样例字符串跑同一个敏感键扫描器。
- **预期结果**:
  - 步骤 1 **被拒绝**，返回**明确错误码**（不是 500），且该事件**未落库**；
  - 步骤 2 正常落库；
  - 步骤 3 的检索结果**不含** `p@ssw0rd`；
  - 步骤 4 的扫描器**命中**（阳性对照 —— 否则「0 命中」不可信，见 dev-guide §9.2）。
- **类型**: 安全
