### AC-S-029: `trace_id` 在**日志 / 响应体 / 审计事件**里是**同一个值**

- **前置条件**: 服务已启动；`tenant-a` 有一个可写的业务对象（用 `platform-app` 的 app 资源）。
- **测试步骤**:
  1. 发一个**不带** `X-Request-Id` 的请求：`POST /api/apps`（合法 body）；
  2. 从响应头取 `X-Request-Id`（记为 `T`）；
  3. 从响应体取 `.traceId`（若失败响应则取 `.trace_id`）；
  4. 查 `platform_audit_log` 里该次操作那一行的 `trace_id`；
  5. 从服务日志（测试里用 `tracing_subscriber` 的内存 writer 捕获）里找 `T`。
- **预期结果**:
  - 步骤 2：响应头**必有** `X-Request-Id`，且是 32 位小写 hex（无连字符）；
  - 步骤 3：**逐字等于** `T`（⚠️ 不是「都有 trace_id 字段」，是**同一个值**）；
  - 步骤 4：`platform_audit_log.trace_id` **逐字等于** `T`
    （⚠️ 审计链路要能按 trace_id 反查，否则「贯穿」是假的）；
  - 步骤 5：捕获到的日志里**至少一行**含 `trace_id=T`
    （⚠️ 判据是「日志里带 trace_id」，不是「日志里有内容」）。
- **类型**: 功能 / 可维护性

### AC-S-030: 入站 `X-Request-Id` 被**沿用**，非法值被**拒绝或替换**（不能原样透传）

- **前置条件**: 同 AC-S-029。
- **测试步骤**（**4 条独立路径**）:
  1. 发请求带 `X-Request-Id: 0123456789abcdef0123456789abcdef`（合法 32 hex）→ 期望**沿用**；
  2. 发请求带 `X-Request-Id: ABCDEF0123456789ABCDEF0123456789`（**大写**）→ 期望**沿用但归一为小写**；
  3. 发请求带 `X-Request-Id: abc`（太短）→ 期望**不用它**，生成新的；
  4. 发请求带 `X-Request-Id: ../../etc/passwd`（**含路径穿越字符**）→ 期望**不用它**，生成新的。
- **预期结果**:
  - 步骤 1：响应头 `X-Request-Id` **逐字等于** 请求给的值；
  - 步骤 2：响应头是**小写版**（`abcdef01...`），⚠️ 不是原样大写、也不是新生成的；
  - 步骤 3/4：响应头是**新生成的合法值**（32 小写 hex），且**不等于**请求里那个非法值；
  - **⚠️ 安全判据（步骤 4）**：非法值**不得**回显到响应头、日志、审计表任何一处
    （日志注入 / 头注入的经典形态）；
  - **判据独立性**：步骤 2 若实现直接透传（不归一）→ 红；步骤 3/4 若实现原样透传 → 红。
- **类型**: 安全

### AC-S-031: 三级限流**各自独立**（租户 / 用户 / 接口）

- **前置条件**:
  - 配置：`rateLimit.tenant.requests = 3` / `rateLimit.user.requests = 2` /
    `rateLimit.endpoint.requests = 1`（**全部**是「每 60 秒」窗口，`windowSeconds = 60`）；
  - 两个用户 `user-a` / `user-b`（**同一个** `tenant-a`）；
  - 两个端点 `/api/rbac/roles` 与 `/api/apps`（都属于**同一个**接口限流维度吗？见下）。
- **测试步骤**（**4 条独立路径**）:
  1. **接口维度**：`user-a` 连打 `GET /api/rbac/roles` **2 次**（上限 1）；
  2. **用户维度**：`user-a` 打 `GET /api/apps` **3 次**（用户上限 2，接口上限 1 —— 这里要
     先把接口维度的键换成不同的 —— 见下方 ⚠️）；
  3. **租户维度**：`user-a` 与 `user-b` 交替打不同端点，合计超过租户上限 3；
  4. **跨维度隔离**：`user-b` 在 `user-a` 已被限流后，打**同一个**被限流的端点。
- **预期结果**:
  - 步骤 1：第 1 次 **200**，第 2 次 **429**（接口维度生效）；
  - 步骤 2：用户维度独立计数 —— 即使接口维度没超，第 3 次也 **429**；
  - 步骤 3：**恰好第 4 次**（累计）开始 **429**，且 `params.dimension == "tenant"`；
  - 步骤 4：`user-b` **仍然 200**（⚠️ **关键判据**：别人的限流不能影响我）；
  - 所有 429 的 `params.dimension` 逐字属于 `{"tenant","user","endpoint"}`，
    且响应体 `code` 是 **`RATE_LIMITED`**。
- **⚠️ 判据怎么写才不互相覆盖**（必读）:
  - 「接口维度」的键是 **HTTP 路径模板**（`/api/rbac/roles`），不是完整 URL ——
    否则 `?a=1` 与 `?a=2` 会算两个桶（**可被绕过**：加个随机 query 就无限打）。
    判据要专门测这个：`GET /api/rbac/roles?x=1` 与 `?x=2` 必须**共用**一个桶；
  - 三个维度**必须**用三个独立的键前缀（`rl:tenant:` / `rl:user:` / `rl:endpoint:`），
    否则 ABAC 上会串桶。判据：把配置改成只有 `tenant` 维度启用
    （`user.requests = 0` 表示**禁用**该维度），此时用户维度**不再**限流。
- **类型**: 功能 / 安全

### AC-S-032: 429 的**响应语义**：`Retry-After` + `params` + 不泄露内部结构

- **前置条件**: 同 AC-S-031，接口维度上限 1。
- **测试步骤**:
  1. 触发接口限流（第 2 次请求）→ 读响应头与响应体；
  2. 等 **窗口过期**（`windowSeconds = 2`，等 3 秒）后再打一次；
  3. 检查响应体里**不得**出现的内容。
- **预期结果**:
  - 步骤 1：**429**；响应头 `Retry-After` **必有**且是**正整数秒**（十进制，无单位后缀）；
  - 步骤 1：响应体 `params.dimension` ∈ `{"tenant","user","endpoint"}`；
    响应体 `code == "RATE_LIMITED"`；
  - 步骤 2：**200**（⚠️ 窗口过期后**立即恢复**，不是「永久封禁」——
    这是「限流」与「封禁」的分界线）；
  - 步骤 3：响应体与响应头里**都不得**出现：
    ① 内部计数器当前值（如 `"current": 2`）—— 泄露限流配置；
    ② 存储实现细节（表名 `platform_rate_limit`、PG 相关字样）；
    ③ 其他租户 / 用户的标识。
    ⚠️ **判据**：对响应体全文做小写包含检查，命中任一项即失败。
- **类型**: 安全

### AC-S-033: 限流**跨实例准确**（PG 共享计数，不是每进程一份）

- **前置条件**: 两个独立的 `RateLimiter` 实例（**各持一个独立的连接池**，模拟两台机器），
  共享同一个数据库；接口维度上限 1。
- **测试步骤**:
  1. 实例 A 打 1 次 → 期望放行；
  2. 实例 B 打 1 次（**同一个键**）→ 期望 **429**；
  3. 检查数据库里的计数行。
- **预期结果**:
  - 步骤 2：**429**（⚠️ 如果实现用进程内内存计数，这里会是 200 —— 这条判据专门区分二者）；
  - 步骤 3：`platform_rate_limit` 表里对应 `(tenant_id, key, window_start)` 的行**恰好 1 行**，
    且计数反映两次请求的事实。
- **类型**: 可靠性
- **⚠️ 这条为什么必须有**: 「内存计数器」是限流最常见的偷懒实现，
  单实例测试**永远发现不了**它（单进程里内存和 PG 表现一样）。
  只有**两个独立连接池**才能区分。
- **补充判据（可断言）**: 同一实例的两次调用不能因为连接池复用而「看起来像跨实例」——
  所以测试里必须**显式**构造两个 `RateLimiter::new(pool_a)` / `new(pool_b)`，
  且 `pool_a.max_connections` 与 `pool_b` **不同**（否则无法排除「其实是同一个池」）。

### AC-S-034: 分页契约**统一**（`limit` / `cursor` / `nextCursor` / `total`）

- **前置条件**: 至少两个已实现列表的端点：`GET /api/audit/events`（已有 cursor）与
  本需求新增的统一样式端点；表里有 25 行数据。
- **测试步骤**:
  1. `GET ...?limit=10` → 读响应；
  2. 用响应里的 `nextCursor` 翻第 2 页；
  3. `GET ...?limit=10&cursor=<第 1 页的 nextCursor>` → 读响应；
  4. `GET ...?limit=0` 与 `?limit=1000`（越界值）；
  5. `GET ...?cursor=not-a-valid-cursor`。
- **预期结果**:
  - 步骤 1：响应含 `items`（**恰好 10 条**）、`nextCursor`（**非空**）、`total`（= 25）；
  - 步骤 3：返回**第 11~20 条**，且与第 1 页**零重叠**（逐条比对 id）；
  - 步骤 4：`limit=0` → **400**（`INVALID_REQUEST`）；`limit=1000` → **400**（超上限 100）；
    ⚠️ **不是静默截断**（截断会让调用方以为拿到了 1000 条）；
  - 步骤 5：**400**，`code` 是 `INVALID_REQUEST`，且 `detail` 说明 cursor 非法
    （⚠️ **不是 500** —— 非法输入不该是服务器错误）；
  - **跨 crate 一致性**：`GET /api/audit/events` 与新增端点的**字段名完全相同**
    （`items` / `nextCursor` / `total`）；⚠️ 断言写「**包含**这些字段」（D194），
    不写「等于某个固定集合」—— 允许各端点有额外字段。
- **类型**: 功能 / 可维护性

### AC-S-035: OpenAPI 产物与代码**一致**（`--check` 守卫）

- **前置条件**: `cargo xtask openapi` 已生成 `openapi.json`。
- **测试步骤**:
  1. 跑 `cargo xtask openapi --check`（干净树上）；
  2. 手工改 `openapi.json` 一个字段（改 `info.title`）；
  3. 再跑 `cargo xtask openapi --check`；
  4. 把一个端点的 `#[utoipa::path]` 注释掉（模拟「代码变了、产物没更新」）；
  5. 再跑 `cargo xtask openapi --check`。
- **预期结果**:
  - 步骤 1：**退出码 0**，输出含「与源码一致」；
  - 步骤 3：**退出码非 0**，输出指出**哪个字段**不一致；
  - 步骤 5：**退出码非 0**（⚠️ 这是核心判据：产物**不能**在代码变更后仍然通过）；
  - **产物内容判据**（步骤 1 后检查文件）：
    - `openapi` 字段是 `"3.1.0"`（⚠️ 不是 `3.0.x`）；
    - `paths` 里**至少**含 `/api/health/live` 与 `/api/rbac/roles`；
    - 每个 path 的响应里含 **`application/problem+json`**（RFC 9457 的媒体类型）；
    - `info.title` 非空、`info.version` 非空。
- **类型**: 可维护性
- **⚠️ 判据的区分力**: 步骤 3/5 是**阳性对照** —— 如果 `--check` 恒返回 0
  （比如只比较文件存在性），这两步不会红。必须有这两步才算验过。

### AC-S-036: 弃用策略：`Deprecation` 与 `Sunset` 头

- **前置条件**: 一个被标记为弃用的端点（本需求新增一个测试用端点，
  或用现有的某个端点标注弃用）。
- **测试步骤**:
  1. 调被弃用端点 → 读响应头；
  2. 调**未**弃用端点 → 读响应头（阴性对照）；
  3. 检查 `Sunset` 的格式。
- **预期结果**:
  - 步骤 1：响应头**必有** `Deprecation`，值为 `true` 或 **IMF-fixdate**
    （RFC 9745 允许两种形态；本实现选一种并**在规格里写明**）；
  - 步骤 1：响应头**必有** `Sunset`，值是 **IMF-fixdate**
    （形如 `Sun, 31 Dec 2026 23:59:59 GMT`）—— ⚠️ **严格 RFC 8594 格式**，
    不接受 ISO8601、不接受 Unix 时间戳；
  - 步骤 2：**两个头都不出现**（⚠️ 阴性对照：不能给所有响应都加上）；
  - 步骤 1：响应**状态码仍是 200**（⚠️ 弃用 ≠ 下线 —— 立刻就 410 是错的）；
  - **判据独立性**：步骤 3 若实现用 ISO8601 → 红；步骤 2 若实现无条件下发头 → 红。
- **类型**: 可维护性

### AC-S-037: OpenTelemetry 导出**配置生效**（无 collector 时的可验证部分）

- **前置条件**: 设置 `OTEL_EXPORTER_OTLP_ENDPOINT` 指向一个**本机不可达**的地址
  （如 `http://127.0.0.1:1`）；`OTEL_SDK_DISABLED=false`。
- **测试步骤**:
  1. 启动服务（或构造 tracer provider）→ 发一次请求 → 检查 span 结构；
  2. 检查**不可达端点**时的行为；
  3. 设置 `OTEL_SDK_DISABLED=true` 再启动。
- **预期结果**:
  - 步骤 1：生成的 span **有** `trace_id` / `span_id` / `parent_span_id`，
    且 `trace_id` **逐字等于**响应头 `X-Request-Id`
    （⚠️ 这是「OTel 与 HTTP 层用一个 trace」的判据，不是「都有 trace」）；
  - 步骤 1：span 层级**至少 2 层**（HTTP 请求 span 是根，其下有子 span）；
  - 步骤 2：**服务不崩、请求照常 200**，只打 **warn/error 日志**
    （⚠️ 关键判据：导出失败**不能**影响业务。这是 OTel 接入最常见的坑）；
  - 步骤 3：`OTEL_SDK_DISABLED=true` 时 **不创建** tracer provider
    （或创建了但 `is_enabled() == false`），且**不打**错误日志。
- **类型**: 功能 / 可维护性
- **⚠️ 明码不做的部分**: **真导出到 collector** 无法验证（本机无 collector）→ **TD-069**。
  上面 4 条判据是**能验证的全部**，不是「验了一部分就宣称验完了」。
