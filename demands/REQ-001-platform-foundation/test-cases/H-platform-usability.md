# H. 底座可用性 —— 测试用例（AC-029 ~ AC-030）

- **需求**: REQ-001 通用项目底座（Base Platform）
- **来源**: [acceptance.md](../acceptance.md) §底座可用性、[design-summary.md](../design-summary.md) §6（开发效率度量）
- **用例数**: 4（TC-H-001 ~ TC-H-004）
- **公共夹具**: 见 [index.md](index.md) §3 测试夹具

## H.0 本域约定

- **本域用例需要一个真实业务系统（第一个消费方）作为被测对象**，属跨项目验证，不在 REQ-001 实现范围内。
- 消费方项目遵循与业务模块相同约定：业务代码落在 `modules/<name>/` 或消费方自己的业务目录；平台核心为 `crates/platform-core/`。
- 度量口径（design-summary.md §6）：标准 CRUD 模块业务代码量 < 500 行；对平台核心的修改次数 = 0；平台同大版本升级导致业务改动次数 = 0。

---

### TC-H-001: 新业务系统代码集中在独立目录，平台核心零改动
- **关联 AC**: AC-029
- **前置条件**:
  - 已存在（或新建）一个最小业务系统：一个实体 + 列表 + 表单 + 一个审批流。
  - 已记录实施前的基线：`git log` / `git diff --stat` 快照、`crates/platform-core/` 文件哈希清单。
- **测试步骤**:
  1. 统计该业务系统的自研代码：按目录/文件列出新增文件与行数（排除锁文件、生成物、构建产物）。
  2. 执行 `git diff --stat <基线>`，检查是否有 `crates/platform-core/` 或 `crates/platform-contracts/` 的改动。
  3. 检查业务代码目录树，确认没有把业务代码写进平台核心目录或平台内部模块。
- **预期结果**:
  1. 自研业务代码全部落在约定业务目录（如 `modules/<name>/` 或消费方业务目录）；无业务代码散落到 `crates/platform-core/`。
  2. `crates/platform-core/` 与 `crates/platform-contracts/` 的改动文件数 = **0**、改动行数 = **0**（hash 清单一致）。
  3. 业务代码量满足「标准 CRUD 模块 < 500 行」的目标（实测值记录在报告中；若超出需说明原因）。
- **类型**: 功能 / 可维护性
- **优先级**: P0
- **自动化**: 半自动
- **设计方法**: 零改动断言 + 代码量度量

### TC-H-002: 用户 / 权限 / 租户 / 通知 / 审计 / 工作流全部复用底座
- **关联 AC**: AC-029
- **前置条件**:
  - 消费方业务系统已实现实体 + 列表 + 表单 + 一个审批流。
  - 底座提供相应能力（用户、权限、租户、通知、审计、工作流）。
- **测试步骤**:
  1. 检索消费方业务代码中是否存在自建的用户表、角色/权限表、租户过滤中间件、通知发送实现、审计表、工作流引擎。
  2. 逐项运行消费方功能：登录与用户列表、按钮级权限显隐与接口 403、跨租户隔离、触发一条通知、查审计记录、跑一遍审批流。
  3. 查看消费方代码对这些能力的调用方式（SDK / trait / HTTP API）。
- **预期结果**:
  1. 业务侧**不存在**自建的用户表 / 角色表 / 权限判定 / 租户过滤 / 通知发送 / 审计写入 / 工作流引擎实现；检索命中数为 0。
  2. 六项能力均由底座提供且行为正确：权限判定返回 403、跨租数据不可见、通知进入投递记录、审计记录含操作人与前后值、审批流按节点流转。
  3. 业务代码通过平台提供的入口调用（`@base/auth` 的 `can()`、平台租户上下文、平台通知/审计/工作流接口），无平行实现。
- **类型**: 功能 / 可维护性
- **优先级**: P0
- **自动化**: 半自动
- **设计方法**: 反模式扫描 + 端到端功能验证

### TC-H-003: 平台小版本升级后业务零改动即可运行
- **关联 AC**: AC-030
- **前置条件**:
  - 消费方业务系统已上线（依赖底座 API，依赖声明为平台 `0.x` 版本区间）。
  - 平台存在一个可升级的**次要版本**（如 `0.1.0` → `0.1.1`）。
- **测试步骤**:
  1. 记录消费方依赖的平台版本与 `Cargo.toml` / `package.json` 中的版本约束。
  2. 升级平台到次要版本，不改任何业务代码。
  3. 执行消费方的构建、单元/集成测试与 e2e；启动并跑一遍主链路（登录 → 列表 → 表单提交 → 审批）。
- **预期结果**:
  1. 消费方构建与测试全部通过（exit code 0），**未修改任何业务文件**（`git diff --stat -- <业务目录>` 为空）。
  2. 主链路功能表现与升级前一致（列表能加载、表单能提交、审批能流转、权限判定正确）。
  3. 平台版本约束允许该小版本自动解析到新版，无需消费方改版本号。
  4. 若升级确实需要消费方改动（例如 API 行为变更），则该变更**不得**出现在小版本中——须记录为缺陷。
- **类型**: 可维护性
- **优先级**: P0
- **自动化**: 半自动
- **设计方法**: 版本兼容回归 + 零改动断言

### TC-H-004: 破坏性变更通过版本化 API 与弃用头提前通知
- **关联 AC**: AC-030
- **前置条件**:
  - 底座已存在版本化 API（如 `/api/v1/...`）；存在一个将被废弃的接口 `/api/v1/order/invoice/legacy`。
  - 已配置弃用策略：`Deprecation` 头 + `Sunset` 头（RFC 8594）。
- **测试步骤**:
  1. 调用 `/api/v1/order/invoice/legacy`，检查响应头。
  2. 查询底座的 API 文档 / 弃用清单，确认该接口已标注。
  3. 消费方分别通过 v1 与 v2 路径访问同一资源，对比行为。
- **预期结果**:
  1. 响应含 `Deprecation: <日期或 true>` 头与 `Sunset: <HTTP 日期>` 头（Sunset 时间点在当前日期之后，给出明确下线期限）。
  2. 弃用清单/接口文档中能查到该接口的弃用说明与替代接口（指向 v2 或新字段）。
  3. v1 与 v2 路径并存期间，v1 行为保持兼容（不破坏现有消费方），且 v1 响应中携带弃用提示。
  4. 弃用策略在代码/文档中成对出现（`Deprecation` 与 `Sunset` 同时存在），不出现只发其一的情况。
- **类型**: 可维护性
- **优先级**: P1
- **自动化**: 可自动化
- **设计方法**: 协议头断言 + 边界（并存期兼容）
