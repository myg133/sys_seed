# D. 前端底座 —— 测试用例（AC-016 ~ AC-019）

- **需求**: REQ-001 通用项目底座（Base Platform）
- **来源**: [acceptance.md](../acceptance.md) §D、[demand.md](../demand.md) §D（SDK 分包表）、[ADR-0001](../../decisions/ADR-0001-底座技术架构基线.md) D4 / D5
- **用例数**: 8（TC-D-001 ~ TC-D-008）
- **公共夹具**: 见 [index.md](index.md) §3 测试夹具

## D.0 本域约定

- SDK 包名沿用 demand.md §D1：`@base/ui`、`@base/sdk`、`@base/auth`、`@base/schema`、`@base/theme`、`@base/i18n`、`@base/hooks`。
- 构建工具：Vite + Bun（包管理/脚本），前端为 pnpm/Bun workspace monorepo，底座壳在 `apps/`，SDK 各包在 `packages/`。
- 类型生成命令：`bun run typegen`（OpenAPI → TypeScript 类型），底层可由 `openapi-typescript` / `orval` 实现。
- 权限组件与路由守卫：`<Can perm="order:invoice:approve">`，守卫失败跳 `/403`。
- 通用渲染器：`@base/schema` 提供的 `SchemaTable` / `SchemaForm`（名称为本用例集约定，实现前需与 Dev 对齐）。

### TC-D-001: 生产产物不含未引入的 SDK 包
- **关联 AC**: AC-016
- **前置条件**:
  - 业务前端只引入 `@base/sdk` + `@base/auth` 两个包。
  - 构建以生产模式执行，产物目录已知（`dist/`）。
- **测试步骤**:
  1. 执行生产构建，产出 `dist/`。
  2. 检索产物（JS chunk、CSS、source map、依赖清单）中是否出现未引入包的标识：`@base/ui`、`@base/schema`、`@base/theme`、`@base/i18n`、`@base/hooks`，以及图表库（ECharts）、富文本编辑器、i18n runtime 的特征字符串。
  3. 用产物分析工具（如 `bunx vite-bundle-visualizer` 或等价方案）列出产物依赖树。
- **预期结果**:
  1. 构建成功（exit code 0），产物可加载。
  2. 产物中**不存在** `@base/ui`、`@base/schema`、`@base/i18n`、图表库与富文本编辑器的代码/资源；命中数为 0。
  3. 产物依赖树中仅含实际引入的 `@base/sdk`、`@base/auth` 及其必要依赖；各 chunk 体积不超过约定预算（若未定义预算，此项只记录实测值不判失败）。
- **类型**: 功能 / 性能
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 等价类（已引入 / 未引入包）+ 产物静态检查

### TC-D-002: 引入的包不产生全局副作用
- **关联 AC**: AC-016
- **前置条件**:
  - 业务前端仅引入 `@base/sdk` + `@base/auth`；已准备一个只渲染业务自身样式的页面 `/probe`。
- **测试步骤**:
  1. 打开 `/probe`，用浏览器 devtools 检查全局 `document` / `window` 上的属性与注入的 `<style>` / `<link>` 标签。
  2. 统计 `body > style`、`<head>` 中非业务自有样式表的数量与作用范围（是否带 `:global` / 全局选择器）。
  3. 检查 `@base/auth` 是否在模块加载时发起登录态请求或改写既有元素的默认行为。
- **预期结果**:
  1. 除平台明确声明的全局（如主题令牌 CSS 变量）外，不存在 SDK 注入的全局变量；注入项数量与声明清单一致，无多余。
  2. 不存在会覆盖业务默认样式的全局选择器；`/probe` 的业务元素样式不被 SDK 改写（对比引入前后 computed style 差异为 0 或仅限声明的令牌变量）。
  3. SDK 加载不产生未经用户操作的登录跳转或请求；请求仅发生在显式调用时。
- **类型**: 功能 / 可维护性
- **优先级**: P1
- **自动化**: 半自动
- **设计方法**: 副作用检测 + 边界（引入前后对比）

### TC-D-003: 无权限时受控按钮不渲染
- **关联 AC**: AC-017
- **前置条件**:
  - 账号 `staff@example.com` 绑定角色 `member`，**不含** `order:invoice:delete`。
  - 页面 `/order/invoice` 含删除按钮，实现为 `<Can perm="order:invoice:delete">`。
- **测试步骤**:
  1. 以 `staff@example.com` 登录，打开 `/order/invoice`。
  2. 在页面 DOM 中检索删除按钮（`data-testid="invoice-delete"` 或等价选择器）。
  3. 以 `boss@example.com`（含 `order:invoice:approve` 与删除权限的角色）登录后重复步骤 1~2 作对照。
- **预期结果**:
  1. 步骤 2 中 `staff` 的 DOM 里删除按钮节点数为 0（不是「渲染但 disabled」，是**不渲染**）。
  2. 页面其余元素正常渲染，无空白报错，浏览器控制台无权限相关异常。
  3. `boss` 登录后删除按钮节点数为 1 且可点击 —— 证明按钮的显隐由权限驱动而非页面缺陷。
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 等价类（有权限 / 无权限）+ 攻击面枚举

### TC-D-004: 直接访问受保护 URL 被路由守卫拦截到 403 页
- **关联 AC**: AC-017
- **前置条件**:
  - 账号 `staff@example.com` 绑定角色 `member`，**不含** `order:invoice:delete`。
  - 存在受该权限保护的路由 `/order/invoice/delete`（或等价需要 `order:invoice:delete` 的操作路由）。
- **测试步骤**:
  1. 以 `staff@example.com` 登录，在地址栏直接输入 `/order/invoice/delete` 回车。
  2. 观察最终 URL、页面内容与网络请求。
  3. 用 `boss@example.com` 重复步骤 1 作对照。
- **预期结果**:
  1. `staff` 被守卫拦截，最终跳转到 `/403`，页面显示 403 提示，**不渲染**删除功能页面主体。
  2. 若路由在渲染前即取不到权限，守卫不应通过「先渲染再隐藏」实现（页面主体内容不出现）。
  3. `boss` 可正常进入该路由且功能可用。
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 攻击面枚举（直接输入 URL）+ 等价类

### TC-D-005: schema 驱动的通用渲染器完成零代码 CRUD
- **关联 AC**: AC-018
- **前置条件**:
  - 后端提供一份列表 + 表单元数据描述（`GET /api/meta/invoice` 返回字段、类型、校验规则、分页与排序配置）。
  - 前端仅提供通用渲染器接入（`@base/schema`），**不写**任何发票专属组件。
- **测试步骤**:
  1. 打开由元数据驱动的发票列表页。
  2. 执行查询、分页（翻到第 2 页）、排序（按金额倒序）、新建表单提交（含一条必填缺失与一条格式非法的输入）。
  3. 执行编辑、删除，并在删除后重新查询。
- **预期结果**:
  1. 列表页正常渲染列、行、分页控件，数据来自后端接口。
  2. 翻页/排序请求参数正确传到后端（`page` / `page_size` / `sort`），返回对应数据；必填缺失与格式非法时表单在**前端**给出具体字段级错误提示且不提交。
  3. 新建/编辑/删除均返回成功，列表刷新后反映最新数据；删除后该行不再出现在列表中。
  4. 该页面前端业务代码量为 0（仅一行渲染器调用 + 元数据引用）。
- **类型**: 功能
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 端到端链路 + 异常路径（校验失败）

### TC-D-006: 新增同类页面无需新增前端代码
- **关联 AC**: AC-018
- **前置条件**:
  - 已有发票（invoice）元数据与通用渲染器；后端新增一份「付款单（payment）」元数据 `GET /api/meta/payment`，字段结构与 invoice 同类（列表 + 表单）。
- **测试步骤**:
  1. 仅新增后端元数据与一条路由注册（指向同一渲染器），不编写任何付款单专属前端组件。
  2. 打开 `/order/payment` 页面。
  3. 执行一次查询与一次新建。
- **预期结果**:
  1. 页面正常渲染付款单列、表单与校验，与发票页复用同一套渲染器。
  2. 查询与新建均成功，无前端专属代码介入。
  3. 本次新增的前端业务代码行数为 0（仅路由/元数据声明），证明「新增同类页面无需新增前端代码」。
- **类型**: 功能 / 可维护性
- **优先级**: P0
- **自动化**: 半自动
- **设计方法**: 等价类扩展 + 代码量断言

### TC-D-007: 后端改字段后类型生成命令同步 SDK 类型
- **关联 AC**: AC-019
- **前置条件**:
  - 后端接口 `GET /api/order/invoice` 响应中字段 `amount` 类型由 `number` 改为 `string`，并新增字段 `currency: string`；OpenAPI 文档随代码生成。
- **测试步骤**:
  1. 在后端修改字段定义并重新生成 OpenAPI。
  2. 在前端执行 `bun run typegen`。
  3. 检查生成文件（`packages/sdk/src/generated/` 或等价目录）中 `amount` 与 `currency` 的类型声明。
- **预期结果**:
  1. 类型生成命令执行成功（exit code 0）。
  2. 生成文件中 `amount` 类型为 `string`，且新增 `currency: string`；生成物与 OpenAPI 一致。
  3. 生成过程无「手工编辑生成目录」提示（生成目录被标记为只读/自动生成）。
- **类型**: 功能
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 正常路径 + 一致性断言

### TC-D-008: 前后端类型不匹配在编译期报错
- **关联 AC**: AC-019
- **前置条件**:
  - 已完成 TC-D-007 的类型同步；前端某处代码把 `amount` 当作 `number` 使用（如 `amount.toFixed(2)`）。
- **测试步骤**:
  1. 在前端源码中新增/保留一处类型不匹配的使用点。
  2. 执行前端类型检查与构建命令（`bun run typecheck`、`bun run build`）。
  3. 记录退出码与错误信息。
- **预期结果**:
  1. 类型检查命令退出码 ≠ 0，错误信息定位到具体文件与行号，并明确指出 `amount` 类型不匹配（`string` vs `number`）。
  2. 构建命令同样失败，**不产出**可发布产物（或产物中不含该错误代码路径）。
  3. 错误信息可读，不出现 `any` 逃逸导致的静默通过（类型定义中该字段不得为 `any`）。
- **类型**: 功能
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 异常路径（故意注入不匹配）
