# 需求：通用项目底座（Base Platform）

- **需求编号**: REQ-001
- **优先级**: P0
- **状态**: 草稿
- **技术栈**: Rust (Axum + sqlx) + Bun + Svelte 5
- **决策记录**: [ADR-0001](../../decisions/ADR-0001-底座技术架构基线.md)
- **更新时间**: 2026-11-17 23:30

## 需求描述

提供一套"装上就能开发业务"的通用管理系统底座。新业务系统的开发成本降到只剩：领域模型、业务接口、业务页面三件事，**不重复造**用户体系、权限体系、租户隔离、通知、审计、文件、流程这些通用轮子。

底座自身用 Rust + Bun + Svelte 5 实现，同时向前后端暴露**可插拔扩展点**，让业务方在其上叠加自己的领域能力，而不是 fork 底座。

### 核心目标

> 全新业务系统从零到可用：**只写业务，不写通用功能**。

**并且二次开发友好**：业务方的代码物理隔离在平台核心之外，平台升级不破坏业务；
AI 辅助开发能直接产出符合平台约定的代码，而不是让 AI 把底座已有的东西重写一遍。

### 范围边界

| | 内容 |
|---|---|
| **在范围内** | 平台自身能力、前端 SDK、扩展机制、交付与运维基线 |
| **不在范围内** | 具体业务系统（作为底座的第一个消费方，另开 REQ 验证底座可用性） |

## 功能要求

标注 `【原】` 为用户原始需求，`【补】` 为补充建议。

---

### A. 身份与访问

**A1. RBAC 权限 `【原1】`**

- 用户 / 角色 / 权限三层模型；权限点命名规范 `module:resource:action`（如 `order:invoice:approve`）
- 角色继承角色；权限支持通配（`order:*`）
- `【补】` **数据权限（数据范围）**：全部 / 本组织 / 本组织及下级 / 仅本人 / 自定义过滤条件
- `【补】` **属性级校验（RBAC + ABAC 混合）**：权限点可携带条件（"金额 < 1 万才可审批"）
- `【补】` **权限点注册表**：应用在 manifest 中声明自己的权限点，平台统一纳管；前端 SDK 自动生成 `can()` 判定与 UI 显隐，业务方零手工维护
- `【补】` **权限申请 / 审批流**：用户可申请权限，走审批后生效
- `【补】` 权限变更全量审计

**A2. 注册 / 邀请 / 配置开关 `【原2】`**

- 注册开关、邀请开关、强制邀请制（全局 / 租户级可配）
- 邀请链接：有效期、使用次数上限、失效、批量生成与导出
- `【补】` **注册策略细分**：邮箱域名白名单（只允许企业邮箱）、邮箱/手机验证码、审批制注册
- `【补】` **密码策略**：长度 / 复杂度 / 有效期 / 历史不重复；密码找回与重置；首次登录强制改密

**A3. SSO 多协议适配 `【原3】`**

- 入站（底座作为 SP）：SAML 2.0、OIDC / OAuth2、LDAP / AD、CAS
- `【补】` **出站（底座作为 IdP / OAuth2 Provider）**：底座自己签发令牌给第三方应用 —— 这是"应用接入"能否成立的前提，见 E2
- `【补】` **免登跳转**：应用间携带令牌直接跳转，不重复登录
- `【补】` **强制 SSO 策略**：租户可禁用本地密码登录
- `【补】` **单点登出**：全局登出 / 按应用登出

**A4. 认证凭证与安全基线 `【补】`**

- Access / Refresh Token 分离与轮换、撤销列表、登出全端失效
- 设备会话管理：查看登录设备、单设备下线、全局下线
- MFA：TOTP + WebAuthn
- 登录失败限流与账号锁定、图形 / 短信验证码
- JWT 签名密钥轮换（kid + JWKS 发布）

### B. 组织与租户

**B1. 用户、组织架构同步 `【原4】`**

- 组织树（公司 / 部门 / 小组）、岗位、汇报关系；组织变更实时生效
- `【补】` **同步协议**：出站 SCIM 2.0（把底座组织推给第三方）、入站 LDAP / AD 定时拉取、增量 + 全量对账
- `【补】` **冲突处理策略**：底座为准 / 外部为准 / 进人工待处理队列
- `【补】` 离职自动禁用账号；组织变更事件推送给受影响用户

**B2. 多租户 `【原7】`**

- 租户开通 / 停用、租户级配置、租户级品牌（logo / 主题色 / 登录页）
- `【补】` **隔离级别可配**：共享表 + `tenant_id`（默认）/ 独立 schema / 独立库。
  **隔离级别决定 DAO 层写法，必须在写第一行业务代码前定死**（见 ADR-0001-D2）
- `【补】` **租户上下文传播**：请求头 + 解析中间件，全链路（DB / 缓存 / 消息 / 日志）自动携带
- `【补】` **跨租户运营后台**：平台管理员视角 —— 租户开通、套餐、配额、用量监控
- `【补】` **配额与限流**：存储空间、API 调用次数、并发数

### C. 配置与品牌

**C1. 基础系统配置、产品配置 `【原5】`**

- 系统参数（键值对，带类型、默认值、作用域：平台 / 租户 / 空间）
- `【补】` **配置分层与覆盖优先级**：平台默认 → 租户覆盖 → 空间覆盖，带缓存与失效机制
- 产品配置：Logo、产品图标、favicon、登录页背景、页脚、版权
- `【补】` **前端主题令牌（design token）**：主色、圆角、字体、组件密度、深浅色模式，运行时可下发
- `【补】` **功能开关 / Feature Flag**：平台级、租户级、灰度按比例

### D. 前端底座

**D1. 标准 UI + 前端基础 SDK `【原6】`**

- 组件库：表格、表单、树、穿梭、图表、上传、编辑器、弹窗、布局
- `【补】` **SDK 不只是组件集，要拆包**，让业务方按需引入：

  | 包 | 职责 |
  |---|---|
  | `@base/ui` | 组件库 |
  | `@base/sdk` | 类型安全 API client（自动刷新 token、错误拦截、幂等键注入） |
  | `@base/auth` | 登录态、当前用户、权限判定 `can()`、路由守卫 |
  | `@base/schema` | schema 驱动的动态表单 / 列表渲染（对接后端元数据） |
  | `@base/theme` | 设计令牌、暗色模式 |
  | `@base/i18n` | 多语言 |
  | `@base/hooks` | 通用 hooks（分页、表格状态、SSE / WebSocket、剪贴板） |

- `【补】` **权限组件与指令**：`<Can perm="order:invoice:approve">` + 路由级守卫
- `【补】` **布局框架**：侧边栏、面包屑、多标签页、租户 / 空间切换器、全局搜索
- `【补】` **API 类型与后端同步**：OpenAPI → 类型生成，前后端契约不漂移
- `【补】` **质量基建**：Storybook 组件文档 + 视觉回归、Vitest 单测、Playwright E2E、MSW Mock

### E. 应用接入与扩展

**E1. 空间 / 项目可扩展 `【原8】`**

- 空间 / 项目作为资源容器：成员、角色、权限、设置、生命周期
- `【补】` **空间与租户是两个正交维度**：租户 = 商务与数据隔离边界；空间 = 组织与协作边界。
  权限模型要同时支持两者，不要混为一谈
- `【补】` 空间级配额、资源路由、归档与删除

**E2. 应用接入 `【原9】`**

- 应用注册表：`app_id` / `secret`、类型（单点登录应用 / 数据接口应用 / 嵌入式应用）、回调地址、令牌有效期
- 授权模式：授权码 + PKCE、Client Credentials、Device Code；令牌校验（JWKS / introspect）
- `【补】` **应用级权限声明 + 用户授权同意页**，授权记录可审计、可撤销
- `【补】` **扩展点机制**：
  - 后端 —— Rust trait + 编译期注册插件
  - 前端 —— 路由 / 菜单 / 组件插槽
  - 运行期可配置的部分走配置，**不要用插件**（插件难测试、难回滚）
- `【补】` **工作台 / 应用市场**：统一入口、常用应用、最近访问
- `【补】` **微前端接入预留**：应用可独立构建部署、运行时加载；单体模式下先不用

### F. 平台运维与治理 `【补】`

> 这一整块原始需求没有列出，但通用管理系统基本都离不开，缺了就等于业务方还要自己再造一遍。

**F1. 审计日志**
- 全量操作留痕（谁、何时、对什么、做了什么、从哪来），按租户 / 空间隔离
- 登录审计（成功 / 失败、IP、设备）
- `【补】` 不可篡改（append-only + 哈希链）、保留策略与归档、审计查询界面

**F2. 通知系统**
- 站内信 + 邮件 + 短信 + Webhook + IM（钉钉 / 企微 / 飞书）
- `【补】` 模板引擎 + 变量 + 多语言、用户订阅偏好、异步投递 + 重试 + 死信

**F3. 工作流 / 审批引擎** —— ❌ **已取消（D121，2026-11-19 用户裁定）**

> **本节整体不再实施。** 它是 BA 的 `【补】` 条目，用户从未单独确认过
> （原话无工作流，见 [decisions.md](decisions.md) D121 的核对口径）。
> 取消的是「通用流程引擎」；底座保留 `WorkflowHandler` 扩展点
> （`platform-core/src/extension/workflow.rs`），业务方自行实现即可。
> 以下内容仅作历史留档。

- 通用管理系统几乎必有（请假 / 报销 / 审批）
- 流程定义、节点、条件分支、会签 / 或签、抄送、超时升级、撤回
- `【补】` 与权限、通知、审计打通；流程实例可查询可追溯

**F4. 文件 / 对象存储**
- 上传下载、预签名 URL、分片、断点续传、图片处理、病毒扫描钩子
- `【补】` 存储抽象层（S3 / MinIO / OSS / 本地），统一 API

**F5. 数据字典 / 元数据 / 编码规则**
- 字典项管理、系统参数、流水号编码规则生成器（前缀 + 日期 + 序号）
- `【补】` **元数据驱动**：表单 / 列表 / 校验规则由后端元数据描述，前端通用渲染器渲染。
  **这是"快速开发"最大的杠杆** —— 标准 CRUD 页面可以做到零前端代码

**F6. 任务与调度**
- 异步任务队列 + worker、定时任务（cron）+ 管理界面、重试退避、任务幂等
- `【补】` 任务进度可查（大批量导入导出依赖它）

**F7. 导入导出**
- Excel / CSV 模板下载、异步导入导出、错误行回执、导入预览与校验

**F8. 报表与仪表盘**
- 可视化配置（拖拽维度 / 指标 / 图表）、定时报表推送

**F9. 可观测性**
- 结构化日志 + `trace_id` 贯穿请求 / 日志 / 消息、OpenTelemetry 指标与链路、健康 / 就绪探针、错误上报

**F10. API 治理**
- 版本化、统一错误格式（RFC 9457）、分页 / 排序 / 过滤规范、幂等键
- `【补】` 限流三级（租户 / 用户 / 接口）、OpenAPI 自动生成、弃用策略（`Deprecation` / `Sunset` 头）

**F11. 交付基线**
- Dockerfile + docker-compose 一键起（开发 / 私有化部署）、Helm / K8s 清单
- `【补】` 环境配置外置（配置与代码分离）、数据库迁移进 CI、蓝绿 / 金丝雀、备份恢复脚本
- `【补】` CI 模板（lint / test / build / scan）+ 依赖漏洞扫描（`cargo audit` / `npm audit`）

**F12. 国际化**
- 多语言、多时区、多币种；前后端文案一致

### G. 二次开发体验与 AI 辅助开发 `【补】`

> A~F 解决「有没有」，G 解决「业务方用起来顺不顺」。
> 这一块直接决定底座好不好用，也是与「框架脚手架」拉开差距的地方。

**G1. 业务模块物理隔离与可插拔**

- 依赖方向单向：**平台 → 扩展点(trait) ← 业务模块**。平台代码永不依赖业务模块
- 业务模块标准目录 `modules/<name>/`，自包含：
  ```text
  modules/order/
  ├── manifest.json     # 模块元信息：权限点、菜单、依赖、路由、配置项
  ├── backend/          # Rust 模块（实现平台 trait）
  ├── frontend/         # Svelte 模块（路由 + 页面）
  ├── migrations/       # 本模块的数据库迁移
  ├── AGENTS.md         # 模块级 AI 引导（见 G3）
  └── README.md         # 人读的开发说明
  ```
- 编译期注册 + 运行时装载；模块**有启停开关**，未启用模块不加载
- `【补】` **裁剪能力**：未被使用的模块（工作流 / 多租户 / 报表）可在构建期剔除，产出更小的单体
- `【补】` **标准范例**：平台自带 `sandbox` 演示模块，作为二次开发的参照实现

**G2. 扩展点契约的稳定性与可测性**

- 扩展点 API 语义化版本 + **向后兼容承诺**：平台小版本升级不得破坏既有扩展点
- 平台提供**扩展点契约测试套件**，业务模块跑同一套测试即验证合规
- 每个扩展点必须有：trait 签名文档 + 最小可运行示例 + 常见错误清单
- `【补】` 平台核心（`crates/platform-core/`）的变更需显式标记，CI 拦截业务模块对其直接修改

**G3. AI 开发引导文件与提示词库**

- **三层引导体系**：
  | 层级 | 位置 | 作用 |
  |---|---|---|
  | 仓库级 | `AGENTS.md` | 全局架构约定、编码规范、可用命令、**禁止事项**（如不得直接改平台核心） |
  | 模块级 | `modules/<name>/AGENTS.md` | 模块上下文：领域模型、涉及哪些扩展点、如何验证 |
  | 提示词库 | `prompts/*.md` | 按任务成套的提示词模板 |
- **提示词库**按任务成套给出，不是零散片段：
  - 新建一个 CRUD 业务模块
  - 新增权限点并接入前端显隐
  - 接入一种新的 SSO 协议
  - 定义一个审批流程
  - 新增通知模板与投递渠道
  - 编写越权测试用例
  - 补测试用例 / 做性能优化
- `【补】` **机器可读的能力索引** `capabilities/`：AI 必须知道底座已有什么，否则它会重写一遍
  - 权限点清单（所有模块 manifest 汇总）
  - 扩展点 trait 签名清单
  - 元数据 schema 的 JSON Schema
  - SDK 各包的导出与用法示例
  - OpenAPI 接口清单
- `【补】` **脚手架**：`create-module` 生成标准目录 + manifest 模板 + AGENTS.md 骨架 + 契约测试接入
- `【补】` **AI 生成代码的护栏**：AI 产出必须过与人工代码同一套 CI（lint / test / 契约检查）；
  平台核心的修改在 PR 中单独标记并强制人工评审

**G4. 开发环境与脚手架**

- 一条命令起全栈（前端 + 后端 + PostgreSQL + Redis + 种子数据）
- `create-module` / `create-permission` / `create-workflow` / `create-notification` 等脚手架
- 本地 mock 与可重置的种子数据
- 依赖预置：业务方无需自行安装 Rust toolchain / pnpm / PostgreSQL

## 非功能要求

| 维度 | 要求 |
|---|---|
| 性能 | 列表接口 P95 < 300ms（万级数据分页）；认证接口 P95 < 100ms |
| 安全 | OWASP Top 10 基线；密码与密钥不入代码、不入日志；越权用例全覆盖 |
| 可用性 | 核心服务 99.9%；支持单实例私有化部署 |
| 可维护 | 模块边界清晰；新增业务模块**不修改平台核心**（扩展点约束） |
| 二次开发 | 标准 CRUD 模块业务代码 **< 500 行**；对平台核心修改 **0 次**；平台同大版本升级导致业务需改动 **0 次**；新工程师 **1 天**跑起环境、**1 周**交付首个模块 |
| 兼容 | PostgreSQL 14+（主数据库）；前端支持 Chrome / Edge / Safari 最近两个大版本 |
