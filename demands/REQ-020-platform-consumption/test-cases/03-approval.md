# 用例：审批流状态机与横切

> 覆盖 **AC-S-189**
> 用例编号：TC-020-019 ~ TC-020-026（8 条）
> **rev 2**：计数表（M5）、错误码写死（N3）、非法流转补 `decide`（N2）、通知落库走 D354

⚠️ **本文件的全部用例必须通过 HTTP 端点驱动**，不得直接调 service 函数（§9.15）。
每条的判据都必须能指到某个测试函数里的 `assert!`。

## 计数表（全文件共用，解决 M5）

| # | 事件 | 审计 | 通知 | 收件人 |
|---|---|---|---|---|
| 1 | 建单（`draft`） | **1** | 0 | — |
| 2 | 提交（`→ pending`） | **1** | **1** | 审批人 B |
| 3 | 审批通过（`→ approved`） | **1** | **1** | 申请人 A |
| 4 | 驳回（`→ rejected`） | **1** | **1** | 申请人 A |
| 5 | 非法流转 | **0** | **0** | — |

⚠️ **「建单算不算流转」必须写死**：本表规定**算 1 条审计、0 条通知**
（创建是状态初始化，不需要通知任何人）。
rev 1 的 AC 说「每次流转恰好一条」而 TC 说「3 次状态变更 → 3 条审计」，两边矛盾。

## TC-020-019 · AC-S-189 步骤 1 · 建单进入 `draft`

- **层次**: 集成（HTTP + 真库）
- **步骤**:
  1. 以申请人 A 登录；
  2. `POST /api/leave/requests`（起止日期 + 理由）；
  3. 独立 `GET /api/leave/requests` 查列表。
- **期望**:
  - 步骤 2 → **201**，响应体 `status == "draft"`；
  - 步骤 3 → 列表里**能查到**这一条。
  - 审计计数 = **1**（计数表第 1 行）。
- **判据形态**: 状态码 + 字段 + 列表存在性 + 审计计数。
- ⚠️ 步骤 3 是关键：只断言 POST 响应体不能证明真的落库。

---

## TC-020-020 · AC-S-189 步骤 2 · 提交：`draft → pending`

- **层次**: 集成（HTTP + 真库）
- **步骤**:
  1. 建单（`draft`）；
  2. `POST /api/leave/requests/{id}/submit`；
  3. 独立 `GET /api/leave/requests/{id}`。
- **期望**: 步骤 2 → **200**；步骤 3 → `status == "pending"`。
- **判据形态**: 两次独立请求的状态比对。
- ⚠️ 通知断言（计数表第 2 行：给审批人 B 发 1 条）放在 TC-020-025 统一验。

---

## TC-020-021 · AC-S-189 步骤 3 · 审批通过：`pending → approved`

- **层次**: 集成（HTTP + 真库）
- **步骤**:
  1. 提交一单（`pending`）；
  2. 以审批人 B 调 `POST .../decide`，body `{"decision":"approve"}`；
  3. 独立查询。
- **期望**: `status == "approved"`，`decided_by == B`，`decided_at` 非空。
- **判据形态**: 状态 + 两个字段。

---

## TC-020-022 · AC-S-189 步骤 4 · 驳回：`pending → rejected`

- **层次**: 集成（HTTP + 真库）
- **步骤**: 同 TC-020-021，body 改为 `{"decision":"reject"}`。
- **期望**: `status == "rejected"`，`decided_by == B`。
- **判据形态**: 状态断言。

---

## TC-020-023 · AC-S-189 步骤 7 · **非法流转必须被拒，且不写审计**

- **层次**: 集成（HTTP + 真库）
- **步骤**（rev 2 补全，N2：rev 1 只测「再 submit」）:
  1. 造一单并审批通过（`approved`）；
  2. `POST .../submit`（已终态再提交）；
  3. `POST .../decide`（已终态再审批）；
  4. 查该单的审计记录数。
- **期望**:
  - 步骤 2/3 均 → **409**，且 `code == "LEAVE_INVALID_TRANSITION"`
    （⚠️ rev 2 写死具体码，N3：rev 1 只说「明确错误码」，而契约 C6 要求
     稳定的大写下划线码）；
  - 步骤 4：审计记录数与步骤 1 之后**相同**（计数表第 5 行：0 条）。
- **判据形态**: 两个状态码 + 一个错误码字符串 + 审计计数比对。
- ⚠️ **两个判据缺一不可**：
  - 只断言状态码 → 不知道失败是否有副作用；
  - 只断言审计数 → 不知道错误码是否明确。
- ⚠️ 这是 AC-S-189 的**核心安全判据**：若非法流转也写审计，
  审计链会把「未发生的操作」记成发生过 → 审计失真。

## TC-020-024 · AC-S-189 · 每次事件恰好一条审计（计数表逐行）

- **层次**: 集成（HTTP + 真库）
- **步骤**:
  1. 走完整链路：建单 → 提交 → 审批通过（**3 个事件**）；
  2. 查该租户审计链，过滤 `object_id == 该单 id`。
- **期望**: **恰好 3 条**（计数表第 1/2/3 行各 1），`action` 能唯一定位：
  `leave.request.created` / `leave.request.submitted` / `leave.request.approved`。
- **判据形态**: `assert_eq!(records.len(), 3)` + 逐条 action 断言。
- ⚠️ 「恰好 3」而不是「>= 3」：多写审计同样是缺陷（重复留痕）。

## TC-020-025 · AC-S-189 · 每次事件的通知条数与收件人（计数表）

- **层次**: 集成（HTTP + 真库）
- **步骤**:
  1. 走 TC-020-024 的链路；
  2. 查 `platform_notify_delivery` 里与本单相关的记录。
- **期望**（计数表第 1~3 行）:
  - 建单 → **0 条**通知；
  - 提交 → **1 条**，收件人是**审批人 B**；
  - 审批通过 → **1 条**，收件人是**申请人 A**。
- **判据形态**: 按事件分组的计数 + 收件人字段断言。
- ⚠️ 必须查**真实的 `platform_notify_delivery` 表**，不能用内存假 sink（§9.15）。
- ⚠️ **落库路径依赖 D354**：业务调 `NotificationSender::send` →
  平台的 `DbNotificationSender` → `enqueue` → 表。
  若平台没补该适配器，本条**判不了**（这是已登记的 D 类缺口）。

## TC-020-026 · AC-S-189 · **对照：审批人必须持权限点**

- **层次**: 集成（HTTP + 真库，阴性对照）
- **步骤**:
  1. 用**没有** `leave:request:approve` 的普通用户 C 调 decide；
  2. 用审批人 B 调同一个端点。
- **期望**: C → **403** `INSUFFICIENT_PERMISSION`；B → **200**。
- **判据形态**: 两个状态码对比。
- ⚠️ **不能省**：只测 B 能通过，无法证明权限层真的生效
  （可能整个端点没挂 `route_layer`）—— `platform-org` 曾经就是这样
  （QA 实测只读用户 201 Created）。
