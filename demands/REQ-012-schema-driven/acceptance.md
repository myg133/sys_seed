## 本需求自有 AC

### AC-S-076: `manifest.json` 可声明实体 schema，非法则进程起不来
- **前置条件**: 一个业务模块的 `manifest.json`；平台已实现 schema 段解析
- **测试步骤**:
  1. 在该模块的 `manifest.json` 里加 `schema` 段，声明一个实体（含 `label` / `api` / 2~3 个字段）
  2. 启动服务，断言启动成功
  3. **造单条违规**：某字段 `type` 写成不存在的值（如 `"currency"`）→ 启动
  4. **造双条违规**：字段 `type` 非法 **且** 两个字段 `key` 重复 → 启动
  5. **造违规**：`fields` 是空数组 → 启动
  6. **造跨文件违规**：某字段的 `permission` 写一个**未登记**的权限点 → 启动
  7. **造跨文件违规**：`reference` 指向一个**不存在**的实体 → 启动
- **预期结果**:
  - 2 → **启动成功**；`GET /health/live` 返回 **200**（随后 SIGTERM 收尾）
  - 3 → **进程起不来**（退出码非 0），错误信息点名**模块 + 实体 + 字段**，
    且说明「`type` 不在允许的取值里」；**且 `issues.len() == 1`**
    （证明没有误报别的规则）
  - 4 → **进程起不来**，**且 `issues.len() == 2`**（证明是**聚合**校验，
    不是只报第一个）
  - 5 → **进程起不来**，说明「实体的 `fields` 不能为空」
  - 6 → **进程起不来**，点名「权限点 `X` 未登记」
  - 7 → **进程起不来**，点名「`reference` 指向的 `module/entity` 不存在」
- **测试执行方式（两条任选其一）**:

  | 路径 | 做法 | 适用 |
  |---|---|---|
  | **A（进程层）** | `BASE_MANIFEST_ROOT=<临时副本>` + 真库 + `base_app` 连接 → spawn `base serve` → 断言退出码非 0 + stderr 含违规点名 | 需真库 |
  | **B（无库替代）** | `base tenant-policies --check`（它**先解析 manifest 再连库**）→ 断言退出码非 0 | 不需要库 |

- **类型**: 功能
- **为什么 fail-fast 而不是告警**：与 REQ-010 的 config 段同源 ——
  **告警就是静默放行的一种**。元数据错了，前端会渲染出错的表单，
  而这在启动时就能知道
- **校验分两阶段**（rev 2）：
  - **阶段 1（单文件）**：格式、类型、重复 key、非空 —— 每个 manifest 解析时判
  - **阶段 2（全局）**：`permission` 已登记、`reference` 目标存在 ——
    **所有 manifest 加载完后**才能判（跨文件一致性不可能在单文件里判出）
  - 两阶段都失败 → 进程起不来

### AC-S-077: schema 段的 JSON Schema 自描述且收录进能力索引
- **前置条件**: AC-S-076 已实现
- **测试步骤**:
  1. 跑 `cargo xtask capabilities`
  2. 检查 `capabilities/schema/manifest.schema.json` 的 `schema` 段定义
  3. 跑 `cargo xtask capabilities --check`
  4. 检查 `capabilities/schema/entity.schema.json`（**命名钉死**，不许「或等价命名」）
- **预期结果**:
  - 2 → manifest 的 JSON Schema 里**包含** `schema` 属性定义，
    且字段类型枚举与 Rust 实现**完全一致**（不多不少）
  - 3 → **退出 0**（索引与源码一致）
  - 4 → 实体元数据的 JSON Schema **存在且非空**，
    `required` 列出必填的键，`additionalProperties: false`
  - **枚举权威链**：Rust 的 `PermissionType` / 字段类型枚举是**唯一来源**，
    JSON Schema 由 `cargo xtask capabilities` **生成**；**手改 schema 会被下次生成覆盖**
    （生成器会 prune 未注册的产物，所以新文件名必须在生成器里注册）
- **类型**: 可维护性
- **为什么**：JSON Schema 是**第三方/AI 能读到**的唯一契约。
  它和 Rust 实现不一致时，AI 会照着 schema 写出平台拒绝的元数据

### AC-S-078: 元数据读取接口返回该实体的字段描述
- **前置条件**: 某模块声明了实体 `E`（字段 `a`/`b`/`c`）；用户 U1 拥有该模块的读权限点
- **测试步骤**:
  1. `GET /api/schema/<moduleId>/<entityKey>`（带 U1 的令牌）
  2. 断言 HTTP 状态码与响应体形状
  3. 断言字段清单
  4. 请求一个**不存在**的实体
  5. 请求一个**不存在**的模块
  6. 不带令牌请求
- **预期结果**:
  - 1 → **200**
  - 2 → 响应体是对象，含 `entity`（实体键）、`label`、`fields`（数组）；
    每个 field 含 `key` / `label` / `type`；`required` / `permission` 按声明如实出现
    （**未声明时字段可以省略，但不得是 `null`**）
  - 3 → 字段 `key` 的**集合与顺序**等于 manifest 里的声明顺序
  - 4 → **404**，`code = 'SCHEMA_ENTITY_NOT_FOUND'`
  - 5 → **404**，`code = 'SCHEMA_MODULE_NOT_FOUND'`
  - 6 → **401**，`code = 'UNAUTHENTICATED'`
- **类型**: 功能

### AC-S-079: 元数据按权限过滤 —— 无权字段连「存在」都不暴露
- **前置条件**: 实体 `E` 有字段 `a`（无权限要求）、`b`（要求 `demo:secret:read`）；
  用户 U1 **没有** `demo:secret:read`
- **测试步骤**:
  1. U1 请求 `GET /api/schema/<module>/E`
  2. 断言 `fields` 里是否有 `b`
  3. 检查响应体的**结构与键集合**（含注释性字段、`total` 之类的计数字段）
  4. 给 U1 授予 `demo:secret:read`，**下一个请求**再取元数据
- **预期结果**:
  - 2 → `fields` 里**没有** `b`（`fields.map(f=>f.key)` **不含** `'b'`）。
    **不是**「有 `b` 但标记 `hidden: true`」——
    那等于告诉无权限用户「这里有个字段你看不到」，**泄露了字段名**
  - 3 → **结构化判据**（rev 2；**不是**「全文不出现 `b`」—— 那**必然**误报，
    因为 `label` 这个键本身就含字母 `b`）：
    - ① `fields.map(f => f.key)` **深度等于**期望数组（不含被过滤的字段）
    - ② 顶层键集合 `Object.keys(body).sort()` **深度等于**期望集合
      （**不含** `hiddenFields` / `deniedFields` / `total` 等清单或计数）
    - ③ 字段名**作为 JSON 键**不出现（`/"b"\s*:/` 不匹配）——
      注意是「作为**键**不出现」，**不是**「作为子串不出现」
    - ④ 被过滤字段的 `label` 文本**不出现在任何字段的 `label` 值里**
  - 4 → **下一个请求**的 `fields` **包含** `b`（撤销/授予**立即生效**，不靠 TTL）
- **类型**: 安全

### AC-S-080: 字段级权限 —— 序列化器剔除无权字段（数据侧）
- **前置条件**: 同 AC-S-079 的实体与用户；**被测接口钉死为新建的
  `GET /api/sandbox/demo-items`（`demoItem` 实体的列表接口）** ——
  **不改** `GET /api/sandbox/scope-item`（那是 REQ-009 的验收资产，动它即越界）；
  该接口**已改用**平台的序列化入口（`SchemaProjector::project`）
- **测试步骤**:
  1. U1（无 `demo:secret:read`）请求该实体的列表接口
  2. 断言响应里每条记录是否**含** `b` 这个键
  3. 授予权限后，**下一个请求**再取
  4. 断言 `b` 的**值**（有权限时）与数据库里的一致
  5. 断言剔除字段的方式
- **预期结果**:
  - 2 → 每条记录的 JSON 里**没有** `b` 这个键。
    判定：`Object.prototype.hasOwnProperty.call(record, 'b') === false`
    —— **不是** `record.b === null`、**不是** `''`、**不是** `undefined`
    （JSON 序列化会把 `undefined` 的键丢掉，但**别的语言/库不一定**；
    必须断言**键不存在**）
  - 3 → **下一个请求**包含 `b`（立即生效）
  - 4 → 值**等于**库里的值（不是占位、不是掩码后的值）
  - 5 → 无权字段**完全不出现**（不是 `"b": "[REDACTED]"`、
    不是 `"b": null`）—— 掩码值同样泄露「这里有东西」
- **类型**: 安全
- **⚠️ 假绿防护**：断言必须是「**键不存在**」。若只断言 `record.b == null`，
  那么「字段被设为 null」的实现也会过 —— 而那是**不一样的语义**（null 是一个值）

### AC-S-081: 契约 C-6 —— 声明了字段权限却没用序列化器 → 检查失败
- **前置条件**: 平台已提供唯一序列化入口；契约扫描器已实现 C-6
- **测试步骤**:
  1. 在**合规**状态下跑契约检查，断言通过
  2. **造违规 1**：某模块的 manifest 声明字段 `b` 有 `permission`，
     但该模块源码**没有**调用序列化入口 → 跑检查
  3. **造违规 2**：模块源码里有序列化入口的调用，但**只在一个** handler 里
     （声明的实体有 **3 个**返回数据的 handler）→ 跑检查
  4. 恢复合规，再跑
- **预期结果**:
  - 1 → **通过**（退出 0）
  - 2 → **失败**（退出非 0），错误信息点名**模块 + 实体 + 字段**，
    并说明「声明了字段级权限但没有找到序列化入口的调用点」
  - 3 → **通过**（退出 0）—— **判据已选定为「至少一处调用」**（见 design §4.4）。
    > ⚠️ **这条判据是弱的**：它**不能**发现「3 个 handler 只有 1 个调用」。
    > 局限已写进 design §4.4 与本节末尾；这是**有意的取舍** ——
    > 静态判定「哪个 handler 返回哪个实体」需要类型推导，在源码扫描里不可靠，
    > 会误报进而被人关掉；**关掉之后比没有更坏**（有个绿的检查在那儿，
    > 让人以为守住了 —— REQ-009 的 C-5 就是这么吃过的）
  - 4 → 恢复**通过**
- **类型**: 安全
- **为什么需要 C-6**：AC-S-080 的保证**依赖业务模块真的调用**了序列化器。
  没有机械检查，「忘了调」就 = 字段泄露。这与 REQ-009 的 C-5 同源：
  **已声明的东西必须有调用点，否则声明是空话**

### AC-S-082: `SchemaTable` 按元数据渲染列表（分页 / 排序 / 空态）
- **前置条件**: 元数据接口可用；某实体有 ≥ 3 条数据
- **测试步骤**:
  1. 用 `SchemaTable` 渲染该实体（**不写任何业务组件**）
  2. 断言表头
  3. 断言行数据
  4. 触发「下一页」，断言请求与渲染
  5. 数据为空时渲染
  6. 断言空态文案
- **预期结果**:
  - 2 → 表头列的**文本与顺序**等于元数据 `fields` 的 `label` 顺序
  - 3 → 行数等于当前页条数；每格的文本**等于**对应字段格式化后的值：
    - `boolean` → **`是`** / **`否`**
    - `date` → **`YYYY-MM-DD`**（**不做时区换算** —— 库里存什么就显示什么）
    - `number` / `text` / `reference` → 原值文本（`reference` 显示 **id 原值**，见 D105）
    - 空值（`null` / `undefined` / 缺字段）→ **空串**（不是 `undefined` 字样、不是 `null`）
    - **不是**原样打印 JSON
  - 4 → 发出**带游标**的请求（断言请求参数里有上一页返回的 `nextCursor`），
    且渲染出下一页的数据（**不等于**第一页的数据）。
    **响应形状钉死**：`{ items: [...], nextCursor: string | null }`
    （`nextCursor === null` 表示没有下一页，此时「下一页」按钮**禁用**）
  - 5 → 渲染空态（**不渲染**表头 + 0 行的空壳表）
  - 6 → 空态文案**非空**且**不包含** `undefined` / `null` 字样
- **类型**: 功能
- **★ 不复用 `@base/ui` 的 Table**（D106）：`Table.svelte` 恒渲染 `thead`、
  空态渲染一行、分页需要 `total`；而本需求要「空态不渲染空壳表」+
  **游标分页没有 `total`** —— 语义不同。`SchemaTable` 自己渲染。

### AC-S-083: `SchemaForm` 按元数据渲染表单（类型 / 校验 / 错误定位）
- **前置条件**: 元数据里有 `text`（required）/ `number` / `boolean` / `date` / `reference` 各一
- **测试步骤**:
  1. 用 `SchemaForm` 渲染（**不写任何业务组件**）
  2. 断言各字段的控件类型
  3. **留空**必填字段后提交
  4. 断言错误展示
  5. `number` 字段填非数字后提交
  6. 填合法值后提交
- **预期结果**:
  - 2 → `text` → 文本框；`number` → 数字输入；`boolean` → 开关/复选框；
    `date` → 日期选择；
    **`reference` → 只读文本（展示 id 原值）** ——
    本期**不做下拉**（D105：选项接口需要路径/形状/权限/上限/分页/搜索，
    是一整块能力，本轮不做；**降级比「定义了却实现不了」诚实**）
  - 3 → **不发出**提交请求（前端就拦住）
  - 4 → 错误**定位在该字段旁边**（不是页面顶部一条汇总）；
    文案指出「必填」；该字段被标记为无效（可被**无障碍属性**发现，
    如 `aria-invalid="true"` 或 `aria-describedby` 指向错误文本）
  - 5 → 同样**不发出**请求，错误定位在 `number` 字段
  - 6 → 发出**一个**写请求，body 的键**只含**元数据声明的字段
    （不含渲染器的内部状态、不含未声明的键）
- **类型**: 功能

### AC-S-084: 前端按元数据跳过无权字段（不渲染、不提交）
- **前置条件**: 元数据已由后端按权限过滤（AC-S-079）；用户 U1 无权 `b`
- **测试步骤**:
  1. 用 `SchemaTable` / `SchemaForm` 渲染 U1 看到的元数据
  2. 断言表头与表单里是否有 `b` 的 label
  3. 提交一个表单，断言请求 body
  4. 断言 DOM
- **预期结果**:
  - 2 → 表头**不含** `b` 的 label；表单**不含** `b` 的控件
  - 3 → 请求 body **不含** `b` 这个键（不是 `null`、不是空串）
  - 4 → DOM 里**不存在** `b` 的 label 文本（不是 `display:none`）
- **类型**: 安全
- **说明**（rev 2 澄清，回应 QA #24）：
  - **前端不做权限判断** —— 它只是「渲染后端给的元数据」。
    权限过滤的唯一权威是后端（AC-S-079/080）。
  - ⚠️ **本条在逻辑上接近同义反复**：输入已经是过滤后的元数据，
    「渲染器不渲染输入里没有的东西」几乎必然成立。它真正守住的是
    **「渲染器不会自造字段」** —— 例如它不去读 `data` 里存在但元数据里没有的键。
  - **权限的正确性由 AC-S-079（元数据）与 AC-S-080（数据）负责**，不是本条。
  - DOM 断言**必须走 Playwright**（真实浏览器）。本仓前端单测是 jsdom，
    没有完整布局与计算样式 —— 用 jsdom 断言「不可见」会假绿。

### AC-S-085: 新增同类页面无需新增前端代码 ★ 父 AC-018 的核心
- **前置条件**: 已有一个实体 `E1` 通过 `SchemaTable` + `SchemaForm` 渲染并跑通 CRUD
- **测试步骤**:
  1. **记录**当前**源码**的文件清单与每个文件的 sha256：
     `packages/schema/src/**` + `apps/shell/src/**`
     （**不含** `dist/`；`package.json` 不在比对范围 —— 它可能需要为新增能力加依赖）
  2. 在 manifest 里**新增**实体 `E2`（不同字段组合，不写任何前端代码）
  3. 重启服务，访问 `E2` 的页面
  4. 断言 `E1` 与 `E2` 都能正常渲染
  5. 比对步骤 1 记录的前端**源码**哈希
  6. **更强的判据**：`grep` 全部前端源码，断言**不含** `E2` 的实体键
     （说明没有人为 E2 写过任何特化代码）
- **预期结果**:
  - 3 → `E2` 的列表与表单**可用**（渲染、分页、校验、提交均正常）
  - 4 → `E1` **不受影响**（回归）
  - 5 → `packages/schema/src/**` 与 `apps/shell/src/**` 的哈希**未变**
    （rev 2 扩了范围：渲染逻辑在包里，只比 `apps/shell` 会漏）
  - 6 → 前端源码**不含** `E2` 的实体键字符串
- **类型**: 功能
- **这条是父 AC 的原话**：「新增同类页面**无需新增前端代码**」。
  它是本需求存在的**唯一理由** —— 如果新增页面还要写前端，那这个需求没有价值
- **成立的前提**（rev 2，回应 QA #12）：`apps/shell` 的 router 必须支持
  **`:param` 通配**（D104），否则每加实体都要在路由表注册一行 → 就不是零代码

### AC-S-086: 零代码 CRUD 闭环端到端
- **前置条件**: `E1` 已可渲染
- **测试步骤**:
  1. 打开列表页
  2. 点「新建」→ 填表 → 提交
  3. 断言列表出现新记录
  4. 点某行的「编辑」→ 改一个字段 → 提交
  5. 断言列表反映修改
  6. 点「删除」→ 确认
  7. 断言列表不再有该记录
  8. **全程**断言没有发起任何「元数据里未声明」的请求
- **预期结果**:
  - 1 → 渲染出 ≥ 1 行（或空态）
  - 3 → 新记录**出现在列表里**（断言唯一标识，不是「行数 +1」——
    分页边界下行数可能不变）
  - 5 → 该记录的该字段**等于**新值
  - 7 → 该记录**不在**列表里
  - 8 → **请求路径白名单**（rev 2；**不是**「集合 ⊆ 5 个中文名」—— 那不可执行且必然误报，
    因为页面加载就会请求 branding / health / 静态资源）：
    - ① **先记录基线**：页面加载**前**已有的请求（branding、health、assets 等），
      从断言集合里**减去**
    - ② 剩余请求的路径必须匹配 `^/api/(schema|sandbox)(/|$)`，或匹配元数据里
      声明的 `api.list` / `api.create` / `api.update` / `api.delete` 模板
    - ③ **元数据里未声明的路径一个都没有**
- **类型**: 功能

### AC-S-087: 元数据演进不破坏已发布页面（AC-S-018 原意）
- **前置条件**: 渲染器已能正常渲染某个元数据快照 `M1`
- **测试步骤**:
  1. 用 `M1` 渲染（基线）
  2. 构造 `M2`：**新增**一个字段 → 渲染
  3. 构造 `M3`：**删除**一个字段（数据里仍可能带该键）→ 渲染
  4. 构造 `M4`：字段 `type` 是渲染器**不认识**的值（如 `"currency"`）→ 渲染
  5. 构造 `M5`：响应数据里**缺**某个非必填字段（值为 `undefined`）→ 渲染
- **预期结果**:
  - 2 → 渲染成功，新字段正常展示（**向后兼容**：加字段不破坏）
  - 3 → 渲染成功，被删字段**不渲染**；数据里多出来的键**被忽略**（不报错、不渲染成「未知列」）
  - 4 → 渲染**成功**（不崩），该字段**降级为纯文本展示**，
    且**控制台有一条可发现的告警**说明「未知字段类型 `currency`」。
    **不是**整个表格白屏 —— 一个未识别的字段类型不该让整页不可用
  - 5 → 渲染成功，缺失值展示为**空**（不是 `undefined` 字样、不是 `NaN`）
- **类型**: 可维护性
- **响应 AC-S-018 的原文**：「元数据结构变更不影响已发布页面的渲染，向后兼容」
- **⚠️ 步骤 4 与 AC-S-076 不冲突**（rev 2 澄清，回应 QA #22）：
  - **manifest 声明**未知类型 → **启动失败**（AC-S-076 步骤 3）
  - **运行时拿到**未知类型（老前端 + 新后端、或前端缓存了旧元数据）→ **降级渲染**（本条）
  - 两者场景不同：前者是**写入时**的错误，后者是**读取时**的兼容

## 本期不验收（明确排除）

| 项 | 原因 |
|---|---|
| CRUD 代码脚手架（`cargo xtask` 生成后端） | 用户拍板延后：元数据形状没跑通前固化脚手架，返工风险最高 |
| 通用数据接口（平台自动读写任意表） | 与 ADR A7「模块自包含、不共享表」冲突；数据访问仍由业务 `Repository` 承担 |
| 元数据管理界面 | 元数据是**编译期声明**（ADR A5），不是运行时数据 |
| 复杂布局（多列栅格 / 分组 / 条件显隐的复杂表达式） | 业务模块自行实现 |
| 导出 / 导入 / 批量操作 | 见 REQ-018 |
| 字段级权限的**写侧**校验（无权就不能改该字段） | 本期只做**读侧**（不返回）。写侧需要另一套校验，且与 AC-S-080 的序列化器不是同一机制 —— 若要做必须单独立项 |
