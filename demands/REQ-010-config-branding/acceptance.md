## 本需求自有 AC

### AC-S-049: 三层覆盖与 `source` 如实反映命中层级
- **前置条件**: 平台级 `logo` = `A`；租户 T1 覆盖为 `B`；T1 下空间 S1 覆盖为 `C`；
  另有一个键 `title` **只在 manifest 登记了默认值**、三层都没配
- **测试步骤**:
  1. 以「无租户上下文」读 `logo`
  2. 以 T1 读 `logo`
  3. 以 T1 + `X-Space-Id: S1` 读 `logo`
  4. 以 T1 读 `title`
  5. 读一个 manifest 里**完全没登记**的键
- **预期结果**:
  - 1 → `value=A`，`source="platform"`
  - 2 → `value=B`，`source="tenant"`
  - 3 → `value=C`，`source="space"`
  - 4 → `value=<manifest default>`，`source="default"`
    （**新增取值** —— 必须能区分「平台显式配了」与「用默认值」）
  - 5 → **404**
  - 五种 `source` 取值必须**互不混淆**；`source` 与实际命中层级**逐条对应**
- **类型**: 功能

### AC-S-050: 作用域越级写入被拒
- **前置条件**: manifest 里 `conflictStrategy` 登记为 `scope: platform`；
  `logo` 登记为 `scope: space`
- **测试步骤**:
  1. 以租户 T1 写 `conflictStrategy`（租户级）
  2. 以 T1 + S1 写 `conflictStrategy`（空间级）
  3. 以 T1 写 `logo`（租户级）
  4. 以 T1 + S1 写 `logo`（空间级）
- **预期结果**:
  - 1、2 **被拒**（400），错误信息说明该键的**允许作用域**
  - 3、4 成功
  - 登记的 `scope` 等于「**允许覆盖到的最深层**」，往更深层写一律被拒
  - 口径：`scope: platform` 不允许租户/空间覆盖；`scope: tenant` 不允许空间覆盖
- **类型**: 安全

### AC-S-051: 未声明的配置键不得写入，且按登记类型校验
- **前置条件**: manifest 里 `cacheTtlSeconds` 登记为 `type: number`
- **测试步骤**:
  1. 写一个 manifest 里**完全没登记**的键
  2. 给 `cacheTtlSeconds` 写字符串 `"60"`（数字的字符串形式）
  3. 给 `cacheTtlSeconds` 写布尔 `true`
  4. 给 `cacheTtlSeconds` 写数字 `60`
- **预期结果**:
  - 1 → **400**，错误信息点名「该键未在 manifest 登记」
  - 2、3 → **400**，错误信息给出**期望类型与实际类型**
  - 4 → 成功
  - 类型判定基于 **JSON 类型**：字符串 `"60"` **不等于** 数字 `60`；布尔**不是**数字
- **类型**: 功能 / 安全

### AC-S-052: 配置变更在**下一个请求**生效（原 AC-S-015 写实版）
- **前置条件**: 平台级 `logo` = `A` 已被读过一次（缓存已填充）；缓存 TTL 设得足够长（≥ 300s）
- **测试步骤**:
  1. 读 `logo` 确认是 `A`
  2. 把平台级 `logo` 改为 `A2`（**不重启、不清缓存、不等待**）
  3. **立刻**再读 `logo`（间隔 < 1s）
- **预期结果**:
  - 3 → `value=A2` —— **不得**出现「改完仍返回旧值」
  - **生效上界 = 下一个请求**（可判定：第 3 步在 1 秒内完成且返回新值）
  - 用**两个独立的解析器实例**（各自持缓存、共享同一 DB）重复 1~3：
    实例 1 写入后，**实例 2** 下一次读也必须返回 `A2`
    —— 验证失效信号来自**共享的数据库**，不是进程内广播
  - 缓存 TTL 明知很长也不影响结论（说明失效不依赖 TTL 到期）
- **类型**: 功能 / 安全

### AC-S-053: 平台级配置变更使**所有租户**的缓存失效
- **前置条件**: 租户 T1、T2 各自读过平台级 `logo` = `A`（两租户缓存都已填充）
- **测试步骤**:
  1. 修改**平台级** `logo` 为 `A2`
  2. **立刻**以 T1 读 `logo`，再以 T2 读 `logo`
- **预期结果**:
  - 2 → T1 与 T2 **都**返回 `A2`
  - **不得**出现「只失效了改动的那个租户」 —— 平台级变更影响所有租户
  - ⚠️ 这一条专门抓「epoch 只按 `tenant_id` 记」的实现（那样平台级变更会让所有租户读到旧值）
- **类型**: 功能 / 安全

### AC-S-054: 品牌公开接口的白名单是 **fail closed** 的
- **前置条件**: 平台级已配 `logo` / `primaryColor` / `conflictStrategy` / `scimBaseUrl`；
  其中 `logo` / `primaryColor` 在白名单内，`conflictStrategy` / `scimBaseUrl` **不在**；
  另外 S1 下配了一个与平台不同的 `logo`
- **测试步骤**:
  1. **不带任何令牌**请求品牌接口（带 `X-Tenant-Id: T1`）
  2. 不带令牌、**也不带** `X-Tenant-Id`
  3. 不带令牌，但带 `X-Space-Id: S1`
  4. 检查响应体里出现的**全部**键名
- **预期结果**:
  - 1 → **200**（不需要令牌），响应只含白名单键
  - 2 → **200**，返回**平台默认品牌**（不是报错 —— 登录页在不知道租户时也要能渲染）
  - 3 → **200**，但返回的是**租户级/平台级**品牌，**不是** S1 的空间级值
    （未认证请求不带可信空间身份；此接口**忽略**空间级覆盖）
  - 4 → 响应键名**逐条枚举**并核对：`conflictStrategy` / `scimBaseUrl`
    **不得出现**；非白名单键**不返回**（不是报错，是缺失）
- **类型**: 安全

### AC-S-055: 前端无硬编码品牌（父 AC-014 收窄版）
- **前置条件**: 平台级 `title` = `示例平台`、`primaryColor` = `#0055aa`、`favicon` 指到一个路径
- **测试步骤**:
  1. 静态检查：`apps/shell/index.html` 与 `apps/shell/src/**` 里搜硬编码的品牌值
  2. 改平台级 `title` → 刷新页面 → 看浏览器标题
  3. 改平台级 `primaryColor` → 刷新页面 → 看页面主色
- **预期结果**:
  - 1 → **不再有硬编码**：`<title>底座壳</title>` 这类写死的品牌值必须消失，改为运行时从接口取。
    检查方式：**枚举改动前后的源码差异**，并确认源码里
    `title` / `primaryColor` 的**具体值**不再出现（键名出现是正常的，值出现不是）
  - 2 → 浏览器标题变成 `示例平台`
  - 3 → 页面主色变成 `#0055aa`
  - **深色模式 / 组件密度 / 字体栈的完整令牌体系不在本期**（REQ-011）
- **类型**: 功能

### AC-S-056: Feature Flag 按租户隔离
- **前置条件**: 功能 `newInvoice` 对 T1 开启、对 T2 关闭
- **测试步骤**: 1. 以 T1 读该开关 2. 以 T2 读该开关 3. 不带租户上下文读
- **预期结果**:
  - 1 → `enabled=true`，`source="tenant"`（若配在租户级）
  - 2 → `enabled=false`
  - 3 → `enabled=false`（无租户上下文 = 不启用，fail closed）
  - 关闭时返回 **200 + `enabled=false`**（契约 C10），**不是 404**
  - 一个租户的开关**不得**影响另一个租户
- **类型**: 功能 / 安全

### AC-S-057: 灰度判定的确定性、单调性与边界
- **前置条件**: 功能 `beta` 配 `rolloutPercent`；准备 200 个不同用户
- **测试步骤**:
  1. `rolloutPercent=50`，**同一用户连读 10 次**
  2. `rolloutPercent=50`，200 个用户各读 1 次，统计命中数与命中集合
  3. 把 `rolloutPercent` 调成 `60`，再读同样 200 个用户
  4. `rolloutPercent=0` 与 `=100` 各读全部用户
  5. `rolloutPercent=101` 与 `=-1`
- **预期结果**:
  - 1 → 10 次结果**完全一致**（确定性）
  - 2 → 命中率落在合理区间（用例给出宽松上下界，避免偶发失败），
    且**命中集合被记录下来**
  - 3 → 原命中集合**必须仍是新命中集合的子集**（**单调性**：
    调高比例不能让已命中的人掉出去）
  - 4 → `0` = 全部不命中；`100` = 全部命中
  - 5 → **400**
  - ⚠️ 用**两个不同的进程**（或两个独立的解析器实例）对同一批用户判定，
    结果**必须完全相同** —— 专门抓「用了 `RandomState` 之类随机播种的哈希」的实现
- **类型**: 安全 / 功能

### AC-S-058: 无用户身份时灰度 fail closed
- **前置条件**: 功能 `beta` 配 `rolloutPercent=100`（即「全都命中」）
- **测试步骤**: 1. **不带令牌**读该开关 2. 带令牌（有 user id）读该开关
- **预期结果**:
  - 1 → `enabled=false` —— 灰度的判据是「这个**用户**在不在比例里」，
    没有用户身份就**无法成立**，必须 fail closed，**不是**「按比例随机给」
  - 2 → `enabled=true`
  - 边界：`rolloutPercent=100` 也不改变第 1 步的结论 —— 缺的不是比例而是**身份**
- **类型**: 安全

### AC-S-059: 未声明的 flag 不返回 404
- **前置条件**: manifest 里只登记了 `newInvoice`
- **测试步骤**: 读一个**未登记**的 flag 名（例如拼错的 `newinvoce`）
- **预期结果**:
  - 返回 **200 + `enabled=false`**（契约 C10：客户端要能优雅降级）
  - **不是** 404，也**不是** 500
  - 同时**记录一条告警日志**，含该 flag 名（便于发现拼错）—— 日志内容可断言
- **类型**: 功能

### AC-S-060: 配置与开关的写接口必须鉴权
- **前置条件**: 用户 M 是普通用户（只有内置角色 `platform-user`）；用户 A 持有
  `config:entry:write` / `config:flag:write`；用户 P 额外持有 `config:platform:write`
- **测试步骤**:
  1. **以 M** 调 `PUT /api/config/entries`（租户级）
  2. **以 M** 调 `PUT /api/feature-flags/{flag}`
  3. 以 A 写**租户级**配置
  4. 以 A 写**平台级**配置
  5. 以 P 写**平台级**配置
- **预期结果**:
  - 1、2 → **403 `INSUFFICIENT_PERMISSION`**（普通用户不得改配置/开关）
  - 3 → 成功
  - 4 → **403** —— 平台级配置是**跨租户影响**，需要**独立的** `config:platform:write`
    （只有 `config:entry:write` **不够**）
  - 5 → 成功
  - 三个权限点都要在 `crates/platform-config/manifest.json` 登记
- **类型**: 安全

### AC-S-061: 新登记的权限点必须有鉴权调用点
- **前置条件**: 契约 C-5 已生效（`extension-points v2`）
- **测试步骤**: 跑 `cargo test -p sandbox --test contracts` 与平台的契约测试，
  确认 `config:entry:write` / `config:flag:write` / `config:platform:write` 三个权限点
- **预期结果**:
  - 三个权限点**各自**都有对应的 `require_permission(...)` 调用点（逐个核对，不是抽样）
  - 若把其中任一调用点删掉 → C-5 **失败**并指名该权限点
  - 平台 crate 的鉴权现状（`platform-org` 那 9 个点）**不得因本需求而恶化**
- **类型**: 安全 / 可维护性

### AC-S-062: 三表分离与 RLS 兜底，`jsonb` 值列可迁移
- **前置条件**: 三张表已建；应用连接用普通角色 `base_app`
- **测试步骤**:
  1. 以租户 T1 的连接读 `platform_config`（平台级表）
  2. 以租户 T1 的连接试图 **INSERT** 一行 `platform_config`
  3. 以 T1 读 `platform_tenant_config`，同时库里存在 T2 的行
  4. 以 T1 + S1 读 `platform_space_config`，同时库里存在 T1+S2 与 T2+S1 的行
  5. 检查三张表的 `value` 列类型；对 `platform_tenant_config` 执行 down 迁移
- **预期结果**:
  - 1 → 能读到平台级行（全体可见是**设计如此**）
  - 2 → **被拒**（表级权限只授予平台管理角色；**租户连接写不进平台级行**）
    —— 这一条专门防「单表 nullable + RLS `WITH CHECK (tenant_id IS NULL OR ...)`」
    那种写法把平台级写入开给租户
  - 3 → 只看到 T1 的行（RLS 生效）
  - 4 → 只看到 T1+S1 的行（RLS 生效，S2 与他租的行都不可见）
  - 5 → 三张表 `value` 均为 **`jsonb`**；down 迁移能执行成功且**可逆**
    （迁移前空表也要有 down 脚本）
- **类型**: 安全 / 可维护性
