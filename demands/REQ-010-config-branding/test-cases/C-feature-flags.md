# C. Feature Flag 与确定性灰度 —— 测试用例（AC-S-056 ~ AC-S-059）

- **需求**: REQ-010「配置、品牌与 Feature Flag」
- **来源**: [acceptance.md](../acceptance.md) §AC-S-056 ~ AC-S-059、[design-summary.md](../design-summary.md) §4.1 / §5、[api-conventions v2 §C10](../../../contracts/api-conventions/v2.md)
- **用例数**: 12（TC-010-020 ~ TC-010-031）
- **公共夹具**: 见 [index.md](index.md) §3 测试夹具

## C.0 本域约定

- **接口**（design §6）：`GET /api/feature-flags`（批量）、`GET /api/feature-flags/{flag}`（单个）、`PUT /api/feature-flags/{flag}`（改开关，权限点 `config:flag:write`）。读接口**需要令牌**。
- **响应形状**：单条 `{"flag","enabled","source"}`（C10）；批量 `{"flags":[{"flag","enabled","source"}]}`。字段名 `flag`（**不是** `key`），这是 C10 的原文。
- **灰度公式**（C10 v2 §10.2，必须逐字实现）：`bucket = sha256("<flag>:<user_id>")` 前 4 字节按**大端**解释为 `u32`；`enabled = bucket % 100 < rolloutPercent`。
- **flag 名规范化**：本用例集统一使用 **manifest 里登记的原样字符串**（`newInvoice` / `beta`）。C10 的示例写的是 `new-invoice`（kebab），与 C9 的 camelCase 以及 AC-S-056 的 `newInvoice` 不一致 —— 同一逻辑 flag 两种写法会得到**不同 bucket**（见 [index.md](index.md) §8 Q-20）。执行前必须确认实例里登记的**字面量**。
- **`rolloutPercent` 的位置**：manifest 的 `ConfigSpec` **没有**该字段（`code/crates/platform-core/src/extension/manifest.rs:147-162`），而设计说 flag 登记为 `type: boolean`（design §5.3）。本用例集按 §7 A8 假设「flag 的存储值是一个复合对象 `{"enabled":bool,"rolloutPercent":number|null}`，flag 写接口独立校验」—— 这一假设本身是硬伤，见 §8 Q-03。
- **`source` 取值**：flag 的 `source` 语义在 design §5.1（无配置 → `platform`）与 C9 v2 §9.3（用默认值 → `default`）之间**自相矛盾**（§8 Q-19）。本域用例只在「显式写在租户级」时断言 `source == "tenant"`；其余情形只断言 `enabled` 的精确值，并在 TC-010-029 记录该缺口。
- **执行位置**：默认「真实库（`base_test`）+ 真机 HTTP」；**灰度批量**（200 用户）用**单元层**直接调 `ConfigResolver::flag`（造 200 个令牌不现实），单用户用例用 HTTP。

### TC-010-020: flag 按租户隔离；关闭也返回 200 + `enabled=false`；无令牌返回 401
- **关联 AC**: AC-S-056
- **前置条件**:
  - **执行位置**: 真实库 + 真机 HTTP。
  - `newInvoice` 已登记（`type: boolean`，默认 `false`，`scope: tenant`）；T1 租户级 `true`、T2 租户级 `false`（§3.6）。
  - 读 T1 用 `u-2001`（普通用户）；读 T2 用 `u-2005`（T2 的账号 —— 用 T1 令牌 + `X-Tenant-Id: tenant-b` 会 404）。
- **测试步骤**:
  1. `GET /api/feature-flags/newInvoice` + `u-2001` 令牌 + `X-Tenant-Id: tenant-a`
  2. 同请求改带 `u-2005` 令牌 + `X-Tenant-Id: tenant-b`
  3. 同请求，**不带** `Authorization`
  4. A（`u-2002`）把 T1 的 `newInvoice` 改成 `false`，再以 `u-2005` 读 T2，然后把 T1 改回 `true`
- **预期结果**:
  1. **200**；`enabled == true`；`source == "tenant"`。
  2. **200**；`enabled == false`；`source == "tenant"`；**不是** 404（契约 C10）。
  3. **401**；`code == "UNAUTHENTICATED"`。**注意**：AC-S-056 步骤 3 期望「不带租户上下文 → `enabled=false`」，但该路由在 design §6 里标注「需要令牌」，未认证必然 401 —— 该期望只可在单元层验证（见 TC-010-021 与 §8 Q-07）。
  4. 改 T1 后：T2 仍 `false`（不受影响）；T1 读 `false`；改回后 T1 恢复 `true`。
  5. 全程 T1/T2 的取值**互不影响**（一个租户的开关不得改写另一个租户的判定）。
- **类型**: 功能 / 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 判定表（租户 × true/false）+ 跨租对照 + 契约 C10 形状

### TC-010-021: 无用户身份时灰度 fail closed —— 攻击者不得靠「没有身份」拿到 true
- **关联 AC**: AC-S-058
- **前置条件**:
  - **执行位置**: 真实库 + 真机 HTTP + 单元层。
  - `beta` 已登记；`rolloutPercent = 100`（「全都命中」的极端值）。
- **测试步骤**:
  1. 不带令牌 `GET /api/feature-flags/beta`
  2. 单元层：`resolver.flag(&RequestContext::new(), "beta")`（无 user、无 tenant）
  3. 单元层：`resolver.flag(&RequestContext::new().with_tenant("tenant-a"), "beta")`（有租户、**无 user**）
  4. 单元层：`resolver.flag(&ctx.with_user("u-3001"), "beta")`（有 user，对照）
- **预期结果**:
  1. **401**；`code == "UNAUTHENTICATED"` —— **不得** 200 + `enabled=true`（未认证请求不得因"没有身份"而走"按比例随机给"）。
  2. `enabled == false`（**不是** `true`，即使 `rolloutPercent = 100`）。
  3. `enabled == false` —— 缺的是**用户身份**，不是租户；有租户不足以让灰度成立。
  4. `enabled == true` —— 有身份 + `p=100` 必须命中（证明第 2/3 步不是"实现永远返回 false"）。
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: fail closed + 边界（`p=100` 不改变结论）+ 正向对照

### TC-010-022: 有身份 + `p=100` → true；`p=0` → false；三档在「有/无身份」下逐一对照
- **关联 AC**: AC-S-058
- **前置条件**:
  - **执行位置**: 真实库 + 单元层（`p` 由测试逐次设置）。
  - 用户 `u-3001`（T1）。
- **测试步骤**:
  1. 以 `ctx(user=u-3001, tenant=tenant-a)`：`p=100` → 读；`p=0` → 读；`p=50` → 读
  2. 以 `ctx(tenant=tenant-a)`（无 user）：同样三档
  3. 以 `ctx()`（无 tenant、无 user）：同样三档
- **预期结果**:
  1. `100 → true`；`0 → false`；`50 → 记录该用户的布尔值`（用于 TC-010-023 的一致性）。
  2. 三档**全部 `false`**。
  3. 三档**全部 `false`**。
  4. 第 1 步的三档**不全相同**（否则说明比例参数没生效）；第 2/3 步三档**全相同**（恒 false）。
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 三档 × 三种身份状态的判定表

### TC-010-023: 确定性：同一用户连读 10 次结果完全一致
- **关联 AC**: AC-S-057
- **前置条件**:
  - **执行位置**: 真实库 + 真机 HTTP（同一实例）。
  - `beta` 的 `p=50`；用户 `u-3001`。
- **测试步骤**:
  1. 用 `u-3001` 的令牌连续 `GET /api/feature-flags/beta` **10 次**（间隔 < 100ms）
  2. 记录每次的 `enabled`
  3. 再连续读 10 次（共 20 次）
- **预期结果**:
  1. 20 次的 `enabled` **完全相同**（全 `true` 或全 `false`）。
  2. 若中途出现翻转（哪怕 1 次），用例判失败 —— 这是"每次请求掷骰子"的判别点。
  3. 20 次响应的 `flag` 字段都等于 `beta`；状态码全 **200**。
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 重复执行（同输入必须同输出）

### TC-010-024: 分布落在合理区间，并记录命中集合
- **关联 AC**: AC-S-057
- **前置条件**:
  - **执行位置**: 真实库 + 单元层（200 个用户逐个判定，无令牌开销）。
  - 用户 `u-3001` ~ `u-3200`（T1，§3.3）；`beta` 的 `p=50`。
- **测试步骤**:
  1. 逐个 `resolver.flag(&ctx(user=u-300i, tenant=tenant-a), "beta")`
  2. 统计命中数 `H50` 与命中集合 `S50`（按 user_id 字典序）
  3. 把 `S50` 的 sha256 指纹写进测试输出（便于比较两次运行）
- **预期结果**:
  1. `70 ≤ H50 ≤ 130`（n=200、p=0.5，±4σ 的宽松界；AC-S-057 未给数值，本用例集按此取值，见 §8 Q-18）。
  2. `H50 ∉ {0, 200}`（既不是全不命中，也不是全命中）。
  3. `S50` 被**逐条记录**（200 个 id 的集合，不是只记数量）；指纹可复现。
  4. 连续跑两次该步骤，`S50` 与指纹**完全相同**。
- **类型**: 功能
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 统计边界 + 可复现集合

### TC-010-025: 单调性：50→60 原命中者不掉出；60→50 反向为子集
- **关联 AC**: AC-S-057
- **前置条件**:
  - **执行位置**: 真实库 + 单元层。
  - 同 TC-010-024 的 200 个用户。
- **测试步骤**:
  1. `p=50` → 记录 `S50`
  2. `p=60` → 记录 `S60`
  3. `p=10` → 记录 `S10`
  4. 再 `p=50` → 记录 `S50'`
- **预期结果**:
  1. `S50 ⊆ S60`（**原命中者必须仍命中**；差集为空）。
  2. `S10 ⊆ S50`（更小的比例是子集）。
  3. `|S10| ≤ |S50| ≤ |S60|`。
  4. `S50' == S50`（把比例改回去，集合必须复原 —— 证明分桶只依赖 `(flag, user)`，不依赖调用顺序/时间）。
  5. 若出现"调高比例后原命中者掉出"，用例判失败（这是"每次重新分配"的判别点）。
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 集合包含关系（正向 + 反向 + 复原）

### TC-010-026: 边界 `p=0` 与 `p=100`
- **关联 AC**: AC-S-057
- **前置条件**:
  - **执行位置**: 真实库 + 单元层。
- **测试步骤**:
  1. `p=0`，对 200 个用户判定
  2. `p=100`，对 200 个用户判定
- **预期结果**:
  1. `p=0` → 命中数 **0**；每个用户的响应仍是 **200 + `enabled=false`**（不是 400/404/空）。
  2. `p=100` → 命中数 **200**（全部命中）。
  3. 两次判定的响应结构与 `p=50` 时**完全一致**（只有 `enabled` 变化）。
- **类型**: 功能
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 边界值（下界 / 上界）

### TC-010-027: 非法比例 `101` / `-1` / 小数：写入被拒；脏数据的读路径 fail closed
- **关联 AC**: AC-S-057
- **前置条件**:
  - **执行位置**: 真实库 + 真机 HTTP + 管理员连接。
  - 写者 P（`u-2003`，含 `config:flag:write`）。
- **测试步骤**:
  1. P：`PUT /api/feature-flags/beta` body `{"enabled":true,"rolloutPercent":101}`
  2. 同 body `rolloutPercent: -1`
  3. 同 body `rolloutPercent: 50.5`
  4. 用**管理员**连接直接把存储值改成 `"rolloutPercent": 101`（模拟脏数据/回滚失败），再以 `u-3001` 读
  5. 恢复 `p=50`
- **预期结果**:
  1. **400**；`code == "CONFIG_VALUE_INVALID"`；`params.range == "0..=100"`；存储值**未被修改**（随后读取仍是原值）。
  2. **400**；同码。
  3. **400**；同码（整数假设：比例是整数百分比，见 §7 A4）。
  4. **200**；`enabled == false`（**fail closed**）—— **不是** 400/500：读它的客户端并没有发送这个非法值；同时产生 **1 条 WARN**，含 `beta` 与「rollout 非法」。
  5. **200**；恢复正常判定。
  6. 判据说明：AC-S-057 步骤 5 只写「400」，未说是写时还是读时。本用例把 **400 固定在写入侧**、读侧 fail closed（见 §8 Q-17）；若 BA 裁定读侧也 400，第 4 步改断言 400，并在契约里写明「读接口可因服务端配置非法返回 400」。
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 边界（0/100 之外）+ 脏数据 fail closed + 写读分离

### TC-010-028: 跨进程/跨实例一致 + 逐用户核对哈希公式
- **关联 AC**: AC-S-057
- **前置条件**:
  - **执行位置**: 真实库 + **两个独立解析器实例**（各自持缓存、共享同一 `base_test`；用于模拟两个进程，同 REQ-009 的 epoch 口径）。
  - `p=50`；用户 `u-3001` ~ `u-3200`。
- **测试步骤**:
  1. 实例 1 对 200 个用户判定 → `S1`
  2. 实例 2 对同一批用户判定 → `S2`
  3. 断言 `S1 == S2`
  4. 对 `u-3001` ~ `u-3005`，在测试代码里**独立**计算：`b = u32::from_be_bytes(sha256("beta:" + user_id)[0..4])`，`expected = b % 100 < 50`
  5. 断言实现返回的 `enabled` 与第 4 步的 `expected` 逐条相等
- **预期结果**:
  1. `S1 == S2`（集合完全相等，与顺序无关）—— **不得**出现"两个实例各命中一半"。
  2. 5 个样本用户与独立公式**逐条一致**。
  3. 独立计算**不得**调用被测实现（不能复用它的哈希函数/桶函数），否则公式抄错也会通过。
  4. 若实现用了 `RandomState` 或其他随机播种哈希，第 1 步或第 2 步必然失败 —— 这是本用例的专门目标。
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 跨实例一致性 + 独立实现比对（抓 `RandomState` / 不同哈希）

### TC-010-029: 未声明的 flag → 200 + `enabled=false` + 一条含 flag 名的 WARN
- **关联 AC**: AC-S-059
- **前置条件**:
  - **执行位置**: 真实库 + 真机 HTTP + 日志捕获（`tracing` 订阅器写入内存缓冲，同 `platform-server` 测试里的 `BufWriter` 做法）。
  - manifest 只登记 `newInvoice` 与 `beta`。
- **测试步骤**:
  1. 以 `u-2001` 读 `GET /api/feature-flags/newinvoce`（拼错一个字母）
  2. 取出捕获到的日志事件
  3. 对照：以 `u-2001` 在 T1 读 `GET /api/feature-flags/newInvoice`
- **预期结果**:
  1. **200**；`enabled == false`；`flag == "newinvoce"`；**不是** 404、**不是** 500。
  2. 恰好 **1 条** `WARN` 事件，其结构化字段 `flag == "newinvoce"`；日志文本不得把它渲染成非法 JSON（字段形式，不是拼字符串）。
  3. 对照读 `newInvoice` → **200 + `enabled=true`**（证明不是"所有 flag 都返回 false"）。
  4. `source` 字段：本用例**只断言字段存在且为字符串**，不断言具体值 —— C9 v2 §9.3 与 design §5.1 对"未声明 flag 的 source"给出不同答案（§8 Q-19）。
- **类型**: 功能
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 正常/异常对照 + 日志结构性断言（AC-S-059 明写"日志内容可断言"）

### TC-010-030: 未声明 flag 名的输入健壮性（日志注入 / 超长 / 特殊字符）
- **关联 AC**: AC-S-059
- **前置条件**:
  - **执行位置**: 真实库 + 真机 HTTP + 日志捕获。
  - 用例性质：**派生** —— AC-S-059 要求"未声明就 200 + 告警"，但没给 flag 名的字符集/长度边界（§8 Q-22）。
- **测试步骤**:
  1. flag 名 = 1024 个 `a`
  2. flag 名 = `"beta\nWARN forged-entry"`
  3. flag 名 = `"../../beta"`
  4. flag 名 = `"%0Abeta"`
  5. 每个请求之后立即再读一次 `newInvoice`（确认进程仍健康）
- **预期结果**:
  1. 四个请求全部 **200** + `enabled=false`（未声明语义）；**不得** 500、**不得** panic。
  2. 日志里 `flag` 是**单个结构化字段值**：格式化后的日志行中**不得**出现由 flag 名带来的裸换行（第 2 个输入不得伪造出第二条日志行）。
  3. 单条日志长度有上限（建议 ≤ 4KB；超长截断并在字段里标明 `truncated=true`），**不得**把 1KB 原文完整拼进日志。
  4. 第 5 步仍返回 **200 + `enabled=true`**（进程未被拖垮/未进入异常状态）。
  5. 结论：`200 + false` 只对「形如 flag 名的字符串」成立；**非法字符/超长名应给 400**（本用例集建议 `^[a-z][a-zA-Z0-9]{0,63}$`），该收紧属 BA 裁定项（§8 Q-22）。
- **类型**: 安全
- **优先级**: P1
- **自动化**: 可自动化
- **设计方法**: 攻击面（日志注入 / 资源耗尽）+ 非法输入边界

### TC-010-031: 空间级不得影响 flag（未校验的 `X-Space-Id` 不能改变行为）
- **关联 AC**: AC-S-056
- **前置条件**:
  - **执行位置**: 真实库 + 真机 HTTP。
  - `beta` 登记为 `scope: tenant`；T1 的 `beta` 为 `false`（或按用例设置）。
  - 写者 A（`u-2002`）。
- **测试步骤**:
  1. A：`PUT /api/feature-flags/beta` body `{"enabled":true}` + `X-Space-Id: space-sales-1`
  2. 读 `beta`：T1（带 `X-Space-Id: space-sales-1`）与 T1（不带空间头）各一次
  3. 用管理员连接查 `platform_space_config` 中 `key='beta'` 的行数
- **预期结果**:
  1. **400**；`code == "CONFIG_SCOPE_FORBIDDEN"`（flag 的允许最深层是 `tenant`；design §4.1 另有一条「Feature Flag 不支持空间级」——两条规则都指向 400，但**具体依据要在错误 `params` 里可区分**，见 §8 Q-34）。
  2. 两次读取结果**完全相同**（`X-Space-Id` 不改变判定）。
  3. `platform_space_config` 中 `key='beta'` 的行数 **0**。
  4. 结论：未校验的 `X-Space-Id` 不得改变开关行为（design §4.1 / R1）。
- **类型**: 安全
- **优先级**: P0
- **自动化**: 可自动化
- **设计方法**: 攻击面（未校验头）+ 库侧证据
