## D1 部署形态：模块化单体

**推荐**：模块化单体（monorepo）

- Rust：一个 crate 树，按领域分 module（`iam` / `rbac` / `tenant` / `org` / `notify` / `audit` / `workflow` / `storage` / `app`），模块间只走内部 trait 边界，不共享数据库表
- 前端：pnpm workspace monorepo（`apps/` 底座壳 + `packages/` SDK 各包）

**理由**

底座的存在意义是「让新业务只写业务代码」。微服务的通信、部署、一致性、联调成本会**直接吃掉**这个收益，而底座本身通常撑不起独立扩容的需求。

**关键约束**：模块边界从第一天就划死（不共享表、不跨模块直接访问对方的 repository）。这样未来真要拆服务，是按已有边界拆，不需要重写。

**备选**

| 方案 | 为什么不选 |
|---|---|
| 一开始就微服务 | 本地开发要起 N 个进程；分布式事务无处安放；排障成本翻倍 |
| 单体但边界不设防 | 半年后必然烂成一坨，届时拆不动 |

## D2 多租户隔离级别 ⛔ 阻塞项

**推荐**：默认 **共享表 + `tenant_id`**，数据库层用 PostgreSQL **Row Level Security** 兜底

三档可配置，向上保留切换能力：

| 档位 | 实现 | 适用 |
|---|---|---|
| L1（默认） | 共享表 + `tenant_id` + RLS | 绝大多数场景，成本最低 |
| L2 | 每租户独立 schema | 中大型客户、合规隔离要求 |
| L3 | 每租户独立库 | 金融/政企，需物理隔离 |

**理由**

RLS 是这里的关键：**即使应用层漏写 `WHERE tenant_id = ?`，数据库层也不会返回别家数据**。这是防呆，不是性能优化。共享表方案里，应用层漏写过滤条件是最高频的越权来源。

**为什么必须最先定**：隔离级别直接决定

- DAO 层写法（是否需要统一的租户上下文注入）
- 缓存 key 是否必须带租户维度
- 消息体是否必须带租户上下文
- 数据库迁移策略（L3 下每租户都要跑迁移）

**备选**

| 方案 | 为什么不选 |
|---|---|
| 只做 L3 独立库 | 运营成本高、迁移复杂、跨租统计难做 |
| 只做 L1 且不用 RLS | 越权风险靠应用层自觉，实测是主要事故来源 |

## D3 认证主体归属：底座自持账号 + SSO 挂载 ⛔ 阻塞项

**推荐**：底座自持用户与账号体系，SSO 作为**可选挂载**

```
本地账号模式（默认）：用户名/邮箱 + 密码，底座是唯一身份源
SSO 挂载模式：外部 IdP 登录 → 自动创建/关联本地账号 → 之后权限完全本地管
混合模式（企业常见）：账号在底座，组织架构来自 LDAP/AD
```

**理由**

底座要提供 RBAC、数据权限、审批流、数据范围 —— 这些都依赖一个**稳定的本地用户主键**。若完全依赖外部 IdP，权限模型会被外部系统的用户模型绑死，外部一次改字段就得跟着改。

同时要支持「组织架构从 LDAP/AD 来、账号在底座」—— 这恰恰是企业客户最常见的诉求，也是你 B1 项「组织架构同步」的真实落点。

**注意**：这不与 D1（出站 OIDC Provider）冲突 —— 底座在 SSO 上既是 SP 也可以是 IdP，两条路都要支持。

## D4 前端形态：单体 SPA + 应用级路由

**推荐**：单体 SPA + 运行时可扩展的应用路由注册表；**预留**微前端接入

**理由**

底座强调 UI 统一（logo、主题、布局、交互），微前端带来的样式隔离、路由冲突、依赖重复、调试复杂度与「统一底座」的目标直接冲突，收益远小于代价。

但「应用接入」要求应用能独立演进 —— 折中做法：

- 应用清单在运行时可扩展（新增应用 = 加一条注册记录 + 一个路由，**不改底座代码**）
- 应用可以独立构建成独立 bundle，底座支持运行时加载
- 先只支持「路由级 + 菜单级」接入，微前端容器（qiankun / wujie 类）留接口不实现

## D5 扩展点机制：编译期 trait 插件 + 运行期配置

**推荐**

| 层 | 机制 |
|---|---|
| 后端 | Rust `trait` + 编译期插件注册（`inventory` / `linkme` 类自动注册） |
| 前端 | schema 驱动渲染器 + 组件插槽 + 路由/菜单注册 |
| 运行期 | 能用配置表达的，一律走配置（不写插件） |

**理由**

运行期动态插件（脚本、热加载模块）带来安全面、调试难、回滚难、性能不可控。编译期插件有类型安全、性能可控、单测友好。

**关键的划分原则**：**「改配置能解决的，不要写插件」**。底座里 80% 的定制需求是元数据 / 配置驱动的（这正是 D 组 schema 渲染器的价值），插件只留给真正要改行为的场景。

## D6 权限引擎：自研 RBAC + 可插拔决策点

**推荐**：自研 RBAC（表驱动）+ 数据范围过滤；预留 OpenFGA / Cedar 适配层

**理由**

需求里的权限模型有三个维度要深度耦合：**租户 × 空间 × 组织架构**。Casbin 用策略文件表达权限很灵活，但映射这三维 + 数据范围（"本组织及下级"）需要自己写数据层和转换层，策略文件与业务代码分家后版本管理会失控。OpenFGA / Cedar 是关系型权限，很强，但要多维护一个服务、多一跳延迟。

务实做法：

- 核心：自研表驱动 RBAC（角色、权限点、数据范围、继承、通配）
- 决策点做成 trait：复杂场景可替换为策略引擎，不影响调用方
- 权限点注册表：应用在 manifest 声明，平台统一纳管（AC-001）

**备选**

| 方案 | 为什么不作为默认 |
|---|---|
| Casbin | 策略文件与租户/空间/数据范围映射成本高，文件版本管理易脱节 |
| OpenFGA / Cedar | 能力强但多一个服务 + 多一跳延迟；建议做成可选适配而非默认 |
