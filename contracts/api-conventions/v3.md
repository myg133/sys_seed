## C1 平台 API 分组前缀（v3 修订）

平台自身能力按前缀分组，与 ADR-0001 D1 的 crate 划分对齐：

| 前缀 | 归属 | 对应子需求 |
|------|------|-----------|
| `/api/iam` | 账号、认证、令牌、会话 | REQ-007 |
| `/api/rbac` | 角色、权限点、数据范围 | REQ-009 |
| `/api/tenant` | 租户、隔离、配额 | REQ-006 |
| `/api/org` | 用户、组织树、岗位、SCIM 同步 | REQ-008 |
| `/api/config` | 系统参数、配置分层、品牌 | REQ-010 |
| `/api/feature-flags` | 功能开关 | REQ-010 |
| `/api/app` | 应用注册表、工作台 | REQ-016 |
| `/api/audit` | 审计查询 | REQ-014 |
| `/api/notify` | 通知模板、投递 | REQ-015 |
| `/api/workflow` | 流程定义与实例 | REQ-017（已取消，前缀保留） |
| `/api/storage` | 文件上传下载 | REQ-018 |
| `/api/tasks` | 异步任务、导入导出 | REQ-018 |
| `/api/meta` | 元数据 schema | REQ-012 |
| **`/api/oauth`** | **OAuth2 授权服务器（IdP 侧）、令牌内省与撤销** | **REQ-022** |

未分配前缀的分组在新增前须先改本契约升版本。

> **另有一个不在 `/api` 下的固定路径**（RFC 8414 规定，不可自定义）：
> `/.well-known/oauth-authorization-server`（授权服务器元数据）。
> 另有 `/.well-known/jwks.json`（REQ-007 已有）。
> 这两个路径属于「**协议规定的发现端点**」，与 C1 的 `/api/*` 分组表**并列**，
> 不占用任何前缀。

### C1.1 授权服务器元数据端点（v3 新增）

`GET /.well-known/oauth-authorization-server` 返回 RFC 8414 的元数据文档。

**最低必填字段**（缺一个即不合规）：

| 字段 | 说明 |
|---|---|
| `issuer` | 授权服务器的标识，**必须**与签发令牌的 `iss` **逐字相同** |
| `authorization_endpoint` | 授权端点（**用户浏览器导航**到它） |
| `token_endpoint` | 令牌端点 |
| `jwks_uri` | 公钥集地址 |
| `response_types_supported` | 至少含 `code` |
| `grant_types_supported` | 至少含 `authorization_code` |
| `code_challenge_methods_supported` | PKCE 方法；**本平台只支持 `S256`** |
| `token_endpoint_auth_methods_supported` | 客户端认证方式 |

**可选但本平台已实现**：`device_authorization_endpoint` / `introspection_endpoint` /
`revocation_endpoint` / `introspection_endpoint_auth_methods_supported` /
`revocation_endpoint_auth_methods_supported` / `scopes_supported` /
`access_token_expires_in`。

> ⚠️ **`authorization_endpoint` 可以不是「返回 302 的端点」** ——
> 本平台把它实现为**前端路由**（返回 HTML 页面），由页面在取得用户同意后
> **在浏览器侧**跳转到 `redirect_uri`。
> 这是 RFC 6749 §3.1 允许的形态（「**用户代理**与授权服务器交互」），
> 但对客户端实现者有影响，故在此显式声明。

## C14 OAuth 协议端点的错误体（v3 新增）

### 14.1 问题

契约 C6 规定「统一错误响应体（RFC 9457 Problem Details）」。
但 OAuth2 的端点（`/api/oauth/token`、`/introspect`、`/revoke`、
`/device_authorization`）**是标准协议端点** —— 第三方应用按 RFC 实现，
错误体形状必须**逐字符合 RFC**，否则现成的 OAuth 客户端库**解析不了**。

### 14.2 规则

| 端点类别 | 错误体 | 依据 |
|---|---|---|
| **OAuth 协议端点** | `{"error": "<protocol_error>", "error_description": "<…>"}` | RFC 6749 §5.2 / RFC 8628 §3.5 / RFC 7662 §2.3 / RFC 7009 §2.2 |
| **平台自有端点**（含 OAuth 的**管理**端点） | RFC 9457 Problem Details（C6） | 本契约 C6 |

- 协议错误的**取值集合**：`invalid_request` / `invalid_client` / `invalid_grant` /
  `unauthorized_client` / `unsupported_grant_type` / `unsupported_response_type` /
  `invalid_scope` / `access_denied` / `login_required` / `consent_required` /
  `authorization_pending` / `slow_down` / `expired_token` / `server_error`
- 协议错误**没有** `type` / `title` / `status` / `instance` / `code` / `trace_id` 字段。
- 协议错误**不得**在 `error_description` 里放中文（与 C6「面向用户的中文文案由前端 i18n 渲染」同理）。
- **HTTP 状态码**按 RFC：认证失败 `401`、其余 `400`、成功 `200`。
  ⚠️ 注意这与 C6 的「`status` 字段与 HTTP 状态码一致」不冲突 —— 协议端点**没有** `status` 字段。

### 14.3 两套错误标识的辨析

同一套系统里同时存在「小写协议码」与「大写平台码」时，**按端点分类，不按大小写猜**：

| | 协议码 | 平台码 |
|---|---|---|
| 形状 | `{"error": "invalid_grant"}` | `{"code": "OAUTH_TICKET_INVALID", "status": 400, …}` |
| 风格 | 小写下划线 | 大写下划线 |
| 出现处 | `/api/oauth/token` 等**协议端点** | `/api/oauth/clients` 等**管理端点** |

### 14.4 一条容易踩的边界

**OAuth 的授权请求端点**（`/api/oauth/authorize/*`）在本平台是**平台自有端点**
（返回 Problem Details），**不是** RFC 6749 §3.1 那个「返回 302 的授权端点」
→ 它按 C6 说平台的话。

> 理由：授权请求由**前端路由**承接（D203 / REQ-022 decisions），
> 前端拿到的是**结构化结果**（`ticket` / `redirectTo`），不是 302；
> 参数校验失败时也不存在「redirect_uri 非法 → 无法重定向」的特例分支。
