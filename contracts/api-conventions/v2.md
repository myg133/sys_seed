## 消费方注意

第 1 条（`source` 增加 `default`）在类型上**可能是破坏性的**：

> 如果客户端对 `source` 做了**穷举**（例如 TypeScript 的 `switch` 配 `never` 兜底、
> Rust 的 `match` 不带 `_` 分支），新增取值会让它编译失败或运行时报错。

- **正确的消费方式**：把 `source` 当作**开放枚举**处理 —— 未知取值**必须**原样透传或降级，
  **不得** panic / 报错 / 当作非法响应。
- 契约保证的只有：`platform` / `tenant` / `space` / `default` 四个取值**当前**会出现在响应里；
  未来可能继续增加，**增加不视为破坏性变更**。

## C9 配置键名与配置响应（v2 修订）

### 9.1 键名

- 键名 **camelCase**，层级用 `.` 分隔：`logo`、`primaryColor`、`theme.radius`

### 9.2 作用域与优先级

- 作用域：`platform` / `tenant` / `space`，优先级 **空间 > 租户 > 平台**
- 配置读取响应带 `source` 字段暴露命中的层级：

```json
{ "key": "logo", "value": "/branding/tenant-a.svg", "source": "tenant" }
```

### 9.3 `source` 的四个取值

| `source` | 含义 |
|---|---|
| `space` | 空间级显式配置 |
| `tenant` | 租户级显式配置 |
| `platform` | 平台级显式配置 |
| **`default`** | **谁都没配，用的是 manifest 登记的默认值**（本版新增） |

**为什么要 `default`**：没有它就区分不出「平台管理员显式把 logo 配成 X」
与「谁都没配、manifest 默认恰好是 X」—— 管理员在界面上看不出哪些值是「继承来的」，
排查「为什么这个租户的 logo 是 X」时会无从下手。

**键在 manifest 里完全没登记** → **404**（不是返回空值）。

### 9.4 作用域约束（本版新增）

**manifest 登记的 `ConfigSpec.scope` 表示「该键允许被覆盖到的最深层」**，不是「它属于哪一层」。

| 登记的 `scope` | 允许写入的层 | 例 |
|---|---|---|
| `platform` | **只能平台级** | `conflictStrategy`（改它等于绕过人工裁决） |
| `tenant` | 平台级 + 租户级 | 每租户不同的业务参数 |
| `space` | 平台级 + 租户级 + 空间级 | 品牌与主题（各工作区可不同） |

往**比登记更深**的层写 → **400**，错误信息给出该键允许的作用域。

**这条是强制的，不是建议**：否则任意租户都能覆盖本该平台独有的配置。

### 9.5 配置值类型校验（本版新增）

- **键与默认值在业务模块 `manifest.json` 的 `config` 段声明**，平台据此自动生成配置界面
- **写入未声明的键 → 400**（未声明的键既没有类型信息也没有默认值，
  允许写入会让前端拿到无法校验的值、配置界面也生成不出来）
- 值按登记的 `type` 校验，判定基于 **JSON 类型**：

| 登记的 `type` | 接受 | **不接受** |
|---|---|---|
| `string` | JSON string | 数字、布尔、对象 |
| `number` | JSON number | **数字的字符串形式**（`"60"` ≠ `60`）、布尔 |
| `boolean` | JSON `true` / `false` | `0` / `1`、`"true"` |
| `array` | JSON array | 对象、单值 |
| `object` | JSON object | 数组、单值 |

类型不符 → **400**，错误信息给出**期望类型与实际类型**。

### 9.7 平台级配置走**独立端点**（本版新增）

平台级配置与租户/空间级配置**必须**是不同的端点：

| 端点 | 读/写 | 权限点 |
|---|---|---|
| `/api/config/entries` | 租户级 + 空间级 | `config:entry:write` |
| `/api/config/platform-entries` | **平台级** | 读 `config:platform:read` / 写 `config:platform:write` |

**理由**：权限校验在实现上是**静态路由层**（挂在路由上对所有请求生效）。
若平台级与租户级共用一条路由，只有租户级权限的人会连自己的配置都改不了；
若改成在处理器内按请求体判定，则平台级权限点**没有静态调用点**，
契约检查 C-5 会判它「已登记但无鉴权调用点」。

通用端点在收到**平台级键**时 → **整请求失败**（`403` `INSUFFICIENT_PERMISSION`），
不是「返回其余键、忽略平台级键」。

### 9.8 flag 只能经 flag 接口改（本版新增）

Feature Flag 的本体键与派生键位于**独立命名空间**，**不得**经通用配置写端点修改：

- 通用写端点收到已登记的 flag 名或 `flags.` 前缀的键 → **400** `CONFIG_FLAG_USE_FLAG_ENDPOINT`
- 改开关只能走 `PUT /api/feature-flags/{flag}`（需 `config:flag:write`）

**理由**：flag 与普通配置是**两种权限**。不隔离的话，任何能改配置的人都能改开关，
`config:flag:write` 形同虚设 —— 这是权限提升。

### 9.6 值的存储类型（本版新增）

配置值在数据库中一律用 **`jsonb`** 存储。

理由：配置值有类型，存 `TEXT` 要在应用层双重编码（JSON 字符串塞进 TEXT），
类型校验也只能落在应用层。`jsonb` 让类型由数据库保证。

## C10 Feature Flag 响应（v2 修订）

### 10.1 响应形状

功能关闭时返回 **200 + `enabled=false`**（不返回 404）：

```json
{ "flag": "new-invoice", "enabled": false, "source": "platform" }
```

理由：客户端需要能区分「功能关闭」与「接口不存在」，前者应优雅降级而非报错。

### 10.2 灰度必须**确定性**（本版新增）

按比例的灰度（`rolloutPercent`）**必须**满足：

```
bucket   = sha256("<flag>:<user_id>") 的前 4 字节按大端解释为 u32
enabled  = bucket % 100 < rolloutPercent
```

三条硬性要求：

| 要求 | 判据 |
|---|---|
| **确定性** | 同一用户对同一 flag 的判定**永远相同**（同一进程内 10 次一致） |
| **跨进程一致** | 两个独立进程 / 实例对同一用户的判定**必须相同** |
| **单调性** | `rolloutPercent` 从 10 调到 20 时，原本命中的用户**仍然命中** |

**禁止**用每次请求随机的方案，也**禁止**用每个进程随机播种的哈希
（如 Rust 的 `std::collections::hash_map::RandomState`）—— 后者在多实例部署下
表现为「同一用户一半请求命中」，比随机数更难排查。

### 10.3 无用户身份时 fail closed（本版新增）

灰度的判据是「这个**用户**在不在比例里」。**没有用户身份时该判据不成立** →
返回 `enabled = false`。

**不得**降级成「按比例随机给」：那等于让未认证请求绕过灰度控制，
且行为不可复现。

> 注意：`rolloutPercent = 100` **也不改变**这个结论 —— 缺的不是比例而是**身份**。

### 10.4 未声明的 flag（本版新增）

读一个**未在 manifest 登记**的 flag 名 → 返回 **200 + `enabled=false`**
（**不是** 404、**不是** 500），同时**记录一条告警日志**（含该 flag 名）。

理由：客户端拼错 flag 名时应当优雅降级（与 10.1 同源），
但服务端必须留下可发现的痕迹 —— 否则拼错永远没人知道。
