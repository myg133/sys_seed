## 变更

**新增契约检查 C-5：已登记权限点必须有鉴权调用点。**

v1 §4「C-2 的口径边界」明写了这个已知缺口：

> C-2 只验「权限点声明完整性」，不验「服务端是否真的执行了鉴权」。
> 一个只在 `permission.rs` 里定义、manifest 里也登记、但服务端从不做鉴权判断的权限点，
> C-2 会全绿且无告警。**等 REQ-009 落地鉴权中间件后，应补一条「已登记权限点必须有对应鉴权调用点」的检查。**

REQ-009 落地了鉴权中间件，本版本把那条检查补上，**缺口关闭**。

同时新增 manifest 的**可选**字段 `permissions[].condition`（属性级校验 / ABAC），见 §5。

**C-1 ~ C-4 的判定口径一律不变。** v1 的 5 个 trait 签名、dyn 兼容性限制、编译期注册方式全部不变。

## 破坏性变更说明

新增一条**强制失败**的检查，对既有消费方是破坏性变更：

- `modules/sandbox` 在 v1 下 C-2 全绿（它的权限点只定义常量、从不鉴权），
  在 v2 下 **C-5 会失败** —— 这是**预期效果**，REQ-009 内已把 sandbox 接上真实鉴权调用。
- 消费方**不需要改 trait 实现**，也不需要改 manifest 结构（`condition` 是可选字段）。
- 需要做的是：确保每个已登记权限点都有对应的鉴权调用点。

## §4 补充：C-5 的判定口径

### C-5：已登记权限点必须有鉴权调用点

| 情况 | 判定 |
|------|------|
| 已登记，且代码里有对应权限点的鉴权调用点 | ✅ 通过 |
| 已登记，但代码里**没有任何**鉴权调用点 | ❌ **失败**（登记了却不执行 = 假权限） |
| 代码里有鉴权调用点，但 manifest 未登记 | ❌ 失败（C-2 已覆盖） |
| 鉴权调用点的参数**不是字面量**（无法静态确认） | ❌ **失败**（无法确认 → 不放行，fail closed） |
| 出现**第二个**鉴权入口（绕过平台唯一入口） | ❌ **失败**（扫描会被绕过） |

### 实现方式与「唯一入口」

平台提供**唯一**的鉴权入口函数，签名形如：

```rust
router.route("/api/order/invoice/approve", post(approve))
    .route_layer(require_permission("order:invoice:approve"));
```

契约检查扫描各模块 `backend/**/*.rs`，**只认这一个入口**的调用，抽出其中的**字面量**权限点，
与 `manifest.json` 的 `permissions[]` 比对。

- **入口必须唯一** —— 模块自己写一个 `check_perm()` 就绕过了扫描。
  出现第二个鉴权入口 → 检查失败。
- **参数必须是字面量** —— `require_permission(&some_var)` 无法静态确认，
  判为**失败**而不是「跳过」。

> 与 C-2 的分工：C-2 验「代码用到的都在 manifest 里声明」，
> C-5 验「manifest 登记的都有真实的鉴权调用点」。两者方向相反，合起来才闭环。

### 为什么这条必须是失败而不是警告

一个「登记了但从不执行」的权限点，在界面上看起来是有权限控制，
实际接口完全裸奔 —— 这是**最坏的一类假象**：所有证据都显示「配好了」。
Sprint 2 复盘里 34 个 QA 问题中有 9 个属于「静默放行」类，
本条按「不得静默放行」的原则定为**失败**。

## §5 补充：manifest 的 `permissions[].condition`

| 字段 | 约束 |
|---|---|
| `permissions[].condition` | **可选**。属性级校验表达式；不填 = 无条件。语法见受限表达式 DSL（白名单字段 + 参数化 + 禁函数调用） |

- **可选**字段 → 既有 manifest 不需要改，向后兼容。
- schema 正本在 `crates/platform-core/src/extension/manifest_schema.rs`，
  快照在 `capabilities/schema/manifest.schema.json`，
  **两者必须完全一致**（v1 §5 的要求继续适用）。
- 条件里的属性**必须在白名单**内；引用白名单外的属性 → 判定为**不通过**（fail closed），
  不是「忽略条件放行」。

## 不是第 6 个扩展点：`PermissionChecker`

REQ-009 引入了 `PermissionChecker` trait（业务模块用它问「我能不能做这件事」）。
**它不属于本契约的扩展点集合**，理由是**方向相反**：

| | 扩展点（5 个） | `PermissionChecker` |
|---|---|---|
| 谁实现 | **业务模块** | **平台**（`platform-rbac`） |
| 谁调用 | **平台** | **业务模块** |
| 放哪 | `platform-core::extension` | `platform-core`（**不放 `extension` 下**） |

扩展点是「业务 ↔ 平台的接缝」，必须**双向都有角色**；
`PermissionChecker` 只是平台向业务提供的一个能力接口，
放进 `platform-core::extension` 会改变已冻结的扩展点集合的形状、逼所有消费方改契约。

**因此：5 个 trait 一个不动，本契约不需要为它升版本。**
