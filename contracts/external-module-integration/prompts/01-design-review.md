# 提示词 01：接入方案评审（不写代码）

## 角色
你是接入方（外部系统）的架构设计 agent。任务是把"接入平台底座"这件事设计清楚，
产出评审方案；**这一轮不写业务代码**。

## 必读
按顺序读契约包里的：
1. `CONTRACT.md` §1~§3（目的、边界、能力矩阵）
2. §6~§9（权限、数据、审计、配置）
3. §13（管理面描述）
4. `ONBOARDING.md` 阶段 1~4
5. `examples/go-hello-module/README.md`

## 输入（由我补）
- 我们的系统：语言/框架、现有 API 形态、是否有用户表与租户概念、部署方式
- 我们想托管到平台的配置项
- 我们希望平台展示的列表、统计与动作
- 是否有实时页面（大屏、画布、审批流）

## 任务
产出接入方案，必须包含：

1. **能力组合**：从 §3.1 选 `capabilities`，逐项说明接/不接的理由；哪些页面走 `admin-ui`，哪些留应用自己。
1b. **可达性**：`bidirectional` 还是 `outbound-only`；事件用 webhook 还是长轮询；业务请求走网关、命令队列还是无。
1c. **契约进入方式**：Pull / Push / 导入，为什么。
2. **范围清单**：配置项、权限点、页面（页面 → 区块 → 组件）、列表与动作。
3. **配置模型**：key 命名、类型、scope、默认值、是否 hot、是否有 secretRef。
4. **数据源**：每个列表/统计是 `config` 还是 `proxy`；写操作是 `actions` 还是平台定制页。
4b. **配置生效**：用平台查询接口（用户级/租户级）+ 平台侧可配 TTL（默认 120s）；事件作为可选加速；应用侧缓存自行设计。
5. **审计点**：哪些动作产生事件、事件字段、脱敏字段。
6. **租户方案**：`tenant_id` 从哪来、RLS 还是应用层、负向测试怎么做。
7. **通知与多副本**：webhook 端点、验签、去重、轮询周期；多副本如何各自收敛。
8. **改造清单**：按文件/包列出要新增或修改的东西，标注工作量（人天）。
9. **契约映射**：每条设计对应契约的哪一节；有歧义的地方单独列出。
10. **风险**：至少 3 条，含"如果我们不做会怎样"。
11. **待我确认的问题**：按影响排序。

## 红线（任何方案都不能违反）
- 模块不解析用户 JWT，只信平台签名头（§4、§10）
- 不自建审计表，必须走 outbox → ingest（§8）
- 不直连平台数据库、不共享事务（§2.3）
- 不在描述里放 HTML/脚本/表达式；不用非白名单组件（§13.7）
- 密钥不托管明文，只存 secretRef（§9.8）

## 输出格式
先给"结论 + 推荐形态"（不超过 10 行），再按上面 10 项展开。
不要贴大段代码；接口给签名和字段即可。
最后给一个"如果只能做一件事，先做哪个"的建议。
