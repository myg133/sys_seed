## 变更

首版。固化 REQ-003 交付的 5 个扩展点 trait 签名与配套契约检查规则。
**业务模块只依赖这些 trait，不依赖平台内部模块**（ADR-0001 D7 硬约束）。

> 与 [api-conventions v1](../api-conventions/v1.md) 的分工：
> api-conventions 管**接口约定**（路径、错误码、分页、命名）；
> 本契约管**扩展点签名**（业务模块与平台之间的接缝）。两者都要 pin。

## 1. 依赖方向

```text
platform-core (定义 trait)  ←  platform-contracts (契约测试套件)  ←  业务模块
```

## 2. 扩展点 trait 签名（冻结）

> ### ⚠️ dyn 兼容性限制（必读）
>
> **5 个 trait 均为 RPITIT 形态，不可用于 trait object。**
> `Box<dyn NotificationSender>` → `error[E0038]: the trait NotificationSender is not dyn compatible`。
>
> 原因：Rust 1.98 上字面 `async fn` 写在公开 trait 上会触发 `async_fn_in_trait` lint
> （`clippy -D warnings` 下失败）且无法保证 `Send`；`async-trait` 会引入第三方依赖。
> 故 trait 侧用 `-> impl Future<Output = ..> + Send` 展开。
>
> **实现方仍写 `async fn`，调用点写法不变。**
> 但**不要**假设 trait object 可用。
> 异构汇聚（多通道通知收集、多工作流处理器收集）**延后到 REQ-015 / REQ-017 决策**：
> 届时要么加对象安全包装，要么引入 `async-trait` —— 那属于本契约的破坏性变更，需升 v2。

### 2.1 PlatformModule —— 模块注册

```rust
pub trait PlatformModule: Send + Sync + 'static {
    fn id(&self) -> &'static str;
    fn version(&self) -> &'static str;
    fn dependencies(&self) -> &[&'static str] { &[] }
    fn setup(&self, ctx: &ModuleContext) -> anyhow::Result<()> { Ok(()) }
    fn enabled(&self) -> bool { true }
}
```

`id` 必须与 `manifest.json` 的 `id` 一致（契约检查 C-1）。

### 2.2 Repository —— 数据访问

```rust
pub trait Repository<T: Send + Sync + 'static>: Send + Sync {
    type Id: Send + Sync;

    fn find(&self, ctx: &RequestContext, id: &Self::Id)
        -> impl Future<Output = anyhow::Result<Option<T>>> + Send;
    fn list(&self, ctx: &RequestContext, q: &ListQuery)
        -> impl Future<Output = anyhow::Result<List<T>>> + Send;
    fn insert(&self, ctx: &RequestContext, item: &T)
        -> impl Future<Output = anyhow::Result<T>> + Send;
    fn update(&self, ctx: &RequestContext, item: &T)
        -> impl Future<Output = anyhow::Result<T>> + Send;
    fn delete(&self, ctx: &RequestContext, id: &Self::Id)
        -> impl Future<Output = anyhow::Result<()>> + Send;
}
```

**每个方法都强制携带 `ctx: &RequestContext`** —— 实现方**没有别的途径拿到租户**，
漏传就编译不过。这是租户隔离的编译期保证。

### 2.3 Auditable —— 审计埋点

```rust
pub trait Auditable: Send + Sync {
    fn audit_events(&self) -> &[AuditEventSpec];
}
```

平台据此自动埋点，业务模块**不手工写审计表**。

### 2.4 NotificationSender —— 通知投递

```rust
pub trait NotificationSender: Send + Sync {
    fn channel(&self) -> &str;
    fn send(&self, ctx: &RequestContext, msg: &NotificationMessage)
        -> impl Future<Output = anyhow::Result<DeliveryResult>> + Send;
}
```

### 2.5 WorkflowHandler —— 工作流接入

```rust
pub trait WorkflowHandler: Send + Sync {
    fn workflow_key(&self) -> &'static str;
    fn on_transition(&self, ctx: &RequestContext, ev: &TransitionEvent)
        -> impl Future<Output = anyhow::Result<()>> + Send;
}
```

## 3. 编译期注册

用 `inventory` crate 做编译期自动注册（**本期唯一新增第三方依赖**，约 3KB）。

```rust
inventory::collect!(ModuleRegistration);
pub fn discover() -> Vec<&'static dyn PlatformModule> { /* ... */ }
```

> `inventory` 0.3 的 `Collect: Sized` 约束使 `collect!(dyn Trait)` 无法编译，
> 因此注册表元素用包装类型 `ModuleRegistration`，对外 `discover()` 签名不变。

## 4. 契约检查 C-1 ~ C-4

业务模块在自己的 `tests/contracts.rs` 接入 `#[platform_module_contract]`：

| 检查 | 内容 | 失败条件 |
|---|---|---|
| **C-1** | manifest 与实现一致 | `manifest.id` ≠ `module.id()`；version / enabled / dependencies 不一致 |
| **C-2** | 权限点声明完整 | 代码里用到但 manifest 没声明 → **失败**；manifest 声明了但没用到 → **警告** |
| **C-3** | 租户隔离生效 | `list()` 串租户、`find()` 命中他人记录 → **失败** |
| **C-4** | 事务边界 | 声明跨表写但不经平台事务辅助 → **失败** |

### C-2 的口径边界

**C-2 只验「权限点声明完整性」，不验「服务端是否真的执行了鉴权」。**

已知局限：一个只在 `permission.rs` 里定义、manifest 里也登记、但服务端从不做鉴权判断的权限点，
C-2 会全绿且无告警。等 REQ-009 落地鉴权中间件后，应补一条「已登记权限点必须有对应鉴权调用点」的检查。

### C-3 的本期口径

本期平台**没有 DB 访问层**（sqlx 推迟到 REQ-006/007），C-3 **不连数据库**，由两条保证构成：

1. **编译期保证** —— 见 §2.2，租户只能从 `ctx` 拿
2. **行为验证** —— 双租户夹具，`list()` 只返本租户数据，`find()` 查他租户 id 返回 `None`

等 REQ-006 落地真实 DAO 层后，C-3 再叠加「真实库多租户数据集」验证。

## 5. manifest.json 结构

模块清单由 `manifest.json` 描述，schema 定义在
`crates/platform-core/src/extension/manifest_schema.rs`，并收录到
`capabilities/schema/manifest.schema.json`（REQ-004 的能力索引自动生成）。

必填字段：`id` / `name` / `version` / `enabled` / `permissions` / `menus` / `dependencies`。

| 字段 | 约束 |
|---|---|
| `id` | 小写字母开头的 kebab-case；**与目录名一致**；与 `module.id()` 一致 |
| `version` | semver `x.y.z` |
| `permissions[].code` | `module:resource:action`，全小写 kebab-case 三段式（契约 api-conventions C4） |
| `menus[].route` | 以 `/` 开头的路径，全小写 |
| `dependencies[]` | 元素按 `id` 规则校验 |

> schema 与平台校验器**必须完全一致** —— schema 是对外发布的，第三方会拿它做校验。
> 2026-11-18 QA 发现过两处分歧（`id` 正则宽严不一、`dependencies[]` 与 `name` 缺约束），
> 已要求收紧 schema 至与实现一致。

## 6. 破坏性变更

以下任一改动视为**破坏性**，需升 v2 并给消费方迁移窗口：

- 5 个 trait 的方法签名增删改
- trait 侧从 RPITIT 改为 `#[async_trait]`（或反之）—— 这会改变 dyn 兼容性
- 契约检查 C-1 ~ C-4 的判定口径
- manifest 的必填字段或字段约束
- `discover()` 的签名
