## 背景

底座由多个子需求并行开发，最容易出的事故不是代码 bug，而是**契约漂移**：
A 改了字段命名，B 还按另一套实现，直到合并那天才发现。
本契约锁死所有跨模块共享的接口约定，各子需求的 Dev 在 `feature-meta/manifest.json` 中 pin 本版本。

## C2 业务 API 路径形式

```
/api/<module>/<resource>/<action>
```

**动作放路径末段**，而不是 `POST /api/order/invoice/{id}/approve` 的资源子路径形式。
理由：权限点与 URL 段一一对应，`order:invoice:approve` ↔ `/api/order/invoice/approve`，
路径即权限点，可读性与可审查性都更好。

- 列表 / 详情：`GET /api/<module>/<resource>`、`GET /api/<module>/<resource>/{id}`
- 动作：`GET|POST /api/<module>/<resource>/<action>`（`<action>` 为动词，不与资源同名）
- 路径全小写连字符分隔（`order-invoice`），不用驼峰、不用下划线

## C3 上下文请求头

| 请求头 | 含义 | 缺失时 |
|---|---|---|
| `X-Tenant-Id` | 租户上下文 | 由认证令牌推断；推断不出返回 401 |
| `X-Space-Id` | 空间/项目上下文 | 视为「不限空间」，不返回错误 |

- 请求头值必须与令牌绑定的租户一致，不一致返回 404（不泄露资源存在性）
- 平台中间件负责解析并注入上下文，业务模块**不得手工解析请求头**
- 上下文自动贯穿 DB / 缓存 / 消息 / 日志，业务模块**不得手工加 tenant_id 过滤条件**

## C4 权限点与路径映射

权限点编码固定为 `module:resource:action`，全小写连字符分隔：

```
order:invoice:read
order:invoice:write
order:invoice:approve
```

- 允许通配 `order:*`（角色层面）
- 权限点在业务模块的 `manifest.json` 声明，由平台汇总进注册表
- 前端 `can()` 与后端鉴权**读同一份注册表**，不允许各自维护映射

## C5 越权响应码口径

| 场景 | 响应码 | 理由 |
|---|---|---|
| 资源类越权（访问不属于自己的资源） | **404** | 不泄露资源是否存在 |
| 动作类越权（有资源但无操作权限） | **403** | 资源本可见，是操作被拒 |

两类都**不得**在响应体或 `detail` 中暴露被拒资源的存在性细节。

## C6 统一错误响应体

采用 RFC 9457（Problem Details）：

```json
{
  "type": "https://errors.base.example/insufficient-permission",
  "title": "权限不足",
  "status": 403,
  "detail": "当前角色缺少 order:invoice:approve",
  "instance": "/api/order/invoice/approve",
  "code": "INSUFFICIENT_PERMISSION",
  "trace_id": "01H8X...",
  "params": { "required": "order:invoice:approve" }
}
```

- `code` 是**稳定的机器可读错误码**（大写 + 下划线），前端据此做逻辑判断
- `detail` 是面向开发者的英文描述；**面向用户的中文文案由前端 i18n 渲染**，
  后端**不得**在 `detail` 里拼中文句子（见 REQ-021 AC-S-029）
- `trace_id` 必带，用于串联日志

## C7 分页、排序、过滤

| 项 | 约定 |
|---|---|
| 分页方式 | **游标分页**（`cursor` + `limit`），响应含 `next_cursor`；列表默认 `limit=20`，上限 200 |
| 兼容分页 | 需要页码跳转时用 `?page=N&page_size=M`，二者互斥，同时给返回 400 |
| 排序 | `?sort=-created_at,name`，字段白名单由各模块声明，未声明字段返回 400 |
| 过滤 | 通用 `?filter[field][op]=value`，`op` 白名单 `eq/ne/in/contains/range` |
| 数据范围过滤 | 由平台**自动叠加**，业务模块不得自行实现，也不得提供绕过开关 |

游标分页为主是因为深翻页在变动的数据集上会漏数据或重复，而管理系统列表普遍需要深翻。

## C8 幂等键

- 写操作（`POST` / `PUT` / `DELETE`）支持 `Idempotency-Key` 请求头（UUID）
- 同一 key 在 24 小时内重复请求返回首次结果，不重复执行
- 幂等记录随租户维度存储，跨租户不共享

## C9 配置键名与配置响应

- 键名 **camelCase**，层级用 `.` 分隔：`logo`、`primaryColor`、`theme.radius`
- 作用域：`platform` / `tenant` / `space`，优先级 空间 > 租户 > 平台
- 配置读取响应带 `source` 字段暴露命中的层级：

```json
{ "key": "logo", "value": "/branding/tenant-a.svg", "source": "tenant" }
```

- **配置键与默认值在业务模块 `manifest.json` 的 `config` 段声明**，平台据此自动生成配置界面

## C10 Feature Flag 响应

功能关闭时返回 **200 + `enabled=false`**（不返回 404）：

```json
{ "flag": "new-invoice", "enabled": false, "source": "platform" }
```

理由：客户端需要能区分「功能关闭」与「接口不存在」，前者应优雅降级而非报错。

## C11 Schema 渲染器组件名

`@base/schema` 导出两个渲染器：

| 组件 | 用途 |
|---|---|
| `SchemaTable` | 按元数据渲染列表 |
| `SchemaForm` | 按元数据渲染表单 |

元数据的 JSON Schema 定义收录在 `capabilities/schema/metadata.schema.json`（自动生成）。

## C12 审计哈希链字段

审计表固定字段：`id` / `tenant_id` / `actor_id` / `action` / `object_type` / `object_id` /
`before` / `after` / `ip` / `user_agent` / `created_at` / `prev_hash` / `hash`。

- `hash = sha256(prev_hash + 规范化事件体)`
- 表只允许 `INSERT`，不允许 `UPDATE` / `DELETE`（权限层面禁止）

## C13 命名与编码约定

| 场景 | 约定 |
|---|---|
| JSON 字段 | camelCase |
| 数据库列 | snake_case |
| Rust 标识符 | snake_case |
| 前端 TS 标识符 | camelCase |
| 时间 | 一律 UTC 存储（`timestamptz`），展示按用户/租户时区渲染 |
| 金额 | 一律用**最小单位的整数**（如分），禁止浮点 |
| 语言 | 面向用户文案由前端 i18n 渲染；后端只返回错误码 + 参数 |
| 布尔 | JSON 用 `true` / `false`，不用 `0` / `1` |
