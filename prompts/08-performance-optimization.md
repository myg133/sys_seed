# 任务：做性能优化

## 目标

在**不改变行为**的前提下把一段代码改快，并给出可复现的证据。

## 输入

- `<模块名>`：业务模块名
- `<热点位置>`：慢在哪（函数 / 接口 / 组件）
- `<当前表现>`：现状（耗时、数据量、调用频率）
- `<目标>`：想要达到什么（如「列表接口 P95 < 200ms」）

## 步骤

1. **先读** `AGENTS.md` 与 `capabilities/index.json`，
   确认**平台已经提供**的能力，别在业务侧优化一个平台已经做过的事：
   - `already_provided.list_query` —— 游标分页（`limit` 默认 20、上限 200）
     与过滤算子白名单已经定义好；分页参数别自己造；
   - `already_provided.request_context` —— 租户过滤由 `Repository` 按 `ctx` 做，
     **不要**为了「少查一点」绕过 `ctx` 自己加条件（那会破坏租户隔离的编译期保证）。
2. **先量后改**：没有基线数据就不要动代码。
   - Rust：写一个能复现的基准用例（`#[test]` 里计时即可，本仓库不引
     `criterion` 之类的第三方基准库）；
   - 前端：用 `performance.now()` 在用例里测，别引第三方基准库。
3. **找真正的瓶颈**（按可能性排序）：
   - **N+1 查询**：循环里逐条取数据 → 改成批量取一次再在内存里关联；
   - **缺索引 / 全表扫描**：本期没有 DB 层，先在内存仓储里看是不是
     `list()` 把全部记录拉出来再过滤（改成先过滤再截断）；
   - **重复计算**：同样的表达式在循环里反复算 → 提到循环外；
   - **不必要的数据拷贝**：大结构体按值传递 → 改引用；
   - **前端重复渲染**：列表里每项都建新对象 → 用稳定 key。
4. **改的时候守住行为**：优化前后**同样的测试必须都绿**。
   契约检查 C-1 ~ C-4 尤其不能破（尤其是 C-3 租户隔离与 C-4 事务边界）。
5. **给对比证据**：改动前后各跑一次基准，把两组数字写进
   `modules/<模块名>/AGENTS.md` 或提交说明里。
6. **自验**：
   ```bash
   cargo test -p <模块名> -- --test-threads=2
   cargo xtask check-modules
   cargo xtask capabilities --check
   ```

## 约束

- 不修改 `crates/platform-core/` 与 `crates/platform-contracts/`。
- **不引入新的第三方依赖**（基准库、并发库、缓存库都不许）——
  本仓库当前的硬基线是零新增第三方依赖 + 低配机冷编译敏感。
- 不为了性能绕过 `ctx` / `Repository` 的租户过滤。
- 不改错误码、不改错误信息、不改接口语义（性能优化不是行为变更）。
- 排序 / 过滤字段的白名单规则不能因为「快」而放宽
  （白名单外字段直接报错是 `api-conventions v1` C7 的要求）。
- 不改 `Cargo.toml` 的 profile，不加 linker 配置。

## 验收

- [ ] 有改动前的基线数字与改动后的对比数字（可复现）
- [ ] 行为未变：同一批测试改动前后都绿，契约检查 C-1 ~ C-4 仍通过
- [ ] 没有引入任何新的第三方依赖
- [ ] 没有绕过 `ctx` 做租户过滤
- [ ] `cargo test --workspace -- --test-threads=2` 全绿
- [ ] `cargo fmt --all --check` / `cargo clippy --workspace --all-targets -- -D warnings` 无告警
